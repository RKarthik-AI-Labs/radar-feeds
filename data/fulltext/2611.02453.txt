Abstract.

Cohort memory can support LLM-based recommendation planning through group-level user profiles and advice. As outcome feedback becomes available, this guidance may need to be updated while preserving the underlying observations. We present 
RecGroupMemory
, a workflow that provides this memory to an orchestration LLM and separates memory construction from feedback-based revision. It uses feedback from the previous day to revise decision guidance, while validation checks keep selected source values unchanged. Online comparisons were conducted among Taobao users with low purchasing power selected by the business team. Relative to a no-memory baseline, memory without feedback and memory with feedback showed increases of 
 and 
, respectively, in the number of guided transaction users.

Keywords: 
e-commerce recommendation, cohort memory, large language models, online feedback, user profiles

1. 
Introduction

Cohort memory summarizes observations about users with shared characteristics to support an orchestration LLM in planning Web recommendation workflows across requests. Delayed browsing and transaction outcomes may challenge earlier guidance without changing the cohort definition, observation window, or recorded metrics. Updating this memory requires revising recommendation judgments while preserving their observational basis. Unconstrained regeneration risks changing the recorded observations. The same observations can support different planning judgments as later outcomes arrive. Keeping observations separate from guidance makes these revisions explicit: an update changes the interpretation of a cohort record while retaining the evidence against which that interpretation can be checked.

2. 
The RecGroupMemory Framework

The framework separates memory construction, feedback revision, and online planning. The Evidence Extractor organizes observations from multiple sources in Shallow Memory. The Memory Builder combines these observations into a cohort memory record, and the Memory Refiner reassesses its guidance when linked outcome feedback becomes available. The online orchestration LLM uses the published Profile and Advise to plan the recommendation workflow. Feedback revision updates the planning context without scoring items or executing downstream recommendation stages.

Each update operates on a cohort memory record rather than an individual interaction or a model parameter. The record contains observations for a defined user group and time window, along with guidance derived from them. This guidance can be revised while selected source values remain unchanged.

2.2. 
Constrained Decision Revision

Figure

: schema version, cohort, recommender version, memory scope, segment definition, observation window, and aggregated metrics. Profile and Advise must remain nonempty strings. The prompt permits changes to their content, structured advice, profile confidence, uncertainties, and change metadata. The validator checks selected values and required structure, rather than enforcing a complete whitelist of editable JSON fields. The fixed values identify the cohort, observation window, and measured behavior to which the advice applies. Preserving them prevents an apparent improvement in the narrative from being obtained by changing the population or measurements. Editable decision content instead describes how those observations should inform subsequent planning.

Profile summarizes the cohort’s current funnel performance and what the feedback suggests about the existing strategy. Advise specifies adjustments for particular objectives, their rationale, and rollback conditions. The prompt records missing metrics and data-quality concerns in uncertainties and summarizes changes from 
 in change metadata. Confidence and uncertainty qualify the interpretation. The conversion-prioritized prompt requests a concise profile and ordered advice, with final discrete strengths stored in structured advice.

Objective priorities are configurable. The conversion-prioritized prompt emphasizes CVR and suppresses GMV adjustment; the browsing-prioritized prompt emphasizes IPV with transaction safeguards. The conversion-prioritized prompt permits CVR strengthening only when the relative changes in both transaction UV and order count are available and strictly positive. Positive intermediate browsing feedback cannot substitute for either outcome. If either relative change is missing or non-positive, the prompt calls for conservative conversion advice. It separates assessment of the previous strategy from selection of the next adjustment: retaining the current advice under insufficient evidence does not imply that the strategy succeeded.

For example, positive browsing feedback accompanied by missing transaction UV cannot satisfy the conversion-strengthening condition. The record can remain eligible for revision while that particular adjustment lacks support. The resulting Profile can describe the observed browsing response, and Advise can retain a conservative conversion position while recording the missing outcome in uncertainties.

The Memory Refiner returns a complete JSON response rather than a patch. The feedback node parses this response and checks fixed-value equality, required text fields, and structured advice. An invalid candidate may undergo one repair attempt, which asks the model to restore valid JSON and fixed values while retaining its conclusions and advice text. The repaired candidate is validated again against 
, but these checks do not establish semantic equivalence. Invalid source records bypass generation, and handled model or validation failures retain the original response.

An accepted update replaces the response and model metadata while retaining source evidence columns. The feedback node writes records to database partition 
; publication to Shallow Memory occurs in a separate stage. The store retains Profile, Advise, and Evidence, but only Profile and Advise enter the orchestration LLM for workflow planning. Stored memory and online evidence support later updates. The revision node does not produce ranking weights. The database stores the revision output, whereas Shallow Memory makes the published record available to later planning and revision. A successful database write and a published memory record are therefore separate workflow outcomes. Figure

Before processing, source IDs must be nonempty and unique. After writing the records, the job checks that the output and input have the same record count and ID set. Per-record statuses distinguish accepted generation from ineligible input, invalid source, and handled model failures. Acceptance indicates successful validation, not necessarily changed advice or improved outcomes. Fallback preserves record coverage without establishing that the original advice is optimal. Publication failures remain the responsibility of the surrounding pipeline.

4. 
Discussion and Limitations

Validation covers selected source values and output structure; semantic correctness still depends on the LLM and prompt instructions. Historical retrieval is not tied to a specific date or content hash, so Memory ID alone cannot identify the version previously used online. Fallback operates on individual records, and a failed partition write may still leave partial output.

The experiments evaluate complete workflow configurations on a selected user population. Deployment artifacts corresponding to the experiments are unavailable, limiting attribution to individual revision safeguards. Broader deployment and evaluation of these safeguards require feedback ablations under matched conditions, traces linking served memory to revisions, and runtime measurements. Natural-language memory and small cohorts also require access controls, retention limits, and aggregation safeguards. Evaluation should distinguish record eligibility, validation acceptance, changes in advice, and downstream outcomes. These events answer different questions about coverage, structural reliability, revision behavior, and recommendation performance. Recording them separately would make failures and unchanged advice easier to interpret without treating every accepted response as an effective update.

5. 
Conclusion

The framework integrates cohort memory construction, feedback revision, and LLM-based recommendation planning. It revises Profile and Advise while preserving selected source values, using validation and fallback to the original record to control updates.
