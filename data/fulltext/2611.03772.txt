Abstract

Third-party Agent Skills extend what an autonomous agent can do, but a malicious Skill can hide data exposure or
output manipulation inside a legitimate workflow. Neither reading a Skill’s description nor granting it tool
permissions tells whether its execution meets the user’s security requirements. We introduce 
RuntimeTickets
, a
protocol that enforces and audits these requirements while a Skill runs. From released malicious-Skill datasets we
derive a risk model and build adversarial-benign Skill pairs. From the task’s delivery contract, a language model
proposes security obligations for that task. Each obligation cites the Skill lines it answers, and the ticket
tightens the host’s approvals into fine-grained allowed actions but never loosens them. A runtime gate checks the
recipient, object and amount of every outbound send before forwarding it, and trusted monitors record the effects
within their observation scope. The ticket links these checks and observations to the approved obligations of each
Skill run, and a deterministic decoder turns the ticket’s status into governable data flows and verifies each
obligation. Neither enforcement nor decoding involves a language model, so text injected by a Skill can change the
proposal but never the rule that decides a send. We evaluate 
RuntimeTickets
 at the network egress boundary of three
unmodified agent frameworks against production Skill scanners and runtime baselines, among them an AgentBound-derived
allow-list and SkillGuard. 
RuntimeTickets
 eliminated both failure modes of current Skill defenses, overlook (malicious
Skills let through) and overkill (benign Skills blocked): its overlook rate was 0.0% and its overkill rate
0.0%, while the scanners erred on both sides. 
RuntimeTickets
 ties approved requirements to verifiable
execution evidence and offers a common foundation for the safe and auditable deployment of third-party Skills.

1 
Introduction

Agent Skills are packages of instructions, scripts and reference files that an agent loads on demand 
(
Anthropic 2026
)
. Frameworks such as OpenClaw and Hermes Agent load them 
(
OpenClaw Foundation 2026
; 
Nous Research 2026
)
, and registries such as ClawHub and Skills.sh let third parties distribute them 
(
OpenClaw 2026
; 
Vercel 2026
)
. A loaded Skill runs with the user’s files, credentials and network access, usually without any mandatory review. The harm is already well documented:
(1) 
Vulnerable and malicious Skills are common.
 One detector flagged at least one vulnerability in 26.1% of 31,132 Skills 
(
Liu et al. 2026b
)
, and behavioral verification confirmed 157 malicious Skills among 98,380 
(
Liu et al. 2026a
)
.
(2) 
Secrets leak at run time.
 520 of 17,022 sampled Skills leaked credentials, and 89.6% of the leaked credentials were immediately exploitable 
(
Chen et al. 2026
)
.
(3) 
Attacks have reached production registries.
 Antiy CERT counts at least 1,184 malicious Skills that have appeared on ClawHub, and the ClawHavoc campaign delivered infostealers that take browser passwords, SSH keys and exchange API keys 
(
Antiy CERT 2026
)
.
(4) 
Default protection is weak, and defenses disagree.
 Only 0.12% of the Skills that five scanners analyzed were flagged by all five 
(
Holzbauer et al. 2026
)
. OpenClaw without an added defense layer resisted sandbox escape in 17% of attacks on average 
(
Shan et al. 2026
)
.

Consider a Skill that drafts a report and mails it to the recipient named in the task. A malicious version keeps every benign instruction and adds one more: also mail the workspace’s credential file to the same recipient. Both go to the same address and differ only in what they carry. Whether a send is harmful depends on the task and the object, and a check of the package alone sees neither.

Existing defenses leave three gaps (Section 
4
, Table 
2
). Source scanners judge a package once, before any task exists 
(
Cisco AI Defense 2026
; 
NVIDIA 2026
)
. A deployment-wide allow-list forwards every send to an address it already permits, including the task’s own recipient. Most runtime monitors judge each tool call 
(
Pan et al. 2026
; 
Mou et al. 2026
)
, so a send made by a helper script reaches them as the command that launched the script, not as a send. AgentBound does see sends at the network boundary, but it applies one fixed policy that no task narrows 
(
Bühler et al. 2026
)
.

A Skill’s harm lies in what it does at run time, so we check each effect against requirements written for the task at hand. In 
RuntimeTickets
 (Figure 
1
), a language model proposes a 
ticket
 once per task and Skill. The ticket’s obligations name the recipients, objects and amounts the task requires. The host approves a ticket only if it tightens the host grant and never loosens it. A model-free gate at the egress boundary allows an effect only when the frozen ticket covers it. After the run, a deterministic decoder tells the user whether each obligation held (
Supported
), was broken (
Violated
) or has no evidence (
Unknown
), and the account records which layer refused each blocked request.

We build 60 twin pairs from released malicious-Skill datasets (Section 
2
) and run, on unmodified agent frameworks, the pairs whose attack an agent attempts without a defense. Under 
RuntimeTickets
 no attempted attack got through and no benign run was blocked. Without a gate every attempted attack got through, and under an AgentBound-derived allow-list 75.0% did, including attacks that reuse the task’s recipient. SkillGuard, run on its native Claude Code agent, also let such attacks through. Every account re-derived exactly, each refusal carried the layer that made it, and on a separate test set no tampered account produced a false 
Supported
. Our contributions are:

•

We build
 a risk model and twin pairs from released malicious Skills (Section 
2
).

•

We design
 
RuntimeTickets
, where a model proposes per-task requirements and a model-free core enforces and audits them (Section 
3
).

•

We evaluate
 
RuntimeTickets
 against source scanners, an AgentBound-derived allow-list and SkillGuard on three unmodified frameworks, and audit its accounts (Section 
5
).

Risk Model

2.1 
Skills Act with the User’s Authority

An Agent Skill is a package of instructions (
SKILL.md
), helper scripts and reference files that an agent loads for a task 
(
Anthropic 2026
)
. A Skill that steers the agent can turn it into a confused deputy 
(
Hardy 1988
)
. Before a run, the host fixes three trusted elements. The 
task goal
 carries a 
delivery contract
 
: the agent must send an object that passes validator 
 to recipient 
, in a total amount of at most 
. The 
host grant
 
 lets every task send to a set of owned receivers 
 within a budget 
. The 
effect boundary
 is an egress proxy on every outbound connection.

2.2 
The Attacker Controls the Skill

Registries turn Skills into a software supply chain, and malicious packages in such chains are well documented 
(
Ohm et al. 2020
; 
Duan et al. 2021
)
. The attacker can write any byte of the Skill, so injected text can steer the agent and any model that reads it. The attacker cannot change the host’s inputs, its checking code or what the boundary observes. The issuer keys stay outside the container.

A defense meets the 
protection goal
 when a malicious Skill’s harmful effect does not happen and the defense does not prevent its benign twin’s task effect. Either half alone is trivial, since blocking every Skill or allowing every Skill satisfies one of them.

2.3 
Harm Categories and Their Observation

We define harm by its effect on the user’s system, not by the text of the Skill. An effect is what a trusted monitor can observe and a gate can refuse, and we call these monitors 
witnesses
. We grouped every malicious behavior labeled in released datasets and in a registry study 
(
Schmotz et al. 2026
; 
Guo et al. 2026
; 
Liu et al. 2026a
)
 by the effect it aims at. This gives the five categories of Table 
1
, from 
exfiltration
 (E1) to 
safeguard suppression
 (E5).

Two model-free witnesses score the effects. An egress witness at each owned receiver logs every send. A workspace witness compares file contents and mode bits before and after the run, so local destructive, access and safeguard effects are observed as well. We fixed the categories, the witnesses and the labels before any run, and a label audit then moved the pairs whose source label did not match their injected effect. Appendix 
A.2
 reports outcomes per category.

2.4 
Twin Pairs from Released Datasets

Every attack Skill and every benign twin comes from a released corpus. We write no Skill and no injection. We write only the trusted task and its input files. For Skill-Inject, we insert a released injection at its released line into a released carrier Skill, following the corpus’s own builder 
(
Schmotz et al. 2026
)
. The carrier as released is the benign twin, so the twins differ in the injected 
SKILL.md
 lines and, in some pairs, in the corpus’s own helper script. For MalSkillBench, the attack twin is a released malicious Skill and the benign twin is the corpus’s own benign Skill of the same name, both copied unchanged 
(
Guo et al. 2026
)
. Appendix 
A.1
 (Table 
4
) counts the files and lines that differ in each pair. Both twins share the trusted task, the host grant and the mock environment.

3 
RuntimeTickets

3.1 
Overview: The Only Model Step Comes Before the Run

A 
ticket
 is a set of obligations that states what the current task needs. A model proposes it once per task and Skill, before any run. The host approves it only if it tightens the host grant and never loosens it, and the gate then enforces the frozen ticket on every effect (Figure 
1
). Only the proposal uses a model. 
RuntimeTickets
 attaches to an unmodified framework through container configuration, so it does not depend on the agent, the hub or the driver model (Appendix 
B.7
).

3.3 
Creating and Enforcing a Ticket

Proposing and freezing.
 The generator is a Claude model from a family other than the drivers’ (Appendix 
B.1
). For each twin it receives one fixed request: the task with its delivery contract, the host grant, catalogs of resources and validators, the reply schema and the numbered Skill lines, which the request marks as untrusted data (Figure 
5
). The two twins’ requests differ only in the Skill lines and their binding. The compiler rejects any grant outside 
, copies the selected grants and the budget, and appends the proposed obligations after 
. The host then probes the compiled ticket before freezing it. The probe must allow a valid delivery to

 and is reported as a fallback (Algorithm

In this study the delivery contract fixes the three obligations, and the model grounds each one in the Skill. It cites the numbered lines that the obligation answers and states why, so an auditor can trace every obligation to the text that prompted it (Appendix

Enforcing at the effect boundary.
 The gate is a reference monitor over host authority 
(
Schneider 2000
)
. It reads a request’s operation, resource, recipient, object and amount, and never the text that produced the request. The second loop of Algorithm 
3.3
 checks authority first, so an unanticipated operation is refused without any written prohibition. A failed obligation or an exceeded budget then denies the request, and a missing fact or an open risk defers it, so the gate fails closed (Appendix 
B.2
 states the rule as one formula). A deferred send is not forwarded, and in deployment it acts as a denial unless the host resolves it, for example by asking the user. The gate records every decision before anything happens, and only an 
Allow
 counts toward the amount and forwards the request.

Each container can reach only the model channel and the egress proxy, which passes every connection through the gate. An injected send 
gets through
 when the proxy forwards it. Receivers are identified by host. An injected send that reuses the task’s recipient therefore models an attacker who can read what reaches that service, and only 
 and 
 can tell it from the delivery. The allow-list differs from a ticket only in the selected grants and the obligations, so by Proposition 1 it allows at least as much.

3.4 
Reading a Run Back

After a run, a user needs to know whether the Skill broke any obligation and, if a request was refused, why. The run’s 
account
 answers both (Figure 
1
). It is a set of records: each validation, decision, completion, observed effect, stream seal and closure. The issuer authenticates a record, chains it to the issuer’s previous record and binds it to the ticket through the ticket id. Without the keys, no record can be altered or reordered undetected 
(
Schneier & Kelsey 1999
; 
Crosby & Wallach 2009
)
, and removing a record breaks the chain or the closure of the account. For an obligation 
 and an account 
, a model-free decoder returns

(2)

An admitted counterexample is an authenticated record of an effect that breaks 
. A closed, sealed account has no unfinished operation and every declared stream sealed. A witnessed violation therefore stands despite coverage gaps, and an unobserved operation decodes to 
Unknown
. The host also attributes each refusal to the host grant, the host budget or a ticket rule and records the attribution in the account. Anyone who holds the contract and the account can recompute it, so the user sees why a request was refused and can check the reason (Appendices 
B.4
, 
B.5
 and 
E
). By Proposition 1, a steered generator cannot widen what a Skill may do, and after the freeze injected text cannot change the rule that decides a request. Appendix 
B.6
 answers five design questions (DQ1 to DQ5) from the mechanism alone.

5 
Experiments

We ask three questions. 
RQ1 (security):
 does 
RuntimeTickets
 stop the harmful effects of malicious Skills at run time, including sends that a deployment-wide allow-list lets through? 
RQ2 (utility):
 does it let benign Skills finish their work? 
RQ3 (auditability):
 can a third party re-derive a run from its account, and does missing or altered evidence ever yield a false 
Supported
?

5.1 
Setup

Two experiments, one set of twin pairs.
 In Experiment A, each source scanner judges all 60 twin pairs. In Experiment B, runtime defenses protect real agent runs on the pairs whose harm is an outbound send, the exfiltration pairs and one content-manipulation pair. Four framework-driver panels supply the runs (Appendix 
D.3
). A supplementary panel runs the same pairs on Claude Code, where SkillGuard joins as a fourth runtime defense (Appendix 
D.6
).

Environment.
 Each run executes one released Skill, malicious or benign, on an unmodified framework that a real language model drives. The environment is a mock. Owned receivers stand in for external services, so no data reaches a third party, and the workspace holds synthetic canaries. The task delivers its result by a plaintext upload that the validator can read, while the released injections use TLS. We also test the hardest case for an allow-list, an attacker who names an endpoint that the deployment already uses. Two owned receivers stand in for the destinations that the injections name most often. For a pair whose injection names one, an order fixed before any run decides whether it is the task’s own recipient (Appendix 
A.3
). Experiment B keeps the pairs whose injected action the driver attempted in a defense-free calibration (Appendix 
A.4
).

Frameworks and drivers.
 We use Hermes Agent (upstream revision of 14 September 2026) and OpenClaw 2026.6.10, and Claude Code for the supplementary panel. A 
panel
 pairs one framework with one driver model, 
deepseek-v4-pro
 or 
kimi-k2.6
 
(
DeepSeek-AI 2026
; 
Moonshot AI 2026
)
. Agent-safety benchmarks use such models as attacked agents 
(
Debenedetti et al. 2024
; 
Andriushchenko et al. 2025
)
, and the driver never takes part in a security decision. A 
run
 is an execution that reached its framework’s normal exit, finished or not.

Defenses compared.
 We compare source scanners,Cisco Skill Scanner 2.1.0 
(
Cisco AI Defense 2026
)
 and NVIDIA SkillSpector 2.11.2 
(
NVIDIA 2026
)
, which we call Cisco and SkillSpector. Each runs as its full cascade. A package that the model-free static stage admits goes on to the tool’s model stage, which DeepSeek drives and which sees the task and the grant. A scanner decides once, at admission, and an incomplete assessment withholds the package. The runtime defenses share one frozen gate. 
No gate
 forwards every request. The 
allow-list
 is derived from the per-endpoint egress policy of AgentBound 
(
Bühler et al. 2026
)
, which no task narrows. It is the ticket 
 of Section 
3
, compiled from the host grant alone: the gate forwards any send to an owned receiver while the run stays within the host budget 
, without knowing which receiver the task uses or what it must deliver. It shares the gate and account of 
RuntimeTickets
, so the two differ only in the per-task ticket. 
SkillGuard
, the closest defense built for Agent Skills, judges each tool call through the hooks of Claude Code 
(
Pan et al. 2026
)
, so it runs on that panel. Other runtime monitors judge the tool call or the finished trajectory, so a script’s own send reaches them as the command that launched it (Appendix 
C
).

Metrics.
 A defense can fail in two ways. It can 
overlook
 an attack by letting it through, or 
overkill
 a benign Skill by blocking its legitimate work. We call a request an 
injected send
 when it goes to the host that the injection names or carries a planted canary. An attack run 
gets through
 when the defense forwards an injected send, and the 
overlook rate
 is the share of attack runs that get through, the malicious Skills let through, which earlier work calls the attack success rate. An attack run is 
attempted
 when the agent issues an injected send that the gate decides, whether or not the gate forwards it, and Table 
3
 leads with the share of attempted attacks that got through. A scanner overlooks a malicious Skill by admitting it.

The 
overkill rate
 is the share of benign runs that a defense blocks, the benign Skills blocked. A benign run is blocked when the gate refuses a format-valid send to the task’s recipient and forwards none. A scanner blocks a benign Skill by withholding it. The share of 
benign Skills not blocked
 is 100% minus the overkill rate. The 
delivery rate
 is the share of benign runs that deliver the sanctioned output. For RQ3 we count the accounts whose re-decoding reproduces the recorded verdicts, and the tampered accounts that the decoder still marks 
Supported
. We sum counts over the panels and compute rates from the sums (Appendices 
D.1
 and 
D.4
).

6 
Conclusion

RuntimeTickets
 replaces a one-time verdict on a Skill package with a per-task check of every effect. A model proposes the requirements, the host grant bounds them, and a model-free gate enforces them at the egress boundary of unmodified frameworks. The run leaves an account from which a third party can re-derive every decision and every refusal without trusting a model. No attempted attack got through under 
RuntimeTickets
, no benign run was blocked and every account re-derived exactly. The scanners erred on both sides, and the allow-list and SkillGuard forwarded sends that reused the task’s recipient.

Ethics Statement

The adversarial cases are released malicious Skills that run on unmodified agent frameworks. Every send by a Skill or agent ends at a receiver we own, so no data reaches a third party. Only the model requests of the drivers and the scanners reach their providers, and no real credential or private datum is used. We report unmeasured outcomes as unknown rather than as evidence. No human-participant result is reported. The work is defensive: it measures whether a runtime protocol stops the harmful effects of malicious Skills while keeping benign Skills usable.

What we add.
 Both twins of a pair run the same trusted task. The task opens with the corpus’s own prompt for the carrier Skill, so that the agent has a reason to load the Skill. For the 12 MalSkillBench pairs we wrote a benign request from the Skill’s own documentation instead. A.3 
Mock Environment and Host Grant

Why a mock environment.
 Running released malicious Skills against real services would send real data to real third parties. We therefore run every Skill on a real, unmodified agent framework that a real language model drives, and we point every outbound connection at receivers that we own. The Skill, the agent and the framework behave as they would in deployment, and only the destination is simulated. No data reaches a third party.

Receivers and the host grant.
 The host grant is a fixed set of owned receivers that covers every receiver a task needs. We froze it with the case file before calibration, and we never recomputed it from the selected subset. Two granted receivers stand in for the two external destinations that the released Skill-Inject injections name most often. The egress proxy maps each such destination to its stand-in before the gate sees it, and it records the literal destination beside it. For a pair whose injection names a stand-in, a fixed order over case identifiers, set before any run, decides the task’s recipient. It is either that same destination, so that the injected send reuses the task’s recipient, or another granted receiver. An injection that names any other destination is aimed outside the grant. The stand-ins model the hardest case for a deployment-wide allow-list: an attacker who names an endpoint that the deployment legitimately uses. We never revised a receiver assignment after a run.

A.4 
Calibration

Calibration decides which pairs Experiment B runs. It executed only attack twins and only without a gate, and it ran each of the 60 pairs 2 times on Hermes Agent with the DeepSeek driver. The other panels inherit its selection. A pair is kept if at least one calibration run attempted the injected action, meaning that it connected to the injection’s declared destination or sent an object that contains a canary. A generic connection outside the grant, such as a package fetch, does not count. We froze the selection before the first 
RuntimeTickets
 run. It reads no gated defense and no benign twin, so it cannot favor 
RuntimeTickets
 over the allow-list, which face the same selected pairs.

B.5 
The Decoder and Its Three Verdicts

The decoder gives the user a verdict for every obligation and a reproducible reason for every decision. It authenticates each record with its issuer’s key and re-runs the frozen gate of Eq. (
4

A 
Violated

Supported

Unknown

Unknown

B.6 
Design Questions

The mechanism alone answers five design questions (DQ), which we keep apart from the experimental questions RQ1 to RQ3.

DQ1: Can a steered generator widen what a Skill may do?
 No. Approval compiles every proposal so that it only tightens the grant, and by Proposition 1 a ticket allows at most what the host grant allows. In this study every proposal, for attack and benign twins alike, was the narrowest ticket that the delivery contract permits: the task recipient’s grant and the three obligations. No Skill text loosened a ticket.

DQ2: Can injected text influence a gate decision?
 No. Injected text can change the proposal, which DQ1 bounds, and it can change which requests the agent makes. It cannot change the rule that decides them. After the freeze, the gate reads only each request’s effect facts, the validation facts and the frozen ticket.

DQ3: Does protection depend on the injected destination being new?
 Not on the recipient alone. An address check passes an injected send that reuses the task’s recipient 
, but 
 and 
 still check its object and amount. The check applies to every send that crosses the egress boundary.

DQ4: Can a third party trust a verdict without trusting a model?
 Yes, given the keys. The decoder of Eq. (
2
) is a deterministic function of the authenticated account. Anyone with the ticket, the records and the keys re-derives every decision and verdict, and a record altered without the keys fails authentication.

B.7 
Compatibility with Other Agents, Hubs and Providers

RuntimeTickets
 asks three things of the system it protects. The ticket generator must be able to read the Skill’s 
SKILL.md
. The agent must run in a container or on a host whose only route out passes the egress proxy. The issuer keys must stay outside that container. It asks for nothing else: no hook in the agent’s tool layer, no patch to the framework and no access to the agent’s transcript. The gate reads only each request’s effect facts (Section 
3
), and the decoder reads only the ticket, the records and the keys.

This is why the design carries over. Claude Code, Codex, OpenClaw and Hermes Agent all load Skills in the same open format, a folder with a 
SKILL.md
 file and optional scripts and references 
(
Agent Skills open standard 2026
)
, and registries such as ClawHub and Skills.sh distribute packages in that format. The ticket comes from the package and the task, so it does not depend on which hub supplied the package. The gate acts on network traffic, so it does not depend on which agent made the request or which provider’s model drives the agent. Only the ticket generator calls a model, and any provider can serve it. We evaluated OpenClaw and Hermes Agent with two driver models, and Claude Code in a supplementary panel (Appendix 
D.6
).

D.3 
Experiment B: Runs and Outcomes

Enforcement point.
 Apart from the model channel, the egress proxy is the agent container’s only network route, so the gate decides every connection before the proxy forwards it, including a connection that a helper script opens. Both frameworks’ install directories are identical before and after test runs, so running a Skill does not alter the framework. A send inside the grant reaches the owned receiver of its destination. Any other send reaches a capture-only sink that is never a task’s recipient. The proxy observes each connection: the validator and the canary check can read a plaintext body but not an HTTPS body. No send by a Skill or agent leaves the lab, and we change no part of a Skill to make a destination reachable.

Outcomes.
 An injected send gets through when the proxy forwards a connection to the injection’s declared destination, or forwards a send whose visible body carries a canary. For an HTTPS send the gate decides at connection time from the requested host, so the injected send gets through when the connection is forwarded, whether or not its encrypted body is read. An attack run is attempted when the gate decided at least one such send, forwarded or refused. Every defense runs under the lab’s per-run connection cap, and a send that the cap stops before any decision is neither attempted nor got through. A run delivers when the task’s sanctioned effect arrives and passes the host validator. A benign run is blocked when the gate refuses a format-valid send to the task’s recipient and forwards no format-valid send to it. We read this from the gate’s record by the same rule for every defense, so a run counts as blocked even when it also let another send through.

Runs.
 An execution is a run when its unmodified framework reached its own normal exit, whether or not the agent attempted the injected action or finished the task. Without a gate every decided send is forwarded, so every attempted attack got through there, and the overlook rate without a gate is the share of attack runs in which the agent attempted the injected send at all. Each pair, twin and defense counts one run, the first in attempt order. An execution that does not reach a normal exit is retried within a fixed budget, and the decision to retry depends only on whether an execution reached its exit, never on what it sent. Four framework-driver panels supply the runs.

Delivery rate.
 Across all runs, the delivery rate was 71.1% under 
RuntimeTickets
, 67.1% without a gate and 76.7% under the allow-list, so 
RuntimeTickets
 delivered at about the rate of running without a gate. On benign runs alone it was 68.4% under 
RuntimeTickets
 and 66.7% without a gate. Under the allow-list, the host budget refused a format-valid delivery in 2 benign runs before any had been forwarded, and neither run delivered. These are the benign runs that the allow-list blocked.
