Abstract

Existing Graphical User Interface (GUI) benchmarks predominantly rely on precise and stateless user instructions. In everyday usage, however, instructions are often 
vague and history-dependent
: users omit the exact details of their past operations because they no longer remember them, leaving the agent to recover the missing context from long and noisy interaction histories. To bridge this evaluation gap, we introduce 
MemU-Bench
, a mobile benchmark of 
118 vague tasks
 grounded in 29 long-horizon user trajectories, where agents must distill raw interaction streams into memory and retrieve the missing context on demand, with task outcomes verified against serialized application databases. Alongside Success Rate, we incorporate Interaction Efficiency (IE) and Success weighted by Path Length (SPL) to expose agents that succeed by exhaustively searching across different applications rather than by 
genuinely recalling
 the history. Evaluations show that without user history, state-of-the-art systems struggle under such ambiguity: the best-performing Gemini-3.1-Pro achieves an SPL of only 16.4%, and end-to-end GUI agents fall below 5%. To address this, we further propose 
AppMem
, a training-free framework that distills user history into a 
structured, app-centric
 memory bank, tracks interrupted intents across application switches, and selectively retrieves relevant memories via target-app inference. AppMem raises the SPL of GPT-5.5 from 15.7% to 66.9% (
+51.2%
), outperforms a naive summary baseline by 9.3%, and delivers consistent gains across evaluated backbones.

Graphical User Interface (GUI) agents built on Multimodal Large Language Models 
(
Wang et al. 2024b
; 
Bai et al. 2025b
; 
Bai et al. 2025a
)
 are rapidly evolving into general-purpose digital assistants that translate natural language instructions into executable action sequences on real devices 
(
Tang et al. 2025
; 
Hu et al. 2025a
; 
Cheng et al. 2024
; 
Lin et al. 2025
; 
Qin et al. 2025
; 
Lu et al. 2026a
; 
Lu et al. 2025
; 
Tang et al. 2026a
)
.

Existing benchmarks almost exclusively evaluate GUI agents under precise, self-contained instructions 
(
Rawles et al. 2023
; 
Rawles et al. 2025
; 
Xie et al. 2024
)
. Everyday usage rarely looks like this. Since users seldom remember the exact details of their past interactions, they tend to issue 
vague, history-dependent
 commands such as “modify the meeting time”, which cannot be resolved unless the agent knows which meeting was created, when, and in which application (Figure 
1
). Unlike preference-driven personalization, the missing context here consists of 
objective operational evidence
: facts that were fully observable in past interactions but are now buried in hundreds of steps of routine phone usage. Completing such tasks therefore demands more than a capable executor. The agent must 
continuously distill its user’s interaction stream into memory
 and 
retrieve the right piece of it on demand
.

Faithfully measuring this ability imposes three requirements on benchmark design. First, real interaction histories are 
long and noisy
: the few decisive state changes are scattered among hundreds of visually redundant screenshots, so the benchmark must 
expose agents to raw histories
 rather than pre-cleaned summaries. Second, real users 
multitask
: a single intent is often interrupted, resumed later, and interleaved with unrelated activities in other applications, so the trajectories must 
preserve such fragmented intents
. Third, task success alone is 
not evidence of memory
: an agent can complete a vague task by exhaustively searching through applications at execution time, so the evaluation must 
distinguish genuine recall from brute-force exploration
.

We introduce MemU-Bench, a mobile benchmark that instantiates these requirements (Table 
1
). It comprises 
118 vague tasks
 grounded in 
29 long-horizon user trajectories
 that cover more than 30 applications, with 100 to 800 steps per trajectory. Tasks are stratified by history length into 71 Level-1 and 47 Level-2 tasks to assess memory scalability. Each task follows a three-phase protocol: the agent first builds a memory bank from the raw history, then retrieves key information for the vague instruction, and finally executes the task online. Outcomes are 
verified programmatically against serialized application databases
, complemented by an LLM judge for open-ended text. Besides Success Rate (SR), we incorporate Interaction Efficiency (IE) and Success weighted by Path Length (SPL) 
(
Anderson et al. 2018
)
, which penalize agents that reach the goal by 
wandering across applications
 instead of recalling the relevant context.

Evaluations on MemU-Bench expose a consistent weakness of current systems. Without access to user history, the best-performing model, Gemini-3.1-Pro, attains an SPL of only 16.4%, and end-to-end GUI agents remain below 5%. Their trajectories degenerate into aimless exploration across applications, which inflates interaction cost even when the task eventually succeeds. 
Long-term memory is thus not an optional extension but a prerequisite
 for handling vague instructions in realistic settings.

Guided by these observations, we propose AppMem, a training-free framework that equips GUI agents with long-term user memory. During daily usage, AppMem summarizes the interaction stream through a sliding window into 
app-centric memory entries
 and tracks the status of each intent, so that events interrupted by application switching are merged into coherent threads instead of fragmented records. Upon receiving a vague instruction, it infers the target applications, retrieves only their associated entries, and iterates until the collected information is sufficient for execution. On MemU-Bench, AppMem raises the SPL of GPT-5.5 from 15.7% to 66.9% (
+51.2%
), outperforming the naive summary baseline by 9.3%, and generalizes across backbones (e.g., improving the SR of MAI-UI-8B by 16.9%).

We summarize our main contributions below:

•

We present 
MemU-Bench
, a mobile benchmark of 118 vague tasks over 29 long-horizon trajectories that evaluates whether GUI agents can recover missing context from 
long, noisy, and interleaved
 user histories, with database-level verification and efficiency-aware metrics.

•

We systematically evaluate closed-source models, open-source models, and end-to-end GUI agents on MemU-Bench, showing that all of them fail under vague instructions without history and that naive summarization helps general models far more than GUI-specialized agents.

•

We develop 
AppMem
, a training-free memory framework combining 
intent-continuation
 memory generation with 
app-guided retrieval
, improving SPL by up to 51.2% and delivering consistent gains across evaluated models.

Related Work

2.1 
GUI Agents and Memory Mechanisms

GUI agents have evolved from script-based automation 
(
Zhou et al. 2024
; 
Wang et al. 2024a
)
 to Multimodal Large Language Model agents that execute closed-loop actions directly from pixels 
(
Qin et al. 2025
; 
Wang et al. 2025
)
. These agents, however, assume 
stateless and precise
 instructions 
(
Zhou et al. 2025
; 
Xu et al. 2026
; 
Xu et al. 2025a
; 
Yan et al. 2025
; 
Gu et al. 2025
; 
Cao et al. 2026
)
: each task is an isolated episode, and prior user activity is discarded. Memory offers a natural remedy and has been studied extensively for LLM agents, which consolidate long dialogue or task histories into retrievable structures 
(
Chhikara et al. 2025
; 
Zhang et al. 2026b
; 
Hu et al. 2025b
; 
Zhang et al. 2025
; 
Tang et al. 2026b
)
. These systems, however, operate on 
textual
 interactions whose semantics are explicit, whereas GUI histories are streams of screenshots and low-level actions with intents fragmented across applications. Existing GUI memory modules sidestep this difficulty by memorizing only transient states within a single task execution 
(
Lu et al. 2026b
; 
Jin et al. 2026
; 
Zhang et al. 2026a
; 
Zeng et al. 2026
; 
Wang et al. 2026
)
. AppMem instead maintains a persistent, app-centric memory across user’s interaction stream.

2.2 
Mobile GUI Benchmarks

Existing mobile GUI benchmarks follow a task-oriented paradigm: they measure execution success under precise instructions and treat each task as independent of the user’s prior history 
(
Rawles et al. 2023
; 
Li et al. 2024
; 
Xu et al. 2025b
; 
Rawles et al. 2025
)
. Benchmarks that move beyond this setting relax it only partially. MemGUI-Bench confines memory to a single task 
(
Liu et al. 2026
)
, and MobileWorld resolves ambiguity by querying the user in real time rather than by consulting long-term history 
(
Kong et al. 2025
)
. Personalization benchmarks do exploit history, but only to extract 
static preferences
 such as habits and tastes 
(
Lyu et al. 2026
; 
Chen et al. 2026
; 
Nie et al. 2026
; 
Chai et al. 2026
)
. None of them evaluates whether an agent can distill 
objective, task-critical facts
 from long, noisy, and unstructured daily usage streams. MemU-Bench fills this gap: its vague tasks can only be completed by recovering missing context from raw long-horizon histories, and outcomes are verified against serialized application databases (Table 
1
).

3.2 
Dataset Construction

Trajectory Sketches and Task Syntheses.

We first manually design vague tasks together with intent-level trajectory sketches. Each sketch outlines a sequence of high-level user intents for a long-horizon session (e.g., ordering food, then casual gaming) without prescribing specific applications or operation paths. The information required to resolve the final vague task is embedded into the interaction process itself. Operators are therefore free to vary applications and execution paths, which increases trajectory diversity.

Synchronous Trajectory Collection and Granular Logging.

Guided by the sketches, operators interact with an Android Virtual Device emulator to simulate daily phone usage. Rather than following deterministic paths, they introduce realistic noise such as accidental touches and redundant app switching. Sessions are fragmented across multi-hour spans with long inactive gaps, mirroring how people actually use their phones. A background script concurrently captures screenshots and atomic actions at 0.3-second intervals, preserving the complete raw interaction log.

Data Processing and State Serialization.

Consecutive identical screenshots are filtered out, yielding clean, action-interleaved logs. Upon trajectory completion, the emulator state is frozen and serialized: we record the system time and pull the runtime databases (e.g., SQLite files) of all involved applications. Restoring these snapshots before testing reproduces the exact device state left by the operator, so every effect of the historical interaction (a sent message, a modified event) exists in the backend and can be verified against ground-truth records.

The resulting benchmark contains 29 user trajectories and 118 tasks: 71 Level-1 (L1) tasks with shorter histories (fewer than 400 screenshots) and 47 Level-2 (L2) tasks embedded in longer flows (more than 700 screenshots). As shown in Figure 
3
, tasks span 5 major application categories, and trajectories cover more than 30 applications, with up to 179 application switches within a single trajectory. Further statistics are provided in the supplementary materials.

3.3 
Evaluation Strategies

Task success is verified by a cascade of checks, applied in order of decreasing determinism.

Rule-based Verification.

For tasks with deterministic objectives and no open-ended text, we extract the raw backend records from the application’s database and verify success conditions programmatically.

LLM-as-Judge.

For tasks involving open-ended text (e.g., messages), deterministic fields such as timestamps are rule-checked, and only the free-text fields are forwarded to an LLM judge for semantic comparison. For a minority of tasks where the database is inaccessible, a VLM evaluates the outcome from screenshots and actions. Restricting the judge to short text fields keeps context small and decisions consistent.

5.2 
Main Results

Necessity of User History Memorization.

Without user history, evaluated system fails under vague instructions (Table 
2
). GPT-5.5 attains an average SPL of only 15.7%, Qwen3.5-397B-A17B reaches 9.7%, and the strongest end-to-end agent falls to 3.4%. Vague instructions therefore cannot be treated as isolated inputs: resolving them requires long-term memory of the user’s history.

Effectiveness and Generalizability of AppMem.

AppMem improves evaluated backbones, whereas Summary only helps models with strong long-context ability (Table 
2
). With Summary, general models gain substantially (Qwen3.5-397B-A17B: 35.6% SR), but end-to-end GUI agents barely move (+1.7% SR): their GUI-specific tuning appears to compromise long-text processing as the history accumulates. AppMem sidesteps this bottleneck by structuring the history into a compact memory bank, raising Qwen3.5-397B-A17B to 52.5% SR and MAI-UI-8B by +16.9% SR.

Efficiency.

The efficiency metric reveals an even sharper contrast. Vanilla agents that do succeed still wander (e.g., IE of 0.65 for Gemini-3.1-Pro), and naive summarization can further lower efficiency on weaker backbones, as their limited long-context capability hinders extracting and retaining key information from lengthy historical trajectories (e.g., GUI-Owl-1.5-8B’s IE drops from 0.67 to 0.30). AppMem instead improves IE across models, up to 0.91 for GPT-5.5, showing that its compact, targeted memory lets agents act with near-human step economy rather than by brute-force exploration.

5.3 
Ablation Study

We ablate the components of AppMem on Qwen3.5-397B-A17B (Table 
3
). Removing Ongoing Intent Continuation (OIC) lowers SPL by 4.7% and nearly doubles the memory size (from 8.8K to 15.3K tokens), confirming that stitching interrupted intents produces memory that is both more complete and more compact. For retrieval, without Information Filtering (IF), raw app entries inflate the agent context from 0.10K to 2.89K tokens and SPL drops to 41.8%. Application Inference (AI) mainly governs cost, cutting retrieval overhead by 66% (from 17.8K to 6.1K tokens) at nearly the same SPL, while Sufficiency Verification (SV) recovers context scattered across applications at only minor overhead.

Error analysis.

Retrieval, not navigation, is the dominant bottleneck. We manually classify the Summary baseline’s outcomes along two axes: whether the retrieved information contains the missing context, and whether online execution succeeds (Figure

6 
Conclusion

We introduced MemU-Bench, a mobile GUI benchmark of vague, history-dependent instructions on which state-of-the-art GUI agents fail without user history. Our training-free framework AppMem consolidates histories into app-centric memory entries and retrieves them through app-guided inference, improving both success rate and efficiency across evaluated backbones. More broadly, our results position memory, not execution ability, as the primary bottleneck for long-horizon GUI agents and a key direction for future work.

Appendix G 
Case Analysis of AppMem

Coverage of Memorized Information.

Figure 
10
 (left) presents a case where the Summary method fails while our approach succeeds. The summary method fails due to information missing; its summary omits critical details like the exact order and arrival times, forcing the GUI agent into an error-prone search within the app where it retrieves an incorrect time. In contrast, our method meticulously records these temporal details. By directly retrieving the correct schedule from its history without risky on-screen searches, our agent accurately infers the target time and successfully completes the task, demonstrating the vital role of structured memory in resolving real-world ambiguities.

Granularity of Memorized Information.

Figure 
10
 (right) illustrates the efficiency gap between the two methods. The Summary baseline manages to complete the task but exhibits low efficiency due to its coarse-grained information retention; while it registers the person’s name, it fails to record the specific phone number. Consequently, the GUI agent is forced to execute redundant steps to relocate the business card on the phone to get the number before placing the call. In contrast, our method maintains fine-grained information, directly storing the exact phone number in memory. This allows the GUI agent to bypass the time-consuming searching steps and make the call immediately, demonstrating that fine-grained memory retention significantly enhances task execution efficiency.

Appendix H 
Evaluation Reliability

Our evaluation protocol consists of two stages: rule-based verification and LLM-as-Judge. Specifically, 44.9% of the tasks are evaluated solely through rule-based verification, while the remaining 55.1% require the LLM-as-Judge to assess open-ended textual outputs. For all LLM-based evaluations, the temperature is set to 0 to ensure deterministic inference and reproducible decisions.

To validate the accuracy of the evaluation protocol, we manually verify the success status of all tasks that require the LLM-as-Judge for Qwen3.5-397B-A17B, and compare the results with those produced by our evaluation protocol. Compared with manual evaluation, our evaluation protocol achieves an accuracy of over 95%, demonstrating that it provides an accurate and reliable assessment of task success.

Prompt Template for Ongoing Intent Continuation

You are analyzing a user’s operation log on an Android device. 

Your goal is to integrate a NEW Memory Event into an EXISTING Memory Event. You must merge them into a single, cohesive narrative that reflects the entire journey within
this app session.

1. Integration Rules (Seamless Narrative):

- **Identify Continuity**: If the new event continues the previous task (e.g., previously searched for shoes, now filtering by size), merge them into a single flow.

- **Capture Pivots**: If the user abandoned the previous task for something new (e.g., stopped looking at shoes and started searching for electronics), reflect this
transition (e.g., ’After looking at shoes, the user shifted focus to…’).

- **Deduplication**: If the new event repeats information from the existing event, do not list it twice; prioritize the most recent state or progress.

2. Details Merging Rule:

- Combine the ’Existing Details’ with ’New Details’ into one comprehensive list.

- **Conflict Resolution**: If a value has changed (e.g., quantity updated from 1 to 2), keep the most recent data point.

- Ensure all hard data (prices, codes, specs) from both sets are preserved unless they are outdated.

3. State Re-evaluation:

- **finished**: The combined journey has now reached a terminal point (e.g., payment completed, final result obtained).

- **ongoing**: The task remains incomplete, or the user is still in the middle of a new workflow.

- **Note**: Even if the previous state was ’ongoing’, it can now become ’finished’ if the new event completes the task.
