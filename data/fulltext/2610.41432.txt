Abstract

Computer-use agents increasingly tackle tasks ranging from everyday desktop activities to long-horizon professional workflows.
Yet interfaces centered on screenshots and mouse-and-keyboard actions can impose a human-interaction prior, requiring repeated screen interpretation while leaving the computer’s semantic and programmatic capabilities underexposed.
We argue for exposing these capabilities and letting models choose and combine them.
We introduce Hybrid Computer Use (HCU), a unified interface for general agents that combines three complementary channels: programmatic interaction through code and command-line tools, semantic interaction through accessibility (AX), and visual interaction through graphical user interfaces (GUI).
Our HCU supports efficient AX interaction and guards against stale-state actions during channel switching. A supplementary HCU skill guides agents in selecting and coordinating channels to use the unified interface effectively.
Our designed AX tools return compact observations, execute actions in batches, and report their effects as AX diffs, so the model needs fewer round trips.
On OSWorld 2.0, HCU achieves the highest Partial and Binary scores among the compared systems.
Analyzing agent trajectories, we find that all evaluated models improve with HCU yet allocate work across the channels differently and consistently outperform compared baselines in terms of both efficiency and task success, highlighting the value of unified computer-use interfaces that allow flexible channel selection and combination.

Introduction

AI agents are increasingly able to carry out user requests by operating software applications on computers directly. Computer-use research has expanded from everyday desktop tasks in OSWorld 1.0 
[
1
]
 to long-horizon workflows and specialized professional software in OSWorld 2.0 
[
2
]
.
As tasks become more involved, agents must sustain progress across many operations, making interaction efficiency important alongside task performance.

Most existing computer-use interfaces mirror how humans operate software: inspect the screen, locate a UI control, and use the mouse or keyboard. While this approach offers broad coverage with human-like perception and action, it also imposes a strong human-interaction prior on the action space of a frontier Large Language Model (LLM), overlooking more efficient channels for interacting directly with the system.
An agent with existing computer-use interface may spend substantial effort precisely locating a field by screen coordinates even when the application exposes its identity and value through accessibility data, or manipulate data through repeated click-and-drag actions when code could process it directly.

Modern computer systems offer a wide range of interaction tools that fall into three complementary channels: visual interaction through GUIs, structured semantic access through accessibility APIs, and direct programmatic access through code and command-line tools such as Bash.
Accessibility (AX), originally developed for assistive technologies and now also used for automation, exposes application UI controls, their properties, and supported operations 
[
3
, 
4
]
. Code and command-line tools provide direct access to files, data, and software, while GUI interaction supplies visual evidence and control where structured access is insufficient.

Prior work 
[
5
, 
6
]
 combines programmatic and visual interaction but makes limited use of the semantic channel provided by AX.
UFO2 combines UI Automation with GUI and application-API execution 
[
7
]
, while Tactile exposes semantic actions alongside OCR and visual fallbacks 
[
8
]
.
CUA Driver, an open-source computer-use interface, supports all three channels but favors AX-based interaction in the background to preserve the user’s active desktop 
[
9
]
.
We build on these efforts to organize reference-addressed AX actions, in-call wait steps, and post-action feedback for efficient, sustained interaction, while exposing all three channels within a general agent for model-directed selection and combination.

We introduce Hybrid Computer Use (HCU), a unified interface for general agents that combines three complementary channels: programmatic, semantic, and visual interaction (Figure 
1
).
HCU adds AX and GUI tools to the agent’s own programmatic tools via the Model Context Protocol (MCP), with cross-channel action guards to maintain a consistent view of the current desktop state and an HCU skill to guide the model in selecting and combining the exposed channels.
Our designed AX channel lets the model read a compact AX view, act on several targets in one call, and see the resulting changes without a separate observation.
Because all three channels act on the same desktop, an action in one can invalidate the evidence held by another; action guards therefore re-check targets and layouts against live state before each input. A supplementary HCU skill explains how to use these tools and when each channel is most effective, helping the model follow the execution and feedback contracts and reduce invocation errors.

We evaluate HCU on OSWorld 2.0 and OSWorld 1.0, and further evaluate it on WeaveBench, MacAgentBench, and Windows Agent Arena in Appendix 
A
. On OSWorld 2.0, HCU achieves the highest Partial and Binary scores among compared systems, advancing the performance–efficiency frontier (Figure 
1
, right).
With 
GPT-6 Astra
, it reaches 72.37% Partial, outperforming CUA Driver by 3.55 points. With Claude Opus 5, it improves Partial by 3.75 points and Binary by 3.76 points over the model’s official leaderboard result, reaching 35.19% Binary at 20% lower Cost. On OSWorld 1.0, HCU outperforms CUA Driver across four other backbone models, each in its own harness, averaging 6.48 more points in Score, 17% fewer Steps, and 30% lower Cost, and reaches 70.13% Score with GPT-5.4 while transferring these performance and efficiency gains to WeaveBench, MacAgentBench, and Windows Agent Arena at roughly half the Cost.
Component ablations and tool-call analyses reveal distinct channel preferences across models, yet gains consistently concentrate on tasks that use HCU’s desktop tools. Within tasks, we observe that channels often play complementary roles, with screenshots supporting observation and AX enabling execution. The skill helps agents use the interface more reliably, reducing the proportion of AX and GUI calls rejected for malformed arguments from 17.37% to 1.36%.

Our contributions are threefold:

1.

We introduce HCU, a unified interface for general agents that combines programmatic, semantic, and visual interaction. HCU pairs model-directed channel selection with cross-channel action guards and AX tools for compact observation, batched actions with wait steps, and post-action feedback.

2.

We show that HCU achieves the highest Partial and Binary scores on OSWorld 2.0 and advances the performance–efficiency frontier, and that it consistently improves both task performance and efficiency over CUA Driver across diverse backbone models, agent harnesses, and desktop platforms.

3.

We analyze the ablations and the cross-model comparison at the level of tool calls, showing that models given the same channels divide them differently, and we distill design lessons for future computer-use interfaces.

From GUI-based to hybrid computer use.

[

[
5

6

[
14

[
15

. Like ALE and WeaveBench, HCU extends a general agent without model training and leaves the division of work among channels to the model, while adding a semantic channel beside the programmatic and visual ones.

Semantic interaction with computers.

Interfaces that expose semantic information differ in how they identify targets and execute actions. The original OSWorld 1.0 set-of-marks baseline uses AX information to identify targets, but maps element identifiers to coordinates for GUI input

Hybrid Computer Use Interface

HCU combines three interaction channels in one agent’s task context: programmatic, semantic, and visual (Figure 
2
, top). The programmatic channel uses the agent’s own code, shell, and file tools. HCU adds the semantic and visual channels through two desktop tools exposed via the Model Context Protocol (MCP) 
[
23
]
: the AX channel reads application accessibility trees and executes reference-addressed actions, while the GUI channel takes screenshots and sends mouse and keyboard input (Appendix Table 
13
). All three channels act on the same computer. Action guards check AX targets and GUI layouts against live state before input. A supplementary skill explains how to use the interface.

The agent uses HCU within its existing observation–action loop. Given the task and available observations, the model chooses a channel to inspect state or act; the selected tool executes the request and returns its result to the same context, from which the model decides whether to continue, inspect further, or change channels. Observation and execution need not use the same channel: a screenshot can supply visual context for a subsequent AX action. Channel selection remains model-directed. HCU adds no planner, subagents, or loop of its own, so the same interface attaches to different agent harnesses (Appendix 
E.5
).

The following subsections describe the AX channel’s observation, execution, and feedback design (Section 
3.1
), the action guards that support switching between channels (Section 
3.2
), and the skill that explains how to use the interface (Section 
3.3
).

Accessibility for Computer Control

AX exposes a structured representation that applications or UI frameworks supply for assistive technologies: a tree of elements with roles, names, values, states, and supported operations. It lets an agent identify and operate controls without locating every target in pixels, but using it to control a computer presents three challenges.

1.

Coverage depends on what applications expose.
 Applications choose which properties and operations to expose through AX. Custom-drawn content may have no accessible elements, accessible objects need not map one-to-one to widgets, and virtualized items may be absent until rendered 
[
3
, 
24
]
. AX therefore provides incomplete coverage of visible content and available interactions. CUA Driver addresses this by returning the tree and a screenshot together by default, so the model can use pixels when AX omits or misrepresents a target 
[
25
]
. HCU retains the acquired AX records, marks unavailable information, and lets the model request a screenshot when semantic evidence is insufficient.

2.

Changing targets.
 Controls can share names, move, disappear, or be recreated; AT-SPI explicitly marks defunct objects 
[
26
]
. A label or tree position therefore cannot establish identity across actions. CUA Driver instructs the agent to refresh element indices before acting and rejects ambiguous window targets 
[
27
, 
28
]
. HCU binds target references independently of the displayed view and resolves them against live elements before each action, including actions within a batch.

3.

Verifying action effects.
 AT-SPI reports invocation, which does not establish that the intended state change occurred 
[
29
]
. CUA Driver verifies caller-defined postconditions through a separate operation 
[
27
]
. HCU lets the agent compose actions and optional AX wait steps in one batch, such as selecting a checkbox and waiting for its checked state before continuing, without a separate verification call.

CUA Driver prioritizes best-effort background input to preserve the user’s active desktop, with foreground input available on request 
[
9
]
. In contrast, HCU prioritizes completing the requested action, using native AX operations or focused input as needed. Its efficiency-oriented design also gives the agent more control over how work is composed: compact views reduce observation size, while batched actions, optional wait steps, and AX diffs let the agent combine execution, verification, and state feedback within a single call.

Composable Semantic Interaction

These properties motivate an AX interface that lets the agent compose actions while HCU validates targets, runs requested wait steps, and returns evidence for continuation. Figure 
2
 (bottom) illustrates this interaction: a compact AX view supplies target references, a batch combines actions with optional wait steps, and post-action feedback supports the next decision.

Compact AX views and target references.

HCU separates the AX records it retains from the compact AX view shown to the model. It removes structural wrappers and condenses repeated content in the view while retaining the acquired records for target identification and state comparison. Target references are bound to elements before this compression, so shortening the view does not change which element a reference identifies. The retained records also support AX diffs after an action, while 
find
 and scoped observations let the model retrieve targets omitted from the compact AX view. Appendix 
E.2
 gives same-capture examples and measures the reduction in tokens.

Batched actions and wait steps.

HCU lets the agent compose known actions and optional AX wait steps in a single call. The 
act
 mode executes the steps in order within one application window, checking each target with the AX target guard before input (Section 
3.2
). A wait step sends no input and holds until an expected state appears, such as a checkbox becoming checked or a dialog opening, before later steps run; placed last, it verifies the final state. This combines batching, also used for GUI interaction 
[
6
]
, with state verification akin to Playwright assertions 
[
30
]
. If an action fails, a wait times out, or window continuity is lost, HCU stops the batch and reports the stopping point and execution evidence. This lets the agent decide how to continue without blindly repeating earlier actions.

Post-action feedback.

HCU returns per-target effect summaries and an AX diff by default after an action call, showing changed values, window changes, and target references relative to the last eligible observation delivered to the model. The agent can instead request a screenshot or execution evidence only, according to what it needs for its next decision. Returning this feedback with the action lets the agent continue without a separate observation when the information suffices (traces and samples in Appendix Figure 
16
 and  
E.3
).

HCU reports only what the available evidence supports, so the agent is not led to treat input delivery as a verified effect. Like CUA Driver 
[
27
]
, it distinguishes known non-delivery from an unknown effect after possible input. The agent uses this distinction and the returned continuation instructions to decide whether to retry, inspect state, or stop.

The model observes the desktop through discrete tool outputs rather than a continuous view of its state. After an action, it may not know which earlier observations remain valid, especially when combining channels. An AX action may open a dialog over coordinates from an earlier screenshot, or a GUI action may replace a control addressed by an AX reference. Reusing that evidence can send input to an unintended target without the model noticing. HCU therefore leaves channel choice to the model while using action guards to check the targets and layouts on which its actions depend immediately before input (Algorithm 
1
).

The AX target guard resolves each target reference immediately before execution and checks the element’s identity and action-specific requirements. If the target is missing, ambiguous, or replaced, or an action-specific requirement is not met, HCU rejects the action without sending input. It does not redirect the action to a similarly named element. The GUI layout guard checks whether the layout underlying the model’s chosen coordinates still matches the last screenshot. Before coordinate input, it compares the current desktop bounds, visible top-level windows, stacking order, active window, and target-point window layout with those associated with that screenshot. If the layout has changed, HCU blocks the affected input and returns a fresh screenshot so the model can choose new coordinates.

Both guards inspect current state regardless of which channel changed it, including earlier actions in the same channel. Detected mismatches lead to explicit rejection before input, allowing the model to revise its next action (Appendix 
E.4
; recorded rejection in Figure 
18
).

Skill for Effective Interface Use

HCU provides a supplementary skill that explains how to choose and compose the interface’s capabilities. We distilled its instructions from recurring mistakes in development trajectories, including malformed arguments and misused target references, following the trajectory-informed refinement of usage instructions in SWE-agent 
[
15
]
. The skill addresses three aspects of interaction: (1) 
Channel capabilities.
 The skill explains what programmatic, semantic, and visual interaction can provide, including their observation scope and limitations, so the model can decide which channels to use and combine for the task. (2) 
Efficient interaction.
 It explains how to use target references, batch known actions with wait steps, and continue from returned feedback, requesting additional observations only when needed. (3) 
Verification and recovery.
 It distinguishes input delivery, local UI changes, and task outcomes; explains how to verify saved or applied results; and describes how to recover from stale targets, invocation errors, or insufficient evidence.

The skill makes these instructions concrete through rules for common invocation and recovery mistakes, while the tool schemas define argument shapes. It contains no task-specific solutions; Appendix 
F.2
 presents its text. The skill ablation in Section 
4.3
 shows reduced invocation errors and improved interaction efficiency; Appendix 
B.1
 describes instruction integration.

Models and comparisons.

Each model always runs in the same harness: GPT-6 Astra and GPT-5.4 in Codex, Claude Opus 5 and Claude Opus 5.5 in Claude Code, Gemini 3.8 Flash in Gemini CLI, and Grok 4.7 in Grok Build. Metrics and budgets.

We report Partial (mean task score) and Binary (full-credit rate) on OSWorld 2.0 and Score on OSWorld 1.0, along with per-task resource use. The main experiment uses a 500-step limit and the ablations a 100-step limit. We average results across runs within each configuration. Appendix

HCU beats the baseline on every measure.

HCU scores 3.29 points higher than the baseline while using 29.80% fewer Steps, 56.85% fewer input tokens, 29.85% less Time, and 55.36% lower Cost. Every component contributes to this efficiency: each one cuts Steps by 11–15%, so the full interface needs the fewest Steps of all configurations.

Skill effects.

AX contributes most.

AX is the channel HCU adds to GUI-based computer use: it exposes the applications’ control tree as named, reference-addressed targets and returns observed state changes after action batches. Added to the harness’s programmatic tools and the GUI channel, it raises Score by 2.79 points and cuts Steps by 14.08%, input tokens by 10.44%, Time by 12.58%, and Cost by 10.64%, the largest gain of any component in Score, input, Time, and Cost. The GUI channel complements AX primarily through interaction efficiency: removing GUI leaves Score within run-to-run variation while increasing Steps by 12.45% (Appendix 
C.1
). AX thus drives the Score gain and most of the resource savings, while GUI saves Steps when visual context or pixel input is required; Section 
4.4
 shows how the two divide observation and execution.

Execution-centered AX design supports efficient interaction.

HCU’s AX channel integrates guarded execution, optional wait steps, and post-action state in one call (Section 
3.1.1
). With only AX and programmatic tools, HCU w/o GUI exceeds CUA Driver by 3.79 points in Score while using 21.06% fewer Steps, 58.33% fewer input tokens, 29.63% less Time, and 56.70% lower Cost. CUA Driver also offers element-addressed actions and separates delivery from effect 
[
27
]
, but leaves verification and renewed observation to separate operations. Both interfaces can sequence actions programmatically; HCU builds verification and feedback into the AX call itself.

The skill improves calling reliability and interaction efficiency.

With the skill (Section 
3.3
), the share of AX and GUI calls rejected for malformed arguments falls from 17.37% to 1.36%, and the share of task-runs that repeat such rejections on the same tool while varying the arguments falls from 44.69% to 0.37% (Figure 
3
). Feedback selection also changes: 87% of AX action calls omit the 
observe
 field, selecting the default AX diff, compared with 0.2% without the skill. GUI input actions decrease from 4.96 to 1.97 per task. These behavioral changes accompany a 14.55% reduction in Steps and a 1.59-point gain in Score (Appendix 
B.1
).

). By leaving channel choice to the model, HCU allows observation and execution to use different channels, enabling the model to draw on their complementary capabilities as the task requires.

(a) Contributions to the HCU–CUA Driver Score difference, grouped by HCU AX/GUI use. (b) Tasks using each interface’s desktop tools; labels show HCU–CUA Driver differences in points.

Score gains concentrate on tasks with AX or GUI use.

Across all four models, nearly all of the overall Score gain over CUA Driver comes from tasks where HCU makes at least one AX or GUI call (Figure 
5
a).
We group tasks by whether HCU makes at least one such call in each run and average the groups’ weighted contributions across runs. The group without these calls contributes only 
 to +0.1 points to the overall Score difference (Appendix 
D.2
).

Overall Steps mask differences in interaction efficiency.

On tasks where both configurations invoke their desktop tools (AX or GUI), HCU uses 19–40% fewer Steps across the four models. HCU also invokes desktop tools on more tasks than CUA Driver (Figure 
5
b). For Claude, tasks where only HCU invokes desktop tools gain 7.6 points in Score, accompanied by 53% more Steps. This group’s weighted increase largely offsets the savings where both configurations use desktop tools, explaining Claude’s nearly unchanged overall Steps despite its higher Score. Appendix 
D.2
 provides the complete decomposition.

Discussion and Conclusion

HCU exposes programmatic, semantic, and visual interaction to a general agent and leaves their selection and combination to the model. It achieves the highest Partial and Binary scores on OSWorld 2.0, and consistently outperforms CUA Driver in both task performance and efficiency across diverse backbone models, agent harnesses, and desktop platforms.
These results suggest that interfaces built on how people operate software, inspecting the screen and using the mouse and keyboard, cost agents both performance and efficiency. Given AX, three of the four models send most of their desktop calls through it (Section 
4.4
). This echoes the bitter lesson 
[
35
]
: a strong human-like interface that fixes how the computer is used may limit what increasingly capable models can do with it. The capabilities HCU exposes already exist on standard desktops and require no model retraining.

Finally, the AX channel exposes element states that code can read and act on. This makes it possible to treat the desktop as a programmable environment and to bring desktop work into code execution and programmatic tool calling 
[
36
]
. HCU’s batched actions with wait steps (Section 
3.1.1
) provide a direct substrate for this composition. We hope this work encourages interfaces that fully leverage what computers already offer to release model capabilities on computer use.

Task sets.

The main experiment uses the OSWorld 2.0 full set (108 tasks; 0808 release). GPT-6 Astra and GPT-5.4 run in Codex; Claude Opus 5 and Claude Opus 5.5 run in Claude Code; Gemini 3.8 Flash runs in Gemini CLI; and Grok 4.7 runs in Grok Build. AX Observation and Target Identity

References, scope, and projection.

The service maintains short references for applications (
aN
), logical top-level windows (
wN
), and elements (
rN
). Element actions resolve these references against live state rather than tree line numbers or display labels; 
activate
 and 
close
 also accept a window-title substring resolved to a unique 
wN
 before input. Window scope defaults to the full window including chrome, whereas 
content
 scope selects the primary content surface and 
root
 narrows an observation to a subtree.

From the provider’s acquired records (roles, names, values, states, actions, geometry, and relations), HCU builds a typed internal tree, binds target references, and projects the compact AX view shown to the model. Projection removes empty structural wrappers, merges adjacent unreferenced text leaves, deduplicates relation-backed labels, preserves context needed to disambiguate same-name controls, displays table cell values alongside names, and summarizes repetitive sibling runs under a structural budget. Because references are bound before projection, omitting a subtree from the displayed view does not invalidate its acquired records, which remain searchable via 
find
.

Server Instructions and Tool Definitions

Server instructions

 
 
 

Two tools for the running desktop. AX reads and operates application windows through accessibility: it lists windows, returns controls as rN refs, acts on them, and waits with wait steps. GUI takes full-desktop screenshots and sends pixel input. Use AX for named controls, values, menus, dialogs, windows, and keys. Use GUI for pixels, canvases, dragging, and controls that AX does not expose; after one targeted AX find misses a visible control, use GUI for it. Send all desktop input (window activation, keys, text, mouse) through these tools, not shell input utilities or scripted accessibility calls: the tools check the target window before input and report what changed, and outside input makes their refs and diffs stale. After GUI input, read AX again before reusing refs.

AX
 tool description

 
 
 

Accessibility for application windows. Modes: apps lists confirmed windows (wN, title, app, active) and reports incomplete inventories; missing windows then remain unknown. observe returns the window tree with rN refs. find returns matching rN. act runs ordered steps, checks them before input, stops at the first failed step, and reports each target’s change, windows opened/closed/focused, and a diff. Copy rN/wN exactly; stale refs fail. keypress/type without ref go to the focused window. select marks ref, its text substring, or ref..to_ref (paragraphs, cells) and reports the selection read back. activate/close take a title substring or wN. A wait step sends no input and fails the batch on timeout: window (title, any app), query (as find), ref with value/state/text, or text; gone inverts. settle needs no prediction: it waits until the UI changes after the step before it and stops changing; it fails only if nothing changed. After a window wait, keys go to that window, after settle to the focused one. Skip waits the report answers. Errors return code and hint. Examples:

 
 
 

{"mode":"act","actions":[{"type":"click","ref":"r12"},{"type":"wait","window":"Export"},{"type":"type","text":"q3.csv"},{"type":"keypress","keys":["ENTER"]}]}

{"mode":"find","window_ref":"w2","query":{"role":"button","name_contains":"Save"}}

GUI
 tool description

 
 
 

Full-desktop screenshot and pixel input. {"actions":[{"type":"screenshot"}]} alone observes; {"type":"zoom","region":[x0,y0,x1,y1]} alone enlarges a frame region to read small text and icons. Any other batch is checked before input and returns one final screenshot. x/y are pixels of the latest full-desktop image (screen width x height) from GUI or AX full/screenshot, which return the same frame. type/keypress go to the current focus, so click the field first. Batch the actions planned from one screenshot; end the batch after an action that may open, close, or move a window, and plan the rest from the returned image. GUI cannot address windows; AX activates and closes them by title. wait is one second with no observation, at most 20 s per bat
