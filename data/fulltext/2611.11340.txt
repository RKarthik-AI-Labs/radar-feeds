Abstract

Security tools raise findings across cloud environments, and AI agents now investigate and prioritize them. A finding is still resolved by people: it has to reach the people responsible for fixing it and accountable for the resource it concerns. Ownership is the organizational context that decides who that is. Where recorded, it is declared by hand in configuration management databases or owner tags and goes stale unless kept current; accounts are shared, and automation creates much of the infrastructure. The knowledge sits in work records, code history, audit logs and identity directories, encoded in each organization’s own conventions. Recovering it poses four challenges: the signal is scattered across sources, none of them authoritative; the conventions that carry it differ between organizations; reaching an owner takes multi-hop links; and those related to a resource differ in the strength of their relation. We define ownership as a set of entities, people or teams, each related to the resource by one of five patterns ordered by strength. We present a reference architecture for agentic ownership attribution that derives ownership from these records instead of declaring it: it profiles an organization offline into tested signal procedures and an ownership playbook, then attributes each resource with a coordinator agent and parallel investigators, with confidence computed by rules. On 100 resources of 50 Amazon Web Services (AWS) resource types in one organization, we pool the architecture’s candidates with those of an unprimed general-purpose agent and verify every evidence piece against the records. The architecture reaches 92.1% weighted recall and 86.6% weighted precision, against 54.8% and 77.4%, at 0.55 times the agent’s cost per unit of coverage. The difference lies in people who build and change resources without an explicit owner, found through work records and code history.

Ownership Definition

An owner of a resource is an entity, a person or a team, whose relation to the resource is supported by the organization’s records. The definition makes ownership a set rather than a single value, and it makes the relation, not the entity, the unit that has to be justified. Each member of the set carries a 
relation pattern
, which names the nature of the entity’s tie to the resource (Table 
1
).

Explicit owner and direct work form the strongest level. An explicit owner is named on the resource itself, in its name or recorded metadata, or is shown by a recorded action to have created it. Direct work covers the people who build, change, run or answer for the resource, or for the thing it exists for. The weaker patterns, in decreasing strength, are indirect work, the same activities on the resource’s surroundings where the link is inferred; relies on it, use of or dependence on the resource; and peripheral, a weak link such as a mention.

The boundary between direct and indirect work separates the people who answer for a resource from those who answer for its surroundings. Work is direct when the thing the person or team works on is the reason the resource exists. Maintaining the database service that a compute node exists to run is direct work on the node; administering the cloud account in which the node runs is indirect work. A resource that exists for an environment, such as the environment’s own certificate, is direct work for the person who runs that environment.

Five rules govern the patterns.

1.

Patterns name behaviors, not data sources, so a relation recorded in a source the definition did not anticipate still has a place.

2.

A pattern is read from the evidence that establishes the relation; assigning it requires no further investigation.

3.

Creating, changing, maintaining, operating and being responsible for a resource are one level; the builder is not ranked above the operator.

4.

Breadth of scope matters only relative to the other people related to the same resource. When nobody does direct work on a resource, indirect work is the strongest relation it has, and it is graded as such.

5.

Non-human identities are not owners. A deployment pipeline, an infrastructure-as-code role or a service principal points to the run it performed. The run points to a branch, commit or ticket, and the people on those records are the candidates.

The order encodes a judgment about allocation. The strongest level holds the entities a finding on the resource should reach: those named as answering for it and those who build and run it. Missing one of them is a larger error than missing a person who once mentioned the resource. The evaluation turns this order into weights.

[

4 
Reference Architecture

The architecture treats ownership attribution as an investigation over the organization’s records, carried out by an agent whose action space is a set of tools (Figure 
1
). Three principles shape it. First, judgment and guarantees are separated: language models decide where to look and how to read what they find, while deterministic code tests their proposals, decides whether a conclusion is admitted and combines evidence scores into a confidence. Second, organization-specific knowledge is compiled once: what can be learned about an organization’s conventions is turned offline into tools, so that per-resource reasoning is spent only on what cannot be pre-computed. Third, every claim is grounded: each owner in the output carries the records that relate them to the resource, with facts kept apart from inferences.

Enterprise security brain.

All agents and tools read the 
enterprise security brain
, the cross-platform security data layer of our prior work 
[
1
, 
2
, 
3
]
. It integrates each platform’s records in one read-only store, relates them in an asset graph before any question arrives, so that an identity-provider account already points to the cloud role it assumes, and holds organizational context beside the graph 
[
3
]
. Relational context of this kind raised agent answer correctness by about 34% relative in our cross-vendor benchmark 
[
23

[
2

.

Offline: compiling the organization into tools.

Profiling agents learn how one organization records ownership (C2) and compile it into two tools. The first is a set of 
signal procedures
, executable lookups from a resource to a person or team. Each procedure starts as a hypothesis that an agent proposes about the organization, for example that the value of a 
stack
 tag names a repository whose pull-request authors work on the resource, and becomes a tool only after code, running it on the organization’s own data, finds that it reaches people, generalizes beyond the values it was built from and behaves as declared. A procedure is defined over keys and joins, not over particular values, so one procedure serves every resource that carries the key. A hypothesis the data refutes is revised or dismissed. Accepted procedures are executed for every resource ahead of time as 
pre-computed signals
, so the deterministic part of attribution is paid once, and each carries a reliability prior derived from its known weaknesses. Signals differ in what they assert: a 
direct
 signal names one person, as an owner tag holding 
alice@example.com
 does; a 
supportive
 signal points toward owners, as a stack tag does; and 
chain segments
 compose into multi-hop chains (C3). The second tool is the 
ownership playbook
, the declarative complement to the procedures: written guidance on which tags are reliable, how logins map to people and which leads are dead ends, which turns profiling from a one-off analysis into context read for every resource.

Online: an agentic search for evidence.

Inference for one resource is a search over the evidence the brain can produce, run by one investigation agent in a loop of reasoning, tool calls and observation 
[
68
]
. The agent first infers what the resource belongs to, its 
context
: a load balancer named 
payments-api-prod-alb
 belongs to the payments API in production, so 
payments
 and 
api
 become search terms for tickets and code (C1, C3). It reads the compiled tools and uses live read-only queries for what they do not cover, such as tickets that mention the payments API. Open leads are pursued in parallel by investigator sub-agents that run the same loop, in the orchestrator–worker pattern of recent multi-agent systems 
[
69
, 
70
]
. Two behaviors keep the search broad rather than greedy: every role holder on a matching record (assignee, reporter, author, reviewer) is registered, not only its leader, and automation is read as delegation, so a pipeline that created the resource is followed to the commit or ticket behind it (rule 
5
). Every 
evidence piece
 separates what the records show from what is inferred from them: 
the person is the assignee of a ticket that names the stack
 is a fact, 
the person therefore works on the resource
 an inference.

Invariants and confidence.

Acceptance is governed by invariants enforced in code rather than by the model’s judgment. A conclusion is admitted only if it rests on evidence the agent has observed, every failed lookup was retried or explained, and every person it mentions is attributed or ruled out; otherwise it is returned for another round. Confidence is never stated by the model: investigators score each evidence piece, and fixed rules combine these scores and the procedures’ priors into a confidence per entity. The output is the ownership set 
: each entity, its evidence and its confidence, from which the relation pattern is read (rule 
2
).

Evaluation

We evaluate the ownership set the architecture returns for each resource against the set returned by an unprimed baseline agent. No ground-truth ownership map exists, so both are scored against a pool of their verified candidates. Three criteria apply, each with its metrics: 
coverage
, whether a system finds the entities the records relate to the resource, measured by weighted recall and by success rate, the share of resources with a verified owner; 
correctness
, whether what it proposes is supported by the records, measured by weighted precision and rejected candidates; and 
cost
, measured by cost per resource and per unit of weighted recall.

5.1 
Experiment design

Resources.

Resources are drawn from a real-life production environment of one organization. Of the 244 AWS resource types we classified, 105 are 
ownable
, meaning a person or team would create, deploy, manage or answer for their instances; inherited records, platform metadata, findings and platform-wide configuration are excluded. Each resource is assigned a 
signal level
 by how many of its applicable signal procedures hold a value for it: rich (at least half), thin (fewer), or metadata only and opaque (none). A stratified selection draws 100 resources of 50 ownable types, two per type, spread over signal levels, avoiding near-duplicate copies of one stack and confirming that each still exists.

Data sources.

Six sources hold the records that relate people to resources, and they play four roles. 
Resource state
: the AWS resource inventory describes each resource by its name, tags, configuration and relations to other resources (59,309 resources of ownable types in one account and 18 regions); these descriptors are where an investigation starts. 
Activity
: the AWS audit log records who created, changed or tagged a resource, over the last 90 days. 
Work
: Jira records who reported, planned and carried out work through ticket roles and text (16,590 tickets in 18 projects over two and a half years), and GitHub records who wrote and reviewed code through pull requests and commits (10,005 pull requests in 44 repositories over two years). 
Identity
: Okta, the identity provider, holds the canonical directory of people with their employment status (73 people), and the AWS identity center (75 people and the roles they act through) and GitHub membership (51 members) link cloud principals and code-hosting logins to these people. Both systems access them read-only.

Systems.

The architecture reads the enterprise security brain, into which the sources are ingested and related ahead of time. Its investigation and procedure-construction agents run on Claude Sonnet 5.5 
[
20
]

[

[

[
19

It receives no ownership definition, strategy or knowledge of the organization, so it measures what an unprimed agent achieves with direct access, as in our earlier comparison with coding agents 
[
2

Pool construction.

The candidates of both systems for a resource are merged into one pool by canonical email, following the pooling practice of information retrieval 
[
17

73
]
. Because the baseline agent contributes candidates the architecture did not find, the pool does not rest on the system under test alone. Recall against a pool is relative recall 
[

[

Evaluation pipeline.

The pool passes four stages (Figure 
2
). People who have left the organization or are unknown to its directories are rejected. A judge on Claude Sonnet 5.5 then verifies each evidence piece on its own: it sees the cited records retrieved afresh, may consult the integrated copy and the live platforms alike, and decomposes the claim, as in atomic-fact evaluation 
[
76
, 
77
]

verified

rejected
 when the reverse holds, and 
insufficient
 otherwise. Each verified person is then assigned a relation pattern by Claude Sonnet 4.6, with three votes combined per person, and weighted. The judge matched all 9 calibration cases in each of 2 runs and all 23 hand-labeled borderline candidates; no agreement study with human annotators was made. Results

Table

Coverage.

The architecture reaches 92.1% weighted recall against 54.8% for the baseline agent (93.3% against 68.5% macro-averaged), and proposes a verified owner for 99 of 100 resources against 89. Of the 230 verified person–resource pairs in the pool, 98 were found by both systems, 100 by the architecture only and 32 by the baseline agent only.

By relation
 (Table 
3
). Both systems find the person named on the resource, 47 and 48 of 49 explicit owners. The difference is direct work: the architecture finds 131 of 141 people against 53, and 117 of 123 against 47 on resources without an explicit owner.

By source
 (Table 
4
). The added owners are found beyond the resource. Code history backs 46% of the architecture’s verified owners against 2%, person directories 68% against 17%, and tickets 65% against 52%. The baseline agent reads GitHub through its CLI, yet none of its verified owners rests on its own lookups there; its few code-history links are pull requests named in Jira tickets.

Owners found only by the baseline agent.
 Of these 32 people, 20 are weaker links (indirect work, relies on it or peripheral), and the most common routes to them are free-text ticket search (14 people) and neighboring resources (11). The architecture reached 11 of the 32 during its investigation without proposing them and never reached the other 21.

By kind of resource

Weighted precision is 86.6% against 77.4% (89.5% against 81.3% macro-averaged). Few proposals of either system are rejected, 12 against 10, of which 8 each by the directory check, so the baseline agent’s lower weighted precision reflects fewer and weaker owners rather than more errors. The judge decided 250 of the 265 pooled candidates (94%).

6 
Discussion

Each challenge posed in the introduction maps to a result. 
Scattered signal (C1):
 the owners the architecture adds are found in systems other than the resource itself; code history backs 46% of its verified owners against 2%, and person directories 68% against 17%. 
Organization-specific conventions (C2):
 recall does not fall where no signal procedure applies (94% against 90% on rich resources); whether profiling transfers to a second organization is untested. 
Multi-hop links (C3):
 of the 88 direct workers that only the architecture found, 68 rest on evidence citing the resource’s own stack, service or component descriptors, which context inference turns into search terms, and 42 on a ticket together with its pull request or commit. 
Relation strength (C4):
 under the pattern weights, the advantage lies in direct work (131 of 141 people against 53), while few proposals of either system are rejected (12 and 10).

The gap is largest where ownership is not written down. On resources with an explicit owner, both systems find the named person; on resources without one, the architecture finds 117 of 123 direct workers against 47. Derived ownership adds most where declared ownership is absent.

The evaluation has limits that its design bounds. It covers one organization, with one cloud provider and 100 resources. The architecture learns an organization’s ownership conventions by profiling its data rather than from rules written for it, but how well profiling works on other organizations is untested. No source is a CMDB, so derived ownership is not compared with declared ownership. Recall is measured against the owners that the two systems found together, so owners neither system found are not counted and true recall may be lower than reported; the comparison between the two systems remains reliable, as it does for pooled evaluation in information retrieval 
[
75
]
.

Future work extends the evaluation along three axes: more organizations, to test how well profiling learns conventions it has not seen; more cloud providers, Microsoft Azure and Google Cloud, whose resource models and audit records differ from those of AWS; and more data sources, including CMDBs, service catalogs, on-call schedules and monitoring systems such as Datadog, so that derived ownership can be compared with declared ownership and drawn from a wider set of records. Each axis tests the same claim: that ownership can be derived from the records an organization already keeps.

7 
Conclusion

Ownership is the organizational context that decides which people a security finding reaches: those responsible for fixing it and accountable for the resource it concerns. Declared ownership ages, and in the evaluated organization most ownership was implicit, held in work records, code history, audit logs and identity directories rather than on the resource.

This paper made two contributions. First, it defined ownership as a set of entities, people and teams, typed by five relation patterns ordered by strength. Second, it presented a reference architecture for agentic ownership attribution: offline, it profiles an organization into tested signal procedures and an ownership playbook; online, an investigation agent with parallel investigators attributes each resource, while code checks its conclusions and computes its confidence.

On 100 resources of 50 AWS types, the architecture reaches 92.1% weighted recall and 86.6% weighted precision against a pool shared with an unprimed agent, which reaches 54.8% and 77.4%, and it delivers coverage at 0.55 times that agent’s cost. The evidence places the difference in people who build and change resources without an explicit owner, found through work records and code history. Whether it holds in other organizations is the next question.
