Abstract.

Modifying an existing application is difficult when it does not provide programmatic access for that change. Recent advances in computer-use agents (CUAs) enable richer understanding and operation of existing interfaces, while generative UI (GenUI) makes it practical to generate new ones. We examine how these advances expand software modification through a design space of what can be changed and a framework for how modifications can be implemented. We then introduce Interface Quilt, a system that combines CUAs and GenUI to generate interface patches, which are new interfaces displayed over an existing application to modify its presentation, interaction, and capabilities. Through demonstrations across a variety of applications, we show that interface patches support a range of modifications without source code, APIs, or accessibility data.

Keywords: 
Generative user interface, Malleable user interface, User interface re-authoring, Pixel-based reverse engineering

1. 
Introduction

Software today is typically designed to be able to satisfy most users’ needs most of the time, but it rarely fits how all users work all of the time. One may want to hide or surface controls based on their tasks, replace one interaction technique with another, or make use of the powerful capabilities locked away by professional software without learning the complex interface. This vision of software reshaped for individual users has long been a pursuit of HCI research  
(
Kay and Goldberg, 1977
; 
Stallman, 1981
; 
MacLean et al., 1990
; 
Henderson and Kyng, 2020
)
. Prior approaches to achieving this were through customization and tailoring 
(
MacLean et al., 1990
; 
Page et al., 1996
; 
Myers, 1998
; 
Cook, 2007
)
, adaptive and adaptable interfaces 
(
Findlater and McGrenere, 2004
; 
Gajos and Weld, 2004
; 
Todi et al., 2021
)
, end-user programming and development 
(
Nardi, 1993
; 
Lieberman et al., 2006
; 
Ko et al., 2011
)
, meta-design 
(
Fischer et al., 2004
)
, and malleable software 
(
Klokmose et al., 2015
; 
Rädle et al., 2017
; 
Borowski et al., 2022
; 
Litt et al., 2025
; 
Beaudouin-Lafon, 2023
; 
Mackay and Beaudouin-Lafon, 2025
)
.
In this work, we use 
modification
 broadly to describe any departure from the software shipped, including changes to what a user perceives (presentation), how they interact (interaction), or what they can do with it (capability). The term follows communities such as game modders and hardware hackers, who alter, extend and retrofit artifacts beyond what their maker anticipated 
(
Thiel and Lyle, 2019
; 
Paul and Mandryk, 2026
; 
Tanenbaum et al., 2013
; 
Hurst and Tobias, 2011
; 
Ramakers et al., 2016
)
, as well as designers who repurpose existing applications and devices as prototyping tools for new behaviours 
(
Hartmann et al., 2006
; 
Ledo et al., 2019
)
.

Prior modification efforts largely rely on adapting the software through programmatic access pathways provided by the developer, such as scripts, plugins, APIs, or source code. These pathways can limit the extent to which a modification can be applied. Modifying an application without developer support can be more difficult, but it is not impossible. Prior HCI systems have used pathways not designed for modification, ranging from websites’ DOM 
(
Bolin et al., 2005
; 
Nichols et al., 2008
; 
Zhang and Guo, 2018
)
, operating system (OS) window APIs 
(
Stuerzlinger et al., 2006
; 
Tan et al., 2004
)
, accessibility APIs 
(
Zhang et al., 2017
; 
Li et al., 2017
; 
Lu et al., 2024c
)
, to runtime code injection to specific application frameworks 
(
Eagan et al., 2011
; 
Meng et al., 2014
)
. However, not all applications provide these pathways, and there have been various systems that use the graphical user interface (GUI) directly and pixel-based techniques to modify applications. Systems such as 
Prefab
 add advanced interaction techniques by identifying common UI elements  
(
Dixon and Fogarty, 2010
; 
Dixon et al., 2011
; 
Dixon, 2013
)
 and Sikuli provided interface scripting through icons 
(
Yeh et al., 2009
)
. These systems demonstrate that interface structure and actions can be recovered without source-code access. However, these techniques require custom-authored models and templates targeting specific UI toolkits, limiting their applicability.

Recent advances in UI understanding 
(
Zhang et al., 2021
; 
Wu et al., 2021
; 
Lu et al., 2024a
; 
You et al., 2024
)
 and computer-use agents (CUAs) 
(
Agashe et al., 2024
; 
Zhang et al., 2025b
; 
Qin et al., 2025
)
 make it possible to recover richer structure and semantics from rendered interfaces and act through them. At the same time, advances in generative UI (GenUI) 
(
Wu et al., 2024
; 
Chen et al., 2025b
; 
Leviathan et al., 2026
; 
Cao et al., 2025
; 
Chen et al., 2025a
)
 make it increasingly practical to generate new interactive surfaces. To understand how these capabilities expand software modification, we first develop a design space that characterizes what a modification can change, including changes enabled by CUAs and GenUI to how users perceive and interact with existing software. We then develop a framework for how modifications are achieved, characterizing both the access a modifying system has to an application and the level of synchronization between the modifying system and the target application. Together, the design space and framework help us examine what is possible when modifying applications that reveal rendered pixel data alone.

We introduce Interface Quilt, a system for modifying existing applications by generating and running 
interface patches
: generated interfaces that change an application’s presentation, interaction, or capabilities while leaving the application itself unchanged. At build time, Interface Quilt provides a harness for computer-use agents to explore the target application, inspect its interface state, and discover the controls needed for a modification. Interface Quilt records this recovered information and makes it available to coding agents, which use it to generate interface patches. An interface patch modifies presentation by covering or augmenting parts of the existing interface, interaction by mediating application output and user input, and capabilities through new logic packaged in the interface patch. At runtime, Interface Quilt orchestrates interface patches, continuously synchronizing application state to interface patches and translating the user’s interactions with the interface patches back into actions on the application. This synchronization makes the interface patch and underlying application behave as a single integrated interface from the user’s perspective, creating the experience of modified software without programmatic access to the target application.

We examine Interface Quilt’s capabilities and boundaries through demonstrations, following Ledo et al. 
(
Ledo et al., 2018
)
. Across PowerPoint, Affinity, Fusion, Slack, and Overleaf, we use Interface Quilt to create interface patches inspired by classical interaction techniques such as put-that-there 
(
Bolt, 1980
)
, marking menus 
(
Kurtenbach and Buxton, 1991
)
, Toolglass 
(
Bier et al., 1993
)
, Side Views 
(
Terry and Mynatt, 2002
)
, Patina 
(
Matejka et al., 2013
)
, Ephemeral Adaptation 
(
Findlater et al., 2009
)
, SILK 
(
Landay, 1996
)
, and ToolTrack 
(
Masson et al., 2022
)
. We build interface patches that recompose task-centric interfaces, restructure interface controls, add in-situ support, and enhance software capabilities. Together, these demonstrations showed that when the states and controls needed by a modification are visible through the interface, Interface Quilt can restructure presentation, introduce new interaction techniques, and add capabilities while managing interface patches synchronized with the target application.

This paper makes three contributions. (1) we present Interface Quilt, a system architecture for generating and running interface patches that modify existing applications through their rendered interfaces; (2) through demonstrations across applications, we show how interface patches can modify presentation, interaction, and capabilities; and (3) we present a design space of software modification, examining changes described in prior systems, and a software framework that separate what a modification changes from how it is achieved, and situate GenUI and CUAs both as forms of modification and as mechanisms for realizing modifications.

2. 
Related Work

This work builds on prior work in end-user customization and software modification and is enabled by the emerging capabilities of generative AI models.

2.1. 
Vision of Modifiable Software

Software that can be reshaped by the individual user has long been a goal of investigation by researchers in interactive computing. In Personal Dynamic Media, Kay and Goldberg described Smalltalk that enables any user to mould by their own needs 
(
Kay and Goldberg, 1977
)
. Stallman built the Emacs text editor with extensibility principles that “users are not limited by the decisions made by the implementers” 
(
Stallman, 1981
)
. MacLean et al. argued that no single design can suit all users and situations, thus systems should be tailorable for users’ modification 
(
MacLean et al., 1990
)
. Henderson and Kyng similarly described continuous design in use, where software systems prepare for user modification in response to users’ idiosyncratic use and the complexity of the world not anticipated by designers 
(
Henderson and Kyng, 2020
)
.

HCI research demonstrates benefits in modifying applications to better fit the user’s tasks, computing environments and abilities. For tasks, users customize a feature-rich word processor to reach frequently used functions faster 
(
Page et al., 1996
)
, and users are provided with a personal interface with only the functions they chose, navigated and learned better with more sense of control 
(
McGrenere et al., 2002
)
. For computing environment change, interfaces regenerated for a device’s input and output constraints, such as screen sizes, allow applications in service of context that the designers did not build for 
(
Thevenin and Coutaz, 1999
; 
Calvary et al., 2003
; 
Gajos and Weld, 2004
; 
Nichols and Lau, 2008
)
. For abilities, the modifying offers the most significant benefit, as interfaces generated from a model of a user’s motor abilities allow them to complete tasks that they could not perform in the original interface 
(
Gajos et al., 2007
; 
Gajos et al., 2008
; 
Wobbrock et al., 2011
; 
Zhang et al., 2017
; 
Zhang et al., 2021
)
.

To support modifications, HCI uses more specific terms across different dimensions. 
Adaptive
 interfaces are changed by the system, whereas 
adaptable
 interfaces are changed by the user 
(
Findlater and McGrenere, 2004
)
. 
End-user programming
 and 
end-user development
 identify users who create computational behaviour without professional programming experiences 
(
Nardi, 1993
; 
Lieberman et al., 2006
; 
Ko et al., 2011
)
. Mørch’s customization, integration and extension dimensions distinguish how deeply a change reaches into the software 
(
Mørch, 1997
)
.

Other terms distinguish how modification is made. 
Customization
 and 
tailoring
 use mechanisms deliberately provided by the developer, such as preference dialog and scripting languages 
(
MacLean et al., 1990
; 
Page et al., 1996
; 
Myers, 1998
; 
Cook, 2007
)
. Plugin extension APIs are similarly developer-supplied contacts for modifications. 
Meta-design
 withholds the specific design at the time for users to complete during use 
(
Fischer et al., 2004
)
. 
Malleable software
 goes further and makes the data and code substrates available for change. Systems like 
Webstrates
 
(
Klokmose et al., 2015
)
, 
Codestrates
 
(
Rädle et al., 2017
)
, and 
Varv
 
(
Borowski et al., 2022
)
 treat applications and documents as the same modifiable material and interaction substrates decompose applications into substrates and instruments in service of modifications 
(
Litt et al., 2025
; 
Beaudouin-Lafon, 2023
; 
Mackay and Beaudouin-Lafon, 2025
)
. For our purpose, these concepts distinguish the routes to modification rather than the act of modification itself, and are all considered as modifications.

These modification pathways share an assumption that software developers prepare modification mechanisms from within the software, such as packaged options in customization, predefined paths in adaptive software, or software with malleability designed from the ground up. Without this support, modifications become much more difficult 
(
Borowski et al., 2022
)
. Our work focuses on providing Interface Quilt that sits over existing software to provide the user with the experience of modified software, even without providing mechanisms for modification.

2.2. 
Modifying Application Without Support Made for Modifications

It is possible to modify software without support or access built into the software. Prior work has introduced pathways from outside the application for modifications, such as through web code, accessibility APIs, language-specific hooks, and operating systems’ APIs.

Web applications are the most readily modified applications, as web pages are declarative documents in HTML and DOMs with client-side source code inspectable for a modifying system. For example, 
Chickenfoot
 creates automation and customization abilities for end-users by keyword matching the source code  
(
Bolin et al., 2005
)
. 
Highlight
 reauthors an existing website for mobile phone and omits pages not used during user demonstrations 
(
Nichols et al., 2008
)
. Other systems record and share web operation procedures, inject widgets, spreadsheets, and panels to web pages that were not designed to host them 
(
Leshed et al., 2008
; 
Toomim et al., 2009
; 
Litt and Jackson, 2020
; 
Zhang and Guo, 2018
; 
Kim et al., 2022
; 
Hao et al., 2026
; 
Lu et al., 2024b
)
. The access to client-side code, combined with the ability to examine function calls, provides deeper modifications. For example, 
d.mix
 enables flexible re-authoring and mashups of API-based web applications 
(
Hartmann et al., 2007
)
 and 
Genie
 reverse-engineers a web application’s commands to retarget them as speech, keyboard and command line interface 
(
Swearngin et al., 2017
)
.

However, many non-web applications on desktop and mobile lack direct source code access and rely on alternative pathways. Some application frameworks support mechanisms for runtime code-injection that systems can reverse-engineer for modification. For example, 
Scotty
 proposed a runtime toolkit overloading to change macOS Cocoa applications’ method implementations at runtime 
(
Eagan et al., 2011
)
, 
WADE
 uses Windows’ dynamic linking library to modify interface layout and behaviours 
(
Meng et al., 2014
)
, and earlier toolkit research taps into the operating system’s drawing pipelines to transform and extend interface widgets 
(
Edwards et al., 1997
; 
Olsen et al., 1999
)
. Some operating systems, such as Windows and Android, provide a windowing system with region names and input redirection, useful for basic layout reconfigurations. 
WinCuts
 use them to duplicate live regions of arbitrary windows 
(
Tan et al., 2004
)
, 
User Interface Facades
 to recombine and replace widgets of running applications 
(
Stuerzlinger et al., 2006
)
, and 
A-Mash
 extracts parts of unmodified Android applications into a single wrapper application 
(
Lee et al., 2022
)
. Specifically for input redirection, 
ICON
 reroutes device inputs with Windows APIs 
(
Dragicevic and Fekete, 2004a
)
 and 
HIDAgent
 simulate human-interface device controls through an external hardware 
(
Bigham, 2026
)
. The accessibility API offers UI element trees with markups designed for screen readers, but it also enables the “curb cut effect” for modification systems to structurally understand the interface. For example, 
Interaction Proxies
 use it to provide augmented metadata and interaction mediation for runtime accessibility repair on Android 
(
Zhang et al., 2017
)
. The API provides abilities to record user demonstration, input manipulation, and interface augmentation 
(
Li et al., 2017
; 
Li et al., 2019
; 
Lu et al., 2024c
; 
Huang et al., 2023
; 
Matejka et al., 2013
)
. Yet, it still relies on developers to provide proper support, which is not always guaranteed 
(
Zhang et al., 2017
; 
Chang et al., 2011
)
. Although these pathways allow access to modify some application behaviours, they are limited by the toolkits, platforms and developer support.

The most common denominator shared across GUI applications is the rendered pixels. As such, researchers investigated pixel-based reverse engineering techniques for modifying an application. 
Prefab
 identifies widget location and outline by template-matching the pixels of known widgets, then retrofits advanced interaction techniques onto unmodified applications 
(
Dixon and Fogarty, 2010
; 
Dixon et al., 2011
; 
Dixon et al., 2012
; 
Dixon, 2013
)
. Similarly, 
Sikuli
 used screenshots templates and synthetic inputs to automate desktop workflows 
(
Yeh et al., 2009
)
, and 
Waken
 recovers widgets and usage from tutorial videos 
(
Banovic et al., 2012
)
. However, pixel-based methods also introduce limitations and constraints to the modification. First, these methods lack state awareness of the applications. To mitigate this, 
Prefab
 reintroduce accessibility APIs to mitigate applications’ state and style  
(
Dixon et al., 2014a
; 
Dixon et al., 2014b
)
. Second, these methods rely on hand-crafted templates or fixed widget styles from a standard UI toolkit, limiting the general applicability.

Modifying an application without support, therefore, remains limited in the extent of supported applications and modifications. In Interface Quilt, we extend the pixel-based technique in 
Prefab
 
(
Dixon et al., 2014b
)
 and recontextualize the layered interface architecture in 
Interaction Proxies
 
(
Zhang et al., 2017
)
 with the latest development in generative UI for creating the modifications and computer use agents to explore existing software and bind modifications to activate them.

2.3. 
Emerging Capabilities: Generative UI and Computer Use Agents

Recent developments in generative UI (GenUI) and Computer Use Agents (CUAs), driven by large language models (LLMs) and visual language models (VLMs), lower the barriers to reproducing interfaces and actions. These capabilities create new opportunities for modifying existing applications, although GenUI and CUAs alone have largely been developed for different ends.

Prior to LLMs, user interface management systems and model-based methods have generated interfaces from domain models in order to design once and target any device 
(
Wiecha et al., 1990
; 
Vanderdonckt and Bodart, 1993
; 
Puerta, 1997
; 
Mori et al., 2004
; 
Limbourg et al., 2005
)
. 
Graceful Degradation
 investigates the transformation rules of interfaces while preserving continuity across platforms. Systems like 
Personal Universal Controller
 and 
Huddle
 generate a more usable interface for appliances 
(
Nichols et al., 2002
; 
Nichols et al., 2006
)
 and 
SUPPLE
 render an optimized interface based on device and user model 
(
Gajos and Weld, 2004
)
. Other work like 
Bespoke
 investigated synthesizing a custom UI from the command line 
(
Vaithilingam and Guo, 2019
)
.

The emerging wave of GenUI takes advantage of LLMs’ coding capabilities and focuses on producing usable interfaces from scratch 
(
Wu et al., 2024
; 
Chen et al., 2025b
; 
Leviathan et al., 2026
)
. GenUI can refer to both runtime generations and adaptations or design-time generations 
(
Chen et al., 2025a
)
. To constrain the generation process, systems like 
BISCUIT
 
(
Cheng et al., 2024
)
 and 
DynaVis
 
(
Vaithilingam et al., 2024
)
 scaffold widget generation with access to source code, 
SQUIRE
 
(
Leung et al., 2025
)
 and 
Athena
 
(
Beason et al., 2026
)
 reintroduce the intermediate models, 
Jelly
 
(
Cao et al., 2025
)
 created data models and UI specifications for gradual UI generation, 
Maru
 
(
Kim et al., 2026
)
 created information architecture to stabilize generation across iterations. Recent work on revibing HCI interactive systems with coding agents suggests coding agents are becoming increasingly successful at producing interfaces 
(
Adar et al., 2026
)
. However, these GenUIs are all built to code bases that the GenUI system owns, and it remains difficult to integrate GenUI into existing applications 
(
Cao et al., 2025
; 
Chen et al., 2025b
; 
Xu et al., 2026
)
. Systems that integrate into existing applications are done through APIs 
(
Liu and Sra, 2026
)
 or via the web 
(
Hao et al., 2026
)
.

UI understanding and CUAs have developed together. Development in screen recognition enabled systems to recover interface semantics 
(
Zhang et al., 2021
; 
Wang et al., 2021
)
, UI models 
(
Wu et al., 2021
)
, interface texts, layouts, and widgets 
(
Lu et al., 2024a
; 
You et al., 2024
; 
Akouche et al., 2026
)
 from screenshots alone. The understanding feeds in for computer use agents to operate applications on behalf of the users 
(
Agashe et al., 2024
; 
Zhang et al., 2025b
; 
Qin et al., 2025
)
. Some systems also fuse screenshots with accessibility API or DOM when available to improve performance 
(
Zhang et al., 2025b
; 
Zhang et al., 2025a
)
. To promote users’ awareness, control, and learnability when delegating tasks to CUA, researchers have explored adding pausing, checking, and handoff mechanisms 
(
Peng et al., 2025
; 
Mozannar et al., 2025
; 
Wu et al., 2026
; 
Chang et al., 2026
; 
Khurana et al., 2025
)
. To improve CUA performance both in accuracy and speed, researchers explored separating build time from runtime process, where a system explores the application once, then packages the recovered controls as a deterministic tool, such as model context protocol (MCPs), for another agent to call on at runtime 
(
Lu et al., 2025
; 
Zhong et al., 2026
; 
Wang et al., 2026
; 
Qiu et al., 2026
; 
Li et al., 2025
)
.

We combine the capabilities of GenUI and CUA in Interface Quilt to create a persistent interaction instrument 
(
Beaudouin-Lafon, 2000
)
 as interface patches bounded over an existing application. Interface Quilt uses CUAs to recover the controls over existing applications and uses coding agents and GenUIs to construct an interface layer for modification. We view these capabilities as emerging mechanisms in a broader space of software modification (
section 3
), enabling changes to how users perceive and interact with software that was not designed for modification.

2.4. 
Prior Design Spaces for Software Modification

Prior work has developed design spaces for specific forms of software modification. 
Interaction Proxies
 provided interaction re-mappings for runtime accessibility repairs 
(
Zhang et al., 2017
)
, and 
InteractOut
 extends the space to input manipulations for curbing phone overuse 
(
Lu et al., 2024c
)
. 
DOMSteer
 describes three operations for in-situ assistance manipulating websites: insert, mutate and recompose 
(
Hao et al., 2026
)
. Design spaces for adaptive interfaces similarly describe system-initiated changes to presentation 
(
Gajos et al., 2006
; 
Findlater and Gajos, 2009
)
. Zindulka et al. develops design space for touch-based LLM interactions by additive, subtractive, and transformative change to text 
(
Zindulka et al., 2025
)
. Min et al. characterize malleable overview-detail interfaces by content, composition and layout 
(
Min et al., 2025
; 
Min and Xia, 2025
)
, and create a design space of abstraction techniques covering unit of interest, granularity, representation, transformability, presentation and guidance 
(
Min et al., 2026
)
.

These design spaces are scoped to specific mechanisms, interface forms or domains. Our goal is to describe modifications across them by separating what changes for the user and how the change is achieved. The design space characterizes modifications along five dimensions of the user’s perception-action loop, including the element and structure of presentation, the modality and steps of interaction, and the capabilities. It further distinguishes reductive, replacement, and additive changes, adapting from the distinction of the modified target used by Zindulka et al. for text manipulation 
(
Zindulka et al., 2025
)
. The framework of modification mechanisms describes how a modification receives and returns states and actions with an application, extending Daniel et al.’s degrees of interoperability 
(
Daniel et al., 2007
)
. To our knowledge, our design space and framework are the first to view GenUI and CUAs as both forms of modification and pathways through which other modifications can be achieved.

3. 
Design Space and Framework

We provide a unified account of software modification by distinguishing 
what changes for the user
 from 
how that change is achieved
. We develop a design space that characterizes the effects of modification on the user’s experience of an existing application, and a complementary framework of modification mechanisms that characterizes how modifying systems gain access to the application and remain connected to its state and actions. We derive both by synthesizing the HCI systems reviewed in our related work and drawing on prior design spaces of customization, adaptation, and modification.

We define an 
existing application
 as an interactive application packaged for the end user with its interface and behaviour fixed by its developers, and refer to this shipped state as the 
baseline
. A 
modification
 is any departure from this baseline that changes what the user perceives, how they interact with the application, or what they can do with it. Using the baseline as a common reference point allows us to compare modifications independently of the mechanisms used to implement them.

3.1. 
Design Space of Software Modification

Figure 2. 
Design Space of Software Modification. 
Types of Modifications
 describes the area of user experience modified. 
Relationship to Baseline
 describes the way the modified experience relates to the unmodified software.

The design space (
Figure 2
) comprises two axes.

First, Types of Modifications describes what part of the user’s experience with the target application has changed, from what users see (
presentation
), how the user operates the application (
interaction
), and what they can do with the application (
capability
). A presentation change can affect individual elements, for example, labels and icons (
element
) or the way elements relate to one another (
structure
). Similarly, an interaction change can affect individual action (
modality
) or a sequence of actions required to complete a task (
steps
). Capability changes whether a functionality is available to the user at all. Our dimensions follow similar distinctions in prior design spaces that distinguish transformations of objects from their layouts 
(
Florins and Vanderdonckt, 2004
)
, transformation from presentation 
(
Min et al., 2026
)
, and behaviour from presentation 
(
Beaudouin-Lafon, 2004
)
.

Second, Relationship to Baseline describes how a modification relates to the baseline for each dimension. First, the baseline can be 
unmodified
. A change can be 
reductive
, removing something from the baseline, 
additive
, introducing something new, or 
replacement
, where something is removed and swapped with something new. Our mappings follow the same descriptors found in prior design space of text manipulation 
(
Zindulka et al., 2025
)
 and the design space of interaction re-mappings 
(
Zhang et al., 2017
)
. The following sections explain dimensions with example systems and compare the dimensions with prior design spaces.

3.1.1. 
Presentation Element

Concerns the visual properties of an individual interface element.

Reductive
 removes part of an element’s presentation without providing alternative encoding in its place. For example, reducing the saliency like 
ScreenCrayons
 rendering the unannotated areas with a light colour 
(
Olsen et al., 2004
)
 and 
Ephemeral Adaptation
 fading the menu items users are less likely to use 
(
Findlater et al., 2009
)
. Adaptive hypermedia similarly describes elements being dimmed 
(
De Bra et al., 1999
)
 and Min et al. identify element representation that removes or simplifies encoding 
(
Min et al., 2026
)
.

Replacement
 preserves the information carried by an element but substitutes another presentation. For example, 
Prefab
 translates interface labels into another language 
(
Dixon et al., 2011
)
, 
Stylette
 rewrites the cascading style sheets (CSS) of a selected web element from natural language 
(
Kim et al., 2022
)
, and 
DOMSteer
 changes the border to increase the saliency of a web element 
(
Hao et al., 2026
)
.

Additive
 introduces new visual channels. For example, 
Prefab
’s favourites enhancement displays a star on existing widgets 
(
Dixon et al., 2011
)
, 
ToolClips
 shows contextual tutorial video over AutoCAD icons 
(
Grossman and Fitzmaurice, 2010
)
, and 
Sikuli
 attach annotations to interface elements 
(
Yeh et al., 2009
)
. The difference between replacement and additive is whether the original presentation remains. Both require identifying the elements, but the former also requires covering or redrawing the element. Presentation change is often also associated with capability change. For example, 
Patina
 overlays community usage over the applications, providing new information while adding presentation element 
(
Matejka et al., 2013
)
 and 
reform
 attaches UI enhancements with new information to a website 
(
Toomim et al., 2009
)
. Both appear as presentation changes, but the information added did not previously exist in the original application, and we therefore consider them as capability additive as well.

3.1.2. 
Presentation Structure

Concerns the organization among the elements, such as the position, grouping, and distribution across regions or screens.

Reductive
 hides groups of elements from the user. For example, the personal interface for Word changes the commands exposed by its menus and menu bars 
(
McGrenere et al., 2002
)
, 
Dark Pita
 enables users to suppress distracting interface content 
(
Lu et al., 2024b
)
. In these cases, the individual hiding is also considered a reducing presentation element.

Replacement
 restructures elements. For example, 
Interface Facade
 lets users cut, duplicate and recombine regions of widgets of running applications 
(
Stuerzlinger et al., 2006
)
, 
Masonview
 reorganizes elements of existing websites 
(
Min et al., 2023
)
, and 
Orca
 
(
Jiang and Xia, 2025
)
 and 
Chickenfoot
 
(
Miller et al., 2010
)
 rewrites the layout of web content. 
SUPPLE
 restructures an interface by computing a layout based on device and user models 
(
Gajos and Weld, 2004
)
.

Additive
 appends a new region alongside the existing layout. For example, 
WinCuts
 copies a live region of a window into another view without removing it from the source window 
(
Tan et al., 2004
)
, 
TaskLens
 add generated task-oriented panels beside Blender’s existing interface for learning 
(
Liu and Sra, 2026
)
, and Gajos et al.’s split interface design creates a duplicate additional toolbar while keeping the unmodified interface 
(
Gajos et al., 2006
)
. Similar to presentation element modification, structural modification may also introduce new capabilities. For example, 
Fusion
’s mashed-up UI 
(
Zhang and Guo, 2018
)
 and 
Wildcard
’s spreadsheet 
(
Litt and Jackson, 2020
)
 appear as additional panels but also introduce computation (capability) not previously available in the application.

3.1.3. 
Interaction Modality

Concerns about modifying the type of modality for an interaction.

Reductive
 disables a type of interaction. For example, disabling short button presses for accessibility 
(
Levine and Schappert, 2005
)
, disabling touch input when a pen is present 
(
Hinckley et al., 2010
)
, or disabling single-finger taps to curb phone use 
(
Lu et al., 2024c
)
.

Replacement
 swaps a type of interaction with another operation or pathway. For example, 
Prefab
 adds target-aware pointing techniques 
(
Dixon and Fogarty, 2010
)
 or changes clicks to sliding gestures for tablet input 
(
Dixon et al., 2014a
)
.

Additive
 introduces an alias to activate the same functions with new pathways. For example, the 
ICON
 toolkit enables rerouting alternative input device to control an application 
(
Dragicevic and Fekete, 2004b
)
, 
Grab ’n’ Drop
 adds toolglass interaction over third-party applications without removing the original menus 
(
Eagan, 2017
)
, 
Astral
 maps phone sensors to mouse and keyboard events for rapid prototyping 
(
Ledo et al., 2019
)
, 
Genie
 exposes recovered web commands through speech and keyboard without removing the page’s existing controls 
(
Swearngin et al., 2017
)
. 
Improv
 
(
Chen and Li, 2017
)
 describes a system for modelling UI behaviours for remapping controls, but since the original interaction channel is intact, we consider it as additive. Zhang et al.’s one-to-zero, one-to-one, and zero-to-one mappings are similar to our reductive, replacement, and additive modifications 
(
Zhang et al., 2017
)
.

3.1.4. 
Interaction Steps

Concerns the sequence of carrying out a task. This is a view on change to the number of steps, which is different from prior definitions that concerned adding or removing elements, structures, or pathways. We take on this definition to echo the many-to-one and one-to-many interaction mappings in 
Interaction Proxies
 
(
Zhang et al., 2017
)
, as it helps describe automation.

Reductive
 shortens the steps it takes to complete an action without changing the action’s outcome. Automating the systems shortens the number of steps for users to complete a task. 
CoScripter
 
(
Leshed et al., 2008
)
, 
Chickenfoot
 
(
Bolin et al., 2005
)
, 
Sikuli
 
(
Yeh et al., 2009
)
, 
SUGILITE
 
(

)
, 
Koala
 
(
Little et al., 2007
)
, 
MultiClick
 
(
Zhang et al., 2025c
)
, 
PUMICE
 
(
Li et al., 2019
)
, and 
Rousillon
 
(
Chasins et al., 2018
)
 all convert repetitive or multi-step interactions into fewer steps or a single trigger. When the system creates a new trigger, such as a new button, that bypasses the original interaction steps, it is also considered to have modified the interaction modality. 
Anchored Customization
 
(
Ponsard and McGrenere, 2016
)
 surfaces, anchors, and highlights setting options in a multi-layered interface, and in doing so, it also modifies presentation elements (adds a highlight) and structure (adds controls).

Replacement
 reroutes one sequence with another without necessarily shortening it. For example, 
Interface Facade
 
(

)
 reroutes a drop-down menu with radio buttons, but this does not change the number of steps to complete the operation.

Additive

3.1.5. 
Capability

Concerns the set of outcomes an application makes available.

Reductive
 restricts the outcome of the application to what’s reachable from the user. UI mashups extract capabilities from an existing application to package them into an app. For example, 
A-Mash
 extracts the selected functionality from an existing application 
(
Lee et al., 2022
)
. In this case, the application being extracted experiences reductive modification, as some of its functionalities are rendered unreachable. But for the newly formed mashup interface, it experiences additive modification. 
Varv
’s schema and actions-based application enables users to remove functionalities through either using the “omit” operator that removes functions or the “pick” operator that selects a subset of actions 
(
Borowski et al., 2022
)
. Since the end result is a reduced set of available features, we consider both as a reductive modification to the baseline.

Replacement
 overrides the underlying implementation and algorithm, which makes the performance or existing capabilities better, without introducing a new capability. For example, 
Chrome Frame
 is an Internet Explorer plug-in that changes the browser’s rendering engine while retaining the original browser interface 
(
Chr, [n. d.]
)
.

Additive
 extends the possible outcome from using the application. For example, 
WADE
 adds external service into a host program 
(
Meng et al., 2014
)
, 
ToolTrack
 add counters to buttons to support users exploring and learning features 
(
Masson et al., 2022
)
, and computation abstractions add new capabilities to existing data 
(
Min et al., 2025
)
. 
Scotty
 injects functionality to the send button to check if the user forgot the attachment 
(
Eagan et al., 2011
)
. This is an example of adding new capabilities but maintaining the original interface.

3.2. 
Framework of Modification Mechanism

We characterize how prior modification systems use different forms of 
application access
 provided by the target application to achieve various levels of 
synchronization
. By that, we mean the extent to which the modified experience remains synchronized with the target application’s state and actions during use. Tight coupling is particularly important for modification systems that leave the application’s underlying implementation unchanged. Because these systems modify how users perceive and interact with the application rather than rewriting the application’s code, the modified interface must continuously create a proxy to reflect the state of the target application, and vice versa. The tighter this coupling, the more the modification can behave as an integrated part of the application, allowing users to interact with the modified experience without distinguishing between the modification interface and the target application.

Figure 3. 
Framework of Modification Mechanism. 
Application Access
 describes the pathway used by the modification system. 
Synchronization
 describes the extent to which the modified experience remains synchronized with the target application’s state and actions.

3.2.1. 
Application access

This describes the representation of the target application that a modification system has access to.

Source Code.
 At one extreme, the modifying system owns the substrate to be modified. In other words, the modification system is the application. As such, the presentation, data, and representations can all be directly inspected and edited by the system. 
Webstrates
 
(
Klokmose et al., 2015
)
, for example, makes the running application a shared document that itself can rewrite, while 
Varv
 represents applications through schema and actions that can be extended or omitted 
(
Borowski et al., 2022
)
. Because the modifying system controls the representation that drives the interface, systems can change the presentation, interaction, and capabilities directly.

Published Interface.
 This includes the domain representation provided by the developer, such as APIs, MCPs, command-line interface, scripting, and plugin frameworks. For example, 
DynaVis
 interfaces with Vega-Lite to generate widgets with callbacks to modify properties of the visualization 
(
Vaithilingam et al., 2024
)
, and 
Bespoke
 builds controls over command-line applications 
(
Vaithilingam and Guo, 2019
)
. This provides a stable access to tested controls. However, the generalizability of modifications would be limited by what the developers enable.

Toolkit or Platform.
 A modifying system may choose to exploit the UI toolkit and or features of the programming language that were not designed as extension points. For example, 
Genie
 analyze a host application’s JavaScript and event structure 
(
Swearngin et al., 2017
)
, 
Scotty
 changes method implementations in running Cocoa applications through runtime toolkit overloading 
(
Eagan et al., 2011
)
, and systems such as 
A-Mash
 use operating-system mechanisms to extract and embed live interface components from unmodified applications 
(
Lee et al., 2022
)
. These accesses are not intentionally designed by the app developers, but can be used by the modification software if the application is built with those toolkits and languages.

Accessibility Tree.
 It exposes a structured description of an interface outside the application’s implementation. Systems such as 
Interaction Proxies
 
(
Zhang et al., 2017
)
 and 
Interface Facades
 
(
Stuerzlinger et al., 2006
)
 use accessibility information representation to recover element labels, roles, bounding boxes, states, and support actuation. These are routes that provide some access to the application internals, but availability is dependent on the quality and completeness of the accessibility information supplied by application developers.

Pixel.
 Finally, a modification system can use the same visible output channel that’s available to the user. 
Prefab
 
(
Dixon et al., 2014b
)
 locates the controls by matching pixel-based pixel properties and recovers widget state and style from the hand annotations 
(
Dixon et al., 2014a
)
, and 
Sikuli
 similarly locates click targets from screenshot templates 
(
Yeh et al., 2009
)
. While rendered output requires the least cooperation from the application developer, it demands the most effort for a modifying system to recover the structure, behaviour, and states that were explicitly provided.

Moving from the left (source code) to the right (pixel) poses a trade-off between developer-supported structure and broader applicability of modifications. Improvements in UI screen understanding and computer use models make it increasingly easy to leverage pixel as a modification substrate, but the access still needs to be connected with actuation back to the unmodified application.

3.2.2. 
Synchronization

Synchronization describes the extent to which the modified experience remains synchronized with the target application’s state and actions at runtime. We distinguish levels of coupling by how directly and continuously this synchronization can be maintained. The mechanisms supporting that synchronization may be explicitly exposed by the target application, or reconstructed by the modifying system from less structured forms of access.

Read Only.
 This is the weakest level, where a system can only recover information about the current interface without routes to actuate on the host software. UI-understanding systems, for example, recover interface elements from pixels 
(
Zhang et al., 2021
; 
Wang et al., 2021
; 
Wu et al., 2021
)
 and 
Patina
 uses the accessibility API to recognize buttons to overlay dynamic usage visualization without actuating on the application 
(
Matejka et al., 2013
)
. The reading channel can inform a presentation modification, but cannot affect the interaction.

Event Actuation
. This adds another route through user-level input. For example, 
Sikuli
 locates the targets from screenshots and automates executions through synthetic mouse and keyboard events 
(
Yeh et al., 2009
)
. More recent vision-based computer use agents, such as 
UI-TARS
, operate applications via unit actions like clicks, typing, and scrolling 
(
Qin et al., 2025
)
. This enables OS-level actions over an application that is opaque for modification. However, input events do not by themselves provide stable handles to operate the host application, and the system must continuously decide where and how to act.

Addressable Operation Binding.
 This provides the modification with a stable handle to the application. Compared with the previous level, it provides modifications that identify control, procedure, and steps, enabling the modifications to affect the operations of the software. The handle might be an interface control, such as 
Interaction Proxies
’ accessibility nodes as inspectable state and route to invoke actions on an element 
(
Zhang et al., 2017
)
. Or the handle can be procedures and commands. 
SUGILITE
 generalizes demonstrated interactions into reusable procedures 
(
Li et al., 2017
)
 and the 
Declarative Model Interface
 abstracts GUI interaction into explicit access, state, and observation primitives for agents to operate 
(
Wang et al., 2026
)
.

Reactive State Binding.
 The strongest operational coupling is to be able to both manipulate the host software and synchronize response to changes to the modified interface to promote human use. For example, 
Wildcard
’s spreadsheet is synchronized with an application-editable spreadsheet, and changes in one representation propagate between representations 
(
Litt and Jackson, 2020
)
. When the modifying system owns an underlying representation, this type of coupling is provided for free. For example, 
Jelly
 can modify a shared task-driven data model to drive real-time updates to the data and generate an interface 
(
Cao et al., 2025
)
. Reactive binding is also possible with a pixel alone. The 
Prefab
 follow-up paper synchronizes the button states between the original interface and a sliding widgets overlay through pixel-based recognition 
(
Dixon et al., 2014b
)
.

4. 
Interface Quilt and Interface Patch

We propose Interface Quilt and interface patches for modifying existing applications (
Figure 1
). An interface patch is a generated interface overlaid on the existing application to modify the user’s experience with the application’s presentation, interaction, and capabilities. And Interface Quilt is a system that supports generating and running interface patches through computer use agents (CUAs) and generative UI (GenUI).

4.1. 
Interface Quilt Supports Generating and Running Interface Patches

The design space (
Figure 2
) identifies modifications to an application’s presentation, interaction, and capabilities, and the mechanism framework (
Figure 3
) characterizes how such modifications access and maintain synchronization with the application. These analyses informed the design of Interface Quilt.

Interface Quilt consists of two parts. First, a build-time pipeline uses CUAs to explore the target application and identify the available UI controls and observable states required to access and synchronize an interface patch with the application. A coding agent then uses these identified operations to generate an interface patch. Second, a runtime hosts the generated interface patch alongside the target application. When a user interacts with the interface patch, the runtime executes the corresponding UI actions in the target application. When relevant application state changes, Interface Quilt observes those changes and updates the interface patch accordingly.

This architecture reflects two points in our framework (
Figure 3
). First, Interface Quilt recovers the target application through its rendered interface rather than source code, application APIs, or accessibility metadata. Second, it maintains synchronization between the target application and the interface patch. Interface patches can request application operations, and application state can update the patch. Together, these mechanisms allow the same runtime to support interface patches that modify presentation, interaction, and capability, which we demonstrate in the following sections.

4.2. 
Demonstrating Interface Patch Modifying Applications

We first provide two compound examples, À la Carte Interface and Put-that-there, to demonstrate the interface patch’s ability to execute multiple types of modifications at once. We then provide two sets of interface patch examples targeting multiple applications to showcase specific types of modifications.

4.2.1. 
À la Carte Interface

With this interface patch, they can tap into the retouching algorithm of professional software like Affinity, without needing to leave PowerPoint, manage multiple open windows, sync the image between applications, or learn how to use the complex interface of Affinity. The user interacts with an interface patch cutout of Affinity’s canvas and retouches by gesturing to paint like they usually do (

This workflow demonstrates Interface Quilt’s ability to create an interface patch that modifies across the design space. On presentation, new interface elements are additive, and the cutout of the original Affinity interface is a structural addition. On interaction, the user’s paint operation on the interface patch is unmodified, the GenUI sliders are modality replaced, and the synchronization between the PowerPoint image and Affinity is step reduction. On capability: from Affinity’s perspective, this is a capability reduction because the user can no longer access other features of Affinity through this interface patch, whereas from PowerPoint’s perspective, this is both a capability replacement, using Affinity’s algorithm for retouch, and a capability add, as PowerPoint’s erase feature does not contain settings for the retouch pen.

This is an extended version of prior systems like WinCuts 
(
Tan et al., 2004
)
, Interface Facade 
(
Stuerzlinger et al., 2006
)
, and Highlight 
(
Nichols et al., 2008
)
. In addition to duplicating interface elements and screen regions, Interface Quilt enables (1) packaging interaction paths discovered from computer use agents at build time into a single button-triggered deterministic workflow at runtime. This effectively breaks down the cross-application data silos; (2) leveraging the generative UI capabilities to reskin one applications’ UI for new ways to interact and more cohesive integration to another application; and (3) automatically handling the window management to position the interface patch directly above the original image in PowerPoint, creating an integrated experience.

4.2.2. 
Put-that-there

Figure 5. 
Interface patch example: Put-that-there. (A) User says “create a blue circle here” while pointing the cursor at a point on the canvas. (B) The system creates a blue circle. (C) User says “put that” while pointing at the red square and “there” while pointing at another point on the canvas. (D) The red square moves to where the user pointed. (E) User says “move the blue circle here” while pointing on the canvas. (F) The system identifies the object and moves it to where the user points.

Figure 5
shows the user manipulating shapes on the vector graphics app, Affinity, with their voice and cursor position, inspired by the put-that-there interaction technique 
(
Bolt, 1980
)
. With Interface Quilt, the user can operate Affinity through multimodal interactions even when the software does not support it. The interface patch includes a live speech bubble at the bottom of the interface. The interface patch also renders the user’s cursor location and corresponds to speech on the canvas, like “here” and “there.”

To create an object, the user describes its properties while pointing to the desired location. The interface patch combines the speech and pointing input and maps the request to application operations recovered at build time. Interface Quilt then invokes the corresponding Affinity controls to create the shape (
Figure 5
A–B). To move an object, the user says “put that” while pointing to the object and “there” while pointing to its destination. Interface Quilt recovers the referenced object’s location, while the interface patch interprets the user’s multimodal command and invokes the corresponding move operation. The user can refer to the object by location or semantics. For example, the user can say “move the blue circle here.” The interface patch identifies the object and its coordinates, then moves the object to the user’s pointed location. In addition, by leveraging Interface Quilt’s ability to identify object location, this put-that-there interface patch also supports adding different shapes with different sizes, changing the colour of a shape, multi-select, align, delete and duplicate shapes.

This demonstrates Interface Quilt’s ability to create an interface patch with a new presentation element. As the user can still operate the original interface as is, the interface patch does not replace the original interaction but adds an alternative voice input modality. It reduces interaction steps, because it automates procedures such as adding objects and changing colours into one command. As the capabilities for rendering and manipulating objects remain the same, this interface patch does not change the application’s capabilities.

Compared with the original put-that-there 
(
Bolt, 1980
)
 implementation for large screen multimodal interactions, our system uses the same point and speech interactions for a desktop application. Because the interface patch is implemented by supplying the coding agent with the original paper, it uses the same symbolic matching algorithm for identifying objects. For recognition of shapes and transcribing the user’s speech, the interface patch sends requests via external APIs. The experience of using the interface patch compared with a vanilla computer use agent is that the interface patch retains the mix-initiative experience, where the user provides verbal commands while maintaining precise location input via cursor location, and repetitive steps like selecting, adding, and aligning multiple objects are automated.

This interface patch demonstrates a presentation structure that is context-aware of the user’s selected object’s type and the location of the object.

5. 
Implementation

Figure 8. 
Interface Quilt Architecture.

Interface Quilt’s runtime architecture separates the UI, logic, and OS support (
Figure 8
). The 
Surface
 renders the interface patch UI and accepts the user’s input. The 
Controller
 orchestrates the I/O events, hosts multiple interface patch runtimes, and dispatches I/O events to the corresponding interface patches. The 
Daemon
 and 
Local Models
 are separate processes that provide an I/O connection for controllers with the OS and provide API call services to VLM/OCR and CUA.

We implement Interface Quilt on macOS, where the surface is an Electron window, the interface patches and controllers are written in TypeScript and executed in a Node.js runtime, and the daemon is written in Swift. We describe the implementation for macOS, but the same architecture can be applied to other operating systems.

5.1. 
Interface Quilt Architecture

5.1.1. 
Surface Layer

The surface is a single Electron window displayed above all applications. We use Electron because it can reliably render the interactive interface patches written in TypeScript. By default, the surface is a transparent, always-on layer that permits all users’ interactions to pass through to the application beneath it by setting 
NSModalPanelWindowLevel
. Only the region where an interface patch is running becomes interactable. Having interface patches on a single surface that’s controlled by the system enables precise interface element placement. We create a shared 
Cut Renderer
 that contains shared frame streaming capabilities to avoid reimplementations between interface patches.

5.1.2. 
Controller Layer

The controller is a standalone TypeScript Node.js process containing the runtime logic. It sits between the daemon and the surface, wiring OS-specific privileged operations such as capture and synthetic input via the daemon, while syncing the windows and hit regions with the surface. The controller decides on which route to best support an interface patch.

An 
orchestrator
 manages all active interface patches by providing a central event queue 
runStreams()
 that provides each active interface patch with its own runtime, including event callbacks, drawing operations, hit-region namespace, and I/O requests. In the case of the slider and marking menu, the two interface patches each contain a runtime, but share the controller, surface, and daemon, managed by the orchestrator. Events from both the surface and the daemon return to the orchestrator. Native pointer, keyboard, window, and application change events come from the daemon, while interactions with the interface patch’s UI come from the surface. The controller routes the events to the interface patch runtime that subscribes to it. For time-based events, where the interface patch needs to periodically poll the values on a region, such as syncing slider values, an interface patch can also initiate the poll without waiting for callbacks. In sum, the controller coordinates and schedules events rather than using an update loop, as many interface patches can be static and do not require periodic repaint.

5.1.3. 
Daemon Layer and Local Models

The daemon on macOS is a Swift application, packaging OS privileges for the controller access, containing the screen capture, an I/O driver, and window management modules. The decoupled design enables Interface Quilt to explore the OS interfaces once, and expose them as custom I/O events to service multiple interface patches. This avoids rebuilding or re-exploring the OS capabilities and enables sharing interface patches between OS by updating the daemon layer alone.

The 
Screen Capture
 module wraps macOS’ 
ScreenCaptureKit
 for two purposes. First, to expose the UI for local models to recognize UI elements and parse text. Second, to support cutting and streaming UIs to interface patches without native support, like available on other OS 
(
Stuerzlinger et al., 2006
)
. The I/O driver handles clicking, typing, intercepting and notifying the orchestrator of low-level HID events.

The 
I/O Driver
 posts events to the corresponding process either through 
CGEvent.postToPid
 or a private macOS API named 
SLEventPostToPid
 
(
Cua AI, Inc., 2025
)
 to control the target application. This allows an interface patch to operate on a background application without moving the user’s cursor or bringing the application to the forefront. However, the activation of menus and controls of some apps depends on the system pointer hover that cannot be simulated this way, such as PowerPoint’s dropdown menus. In such cases, the daemon provides a fallback that temporarily borrows the user’s cursor with 
CGWarpMouseCursorPosition
 to click. The daemon streams continuous user mouse events live to support the painting strokes. Synthetic events are tagged so that the daemon does not report them back to the controller. To type, the daemon uses 
CGEvent(KeyboardEventSource:)
 to simulate low-level keyboard events.

The 
Window Management
 module supports identifying which window is currently active with 
CGWindowListCopyWindowInfo
 to switch between corresponding interface patches. It also identifies the pid of the current window, allowing the display of the corresponding interface patch and the wiring of I/O events.

The 
Local Models
 provide three paths for parsing the application’s UI. First, a full pass uses bounding boxes, OCR, and computer vision models to identify UI elements and controls. Second, a faster, cheaper runtime route uses the UI grounding cached at build time to conduct pixel-based comparisons using local luminance for text tags and zero-mean normalized cross correlation (ZNCC) glyph template matching. Third, the daemon also uses OS-specific user input APIs that do not assume developer support as heuristics to trigger screen captures and state updates

5.2. 
Building an Interface Patch

Interface Quilt’s architecture serves as a development harness for coding agents. At build time, the coding agent uses Interface Quilt’s computer use and perception capabilities to explore the target application. We prompt a coding agent with the desired modification and give it access to the existing Interface Quilt codebase and runtime architecture. When recreating an interaction technique from prior work, such as marking menus or put-that-there, we additionally provide the corresponding paper as a specification of the intended behaviour. The coding agent can use Interface Quilt’s daemon to control the target application and inspect the streamed interface, while local models expose information such as element bounding boxes, text, and visual assets. It can also use its own visual understanding to interpret interface structure and behaviour. Together, these infrastructures allow the coding agent to explore the target application, identify relevant states and controls, and implement the runtime interface patch specifying the behaviours.

Each interface patch contains a TypeScript file with its executable interaction logic and a JSON binding containing application-specific data. The TypeScript implementation exposes an 
onStream(ctx, params)
 function that connects the patch to controller events at runtime, while the binding stores application-specific information such as visual assets and execution routes. Separating patch logic from application-specific bindings allows the same interface patch implementation to target multiple applications with minimal changes. For example, we use the same marking-menu logic for both PowerPoint and Overleaf. Through 
onStream
, an interface patch receives a shared context and subscribes to callbacks such as 
onPointer
, 
onKey
, and 
onReload
. The context also exposes surface and daemon APIs, allowing the interface patch to invoke operations such as

paint()
, 
skyClickAt()
, 
keyToPid()
, and 
pointerAt()
.

6. 
Discussion

We review the successes and limitations of Interface Quilt as a system for creating and running interface patches on applications with only pixel access, consider when alternative forms of application access could better support their construction and runtime synchronization, and discuss the broader implications of Interface Quilt’s architecture and interface patches as a form of software modification.

6.1. 
What Interface Patches Can and Cannot Modify

Our demonstrations show that interface patches can modify presentation, interaction, and capabilities across a range of existing applications, but that these modifications vary substantially in difficulty. These differences stem from what Interface Quilt can observe and control through the rendered application UI, and from how much of the target application’s behaviour an interface patch must reproduce rather than reuse.

Adding 
presentation
 and 
capabilities
 is simple, as Interface Quilt can render a new interface running on top of the target application. It is harder to reduce or replace 
presentation
, because the system needs to first identify the area of the original interface through a vision model, then recover assets such as text and labels to recreate an interface patch with coherent visual language.

Reducing and replacing the 
capabilities
 is even more effortful. It is often easier to reuse the main canvas interface and recreate the controls surrounding it. For example, with Interface Quilt, it is possible to achieve the effect of a complete replacement of application A’s core capabilities with a similar application B while retaining A’s interface. However, to do this, Interface Quilt would recreate application A’s interface and use it as controls for application B, rather than actually replacing the runtime library of application B. This is because Interface Quilt’s approach is suitable for recreating the controls UI as they are observable, but impossible to recreate an application’s internal algorithm, such as rendering behaviours, as it’s inaccessible from observation alone.

The difficulty of 
interaction
 modifications varies by modalities or what is exposed on the surface of the target application. Mapping users’ clicks or more sophisticated input techniques to basic clicks on the interface is easy, as the buttons are exposed and Interface Quilt’s daemon can easily reproduce clicks. Similarly, adding multimodal interactions is easy, as Interface Quilt’s architecture enables generating and hosting multimodal behaviours. Supporting gesture inputs on the target application is more difficult, such as a drag gesture, depending on its implementation. For example, we demonstrate success with Affinity (
Figure 4
), but we cannot retarget gestures on Fusion that used the Qt framework on macOS. The daemon has no path through the OS-level APIs to manipulate and stream the user’s input events to Fusion, without taking over the user’s cursor, which interrupts the user’s sense of control.

6.2. 
Pixels vs. APIs

Pixels and computer use provide benefits not available through other application access pathways, such as API. First, the pixel provides Interface Quilt with visual information of the interface, enabling generating interfaces that share the visual language of the target application. We demonstrate this with the reordered controls (
Figure 6
A) and generated buttons with similar visual language positioned adjacent to the target application’s controls (
Figure 6
B). Controlling the interface through computer use agents makes it easy to build multimodal interactions that require information about the user’s cursor, like capturing the user’s cursor in the put-that-there example (
Figure 5
).

The Interface Quilt’s pathway trades off seamless synchronization for generalizability. For example, in the à la carte interface patch, synchronizing the image between PowerPoint and Affinity required a sequence of clicks on the interface, rendering the OS temporarily unusable to the user. On one hand, APIs, MCPs, and scripting can make the process faster and work in the background. On the other hand, Interface Quilt promotes generalizability, where any application’s file import and export can be executed, regardless of developer support. Additionally, even though the synchronization between the values on the interface patch and the target application is near instant, there exists a short delay. This becomes especially apparent in the in-situ control interface patch (
Figure 7
C) where Interface Quilt uses models to classify the object a user interacts with. We expect that more capable and efficient models will reduce or close the gap.
