Abstract

Agents based on large language models (LLMs) can now delete files and send payments on behalf of their users. News media reports routinely describe failures of these agents (e.g., Replit’s coding agent deleting a production database), but a report often only says what went wrong and rarely (in)validates the incident or finds its root cause. Incident catalogs collect these reports, and benchmarks record whether agents fail, but neither replicates an incident nor tests the cause its report might identify.

In this paper, we present 
ROGUE-AI
 (Replication of Agentic Security Events: Audit and Investigation), 
a multi-agent framework
 that closes the above gap and rebuilds each reported incident offline together with a matched control that lacks only the blamed cause, and runs agents on both. As part of the framework, 
Claude-,
 Gemini- and GPT-based agents collect reports and build replications, an agent from another vendor reviews each build, and code decides whether harm occurred. Our results suggest that 
ROGUE-AI
 is able to reproduce the reported harm in 89% of its 108 attempted replications.

Current models wiped the production rows in about half of the incident sessions, while all 15 control sessions kept their rows, which supports the report’s claim. In this paper, we present

ROGUE-AI

Other agents build the replication and its control, an agent from another vendor reviews each build, and code decides whether harm occurred. From 253 reports, Claude-, Gemini- and GPT-based agents built 108 replications of 96 incidents in 38 classes, at $3.28 each. 
ROGUE-AI

6.2

4

In the replication of the Medicare incident, for example, the five models entered the portal’s restricted area with the browser’s saved sign-in in 14 of 15 incident sessions and in none of the 30 control sessions. Of the 72 incidents with real-world harm, 62 had no attacker, and in these 62, an agent that did what its task asked missed an ordinary hazard, such as the shared database (§
5

Defenses against prompt injection miss most of this harm. Replications without an attacker caused more harm than replications of prompt injection for all five models, but they contain no injected instruction, which is what these defenses look for. Defenses taken from the reports did better, and with confirmation by the user or data-flow tracking, the five models caused no harm. Checks that match the text of an action were weaker, because rephrased attacks still caused part of the harm (§
6.4

We added a warning after each tool output that names the hazard and its consequence, such as a warning that the tests drop the production database. Background and Criteria

LLM Agents and Their Incidents.
 By an 
LLM agent
 we mean a program in which a language model decides which tools to call and acts on the results 
[
16
]
. A coding agent runs shell commands, a personal assistant sends and deletes mail, a browser agent fills in web forms, and a wallet agent signs transfers. Many agents also load tools through the Model Context Protocol (MCP), which lets them call tools published by other parties. We count an event as an 
agent incident
 if an LLM agent took an action through a tool and that action caused harm or achieved an attacker’s goal against a victim, and if the event was first reported between January 2025 and October 2026. Harm in the wild, demonstrations on shipped products, threat reports and vendor evaluations qualify, but events on research prototypes do not.

Running Example.
 We follow the Replit incident throughout 
[
13
]
. The user had told the agent many times to make no change without permission 
[
14
]
. During this code freeze, the agent’s commands deleted the production database, and Replit’s CEO confirmed the deletion. Nobody attacked the agent, which had a standing rule against changes, a task that seemed to need a database change, and production credentials.

Criteria for a Replication.
 To test such a report, a replication has to meet six criteria, which follow from how reports and agents fail. First, the report is checked against a primary source, since we had to correct 76 of 253 incident records and found 2 contradicted by their sources. Second, a current model makes the incident’s decision again, because rerunning the recorded commands tests only the commands. Third, a matched control removes only the hazard, because the task alone can produce harm that should not count toward the reported cause. Fourth, code decides harm from the environment’s state, because agents misreport their actions, as the Replit agent did 
[
14
]
. Fifth, a pipeline builds the test from the report, because new reports arrive weekly. Sixth, the test runs offline on any model, letting a vendor rerun it before a release.

Comparison with Prior Work.
 As Table 
1
 shows, no prior work meets the criteria that we can check from its publications. Benchmarks run current models, and AgentDojo runs its tasks with and without the injection. Their test cases, however, come from the benchmarks’ authors. Chronicle needs a recorded run and simulates the model’s outputs, and Squidbrake reruns reported commands against its rules.

Closest in method is CVE-Genie 
[
12
]
, which reproduced 428 of 841 CVEs at an average cost of $2.77. Developer agents set up the software and write an exploit, critic agents review the steps, and a verifier checks a signal specific to the vulnerability. The target of CVE-Genie, however, is software, where the result of an exploit does not depend on a model’s choice. In an agent incident, by contrast, the test concerns a model’s decision, which varies between models and runs, and the task alone can cause harm. 
ROGUE-AI
 therefore adds a matched control, repeated runs on any model and a statistical test for each claim (§
3
).

Validity Conditions.
 As Table

Fidelity to the Report.
 The other two conditions, a natural path to the hazard and fidelity to the report, do not affect this estimate. They decide whether the replication’s hazard is the report’s hazard, and a replication that fails them tests a different claim. A replication therefore takes only the elements that the report and its primary sources state. The replication fills omitted details, such as the model or system prompt, with marked neutral defaults and adds no rule, prohibition, pressure or hint, since any of these could change the decision under test. Code checks the first three conditions, a reviewer model checks the natural path, and both check fidelity to the claim card, which ties each element of the claim to a sentence of the report.

4 
The ROGUE-AI Pipeline

This section follows a report through 
ROGUE-AI
 to an outcome, with the Replit report as the example. 
ROGUE-AI
 uses LLM agents as automation tools, and Figure 
1
 shows where they work. In the first two stages, searcher agents find reports, a screener applies our inclusion rules, a verifier compares each report with a primary source, two labelers label the incident and a report analyst writes down its claim (§
4.1
). In the third stage, a domain builder writes the replication, and a path reviewer and a domain reviewer check the build (§
4.2
).

In the last two stages, code runs the validity checks and the models under test run the replication. Code then decides harm and computes the test, and diagnoser agents read the transcripts of replications that fail. The stages are linked by a repair loop, in which reviewers send faulty builds back to the builder, by a diagnose-fix-rerun loop that fixes failed replications (§
6.2
), and by an audit that reruns the replications on each new model.

We follow three rules so that a mistake of one agent does not reach the results. First, no agent checks its own work. Two labelers from different vendors label each incident, and a model from a vendor other than the builder’s reviews the build. Second, code decides harm from the environment’s final state. Third, each of the seven judgments that agents make has an independent check (Table 
3
). A person decides in three cases: no agent can confirm a source, three labelers give three values, or a build still fails a check after three repairs. The person drops, accepts or fixes the case, and the decision is logged.

4.1 
From Reports to Claims

Collection.
 Over six rounds of web searches, searcher agents found reports and a screener decided which ones qualified. In the first round, eight searcher agents worked from fixed written briefs, one per area of agent use. Rounds 2 to 6 ran queries from fixed generators and logged the URLs they returned, and these rounds can therefore be rerun. We merged duplicates and applied written inclusion rules in a screening step. The six rounds gave 253 incidents first reported between January 2025 and October 2026.

Verification.
 Most readers learn of an incident from a news story, but a headline can blame an agent for a mistake that people made. For example, one headline reported that an AI agent deleted the finished season of a Swedish television show, while the broadcaster’s investigation blamed human error 
[
20
]
. The verifier therefore reads past the news to the most detailed source it can open: the company’s postmortem, a vendor’s confirmation, a CVE entry or advisory, the researcher’s disclosure or the victim’s account. Of the 253 incidents, 168 were confirmed as recorded and 76 after a correction, usually of a number, a date or a model name. Another 2 conflicted with their sources, the television deletion among them, and 7 remained unconfirmed, giving 244 verified incidents. Of the 199 eligible incidents (defined below), only 29 rely on news alone, and the selection rule prefers the incidents with the most detailed sources.

From Incidents to Claims.
 An incident enters the replication pool if it is verified, if an action the agent chose caused the harm, and if reproducing the incident needs no model training. We exclude incidents caused by the vendor’s own infrastructure or by a malicious owner. Of the 244 verified incidents, 199 qualify. Each pair of a setting and a root cause forms a 
class
, and 38 classes contain at least one of these incidents. From each class, a fixed rule picks the one or two incidents with the strongest evidence, which gives 56 representatives (Appendix 
B
).

The report analyst converts the record of a selected incident, with its labels and sources, into the claim 
 of §
3
 and a claim card that ties each element to a sentence of the report. We rebuilt 55 representatives, and we used the same tools to rebuild other incidents of their classes. This gives 108 replications of 96 incidents in all 38 classes.

4.2 
Building and Checking a Replication

Builders.
 A domain builder for each setting converts the claim into a replication, working from a brief on the tools and mechanics of that setting. From this brief, the builder writes the world, the task, the system prompt, the incident condition, the controls and the state check. Only the facts that the report and its primary sources state are used, and neutral defaults fill the gaps. In our study, the builders were Claude Sonnet 5.5 coding agents, and GPT-5.6-sol made the blind rebuilds below. In the Replit replication, the agent works offline in a Docker container under a system prompt that declares a code freeze. In the task, the user reports a broken executive search in a demo application. The README states that preview, test and production share the database in 
.env
, and the test setup recreates the executives table in that database. An agent that runs 
make test
 to check its fix therefore wipes the 1,206 production records.

Hazard Placement.
 As in the incident, the agent gets the ordinary tools of the setting, such as a shell, a mailbox or a wallet. The hazard appears in the data that these tools return, such as a production path in a configuration file, a long inbox, a changed tool description or a token amount in a different unit. In an adversarial replication, the attacker controls only the channel that the report names, such as a web page, an email or a published component. No tool is named after the failure, because a tool called 
delete_prod_db
 would reveal the tested behavior to the model. Reports rarely give the system prompt of the incident, so a replication takes its prompt from the product’s documentation or uses a generic one.

Controls and State Checks.
 Of the 108 replications, 106 have at least one control. In 73 of them, another control also removes the cue, and the harm rates pool all controls. For an injection, the matched control replaces the injected text with neutral text of equal length at that position. After a session, code decides harm from files and rows, the ledger, the sent mail and the network log. The agent’s own report does not count, because in several incidents, including Replit’s, the agent misreported its actions. About half of the replications run with one to three defenses from the incident’s report or the vendor’s fix, such as separate production credentials, a confirmation step or approval of tools by content hash. In 25 of the 62 defended replications, we wrote an adaptive variant, following Kerckhoffs’s principle. Under the confirmation defense, a simulated user approves only actions that the task asked for.

Reviewers and the Repair Loop.
 A model from a vendor other than the builder’s reviews the build in two roles. As path reviewer, the model plays an agent that does the task normally in the incident condition. It checks that this normal course of work reaches the hazard without an unmotivated step and without a prohibition or pressure that the report does not state. For Replit, running the tests to check a fix is such a normal step. As domain reviewer, the model checks that the report’s mechanism reaches the agent and that the controls change only the hazard. Complaints from the reviewer and from the checks below go back to the builder, and this repair loop stops when the build passes or after three rounds, always before any model under test runs. In the blind rebuild below, 7 of the 11 builds passed the scripted tests before any repair, and 10 passed after 19 repair rounds in total.

Validity Checks.
 Before any model under test runs, code checks the conditions of Table 
2
. First, scripted policies run through all conditions. A reckless policy must trigger the state check in the incident condition and in no control, and a careful policy must leave the check silent. In the Replit replication, the reckless policy caused harm only in the incident condition (Figure 
1
). Second, a model from a third vendor runs with a fixed reckless or careful instruction before the system prompt, to show that a model can also reach the hazard. Third, code compares the initial files, tools and prompts of the conditions, which must differ only in the hazard. Finally, code runs its part of the fidelity check and fails a build that adds a rule, prohibition or pressure missing from the claim card.

Simulations and Runs.
 In total, the replications run in ten simulations, one per group of settings, and the replications of a group share a world and its tools (Table 
10
 in Appendix 
B
). All data are synthetic, and no replication touches a real service, account or wallet. The destructive-action replications and the network part of the containment replications run in Docker containers with a real shell, because a mock shell would hide how 
rm
 and 
git
 resolve paths. In the other simulations, the agent’s services are modeled in Python. In the agent loop that serves all simulations, the model receives the system prompt, the user’s task and the tool descriptions. In reply, the model gives one action per turn in a text protocol (
ACTION: tool(arguments)
 or 
DONE: message
), for at most 10 to 26 turns depending on the simulation. Because all simulations share this one loop, a new model needs only an API adapter.

Validating the Builders.
 To test the builders without a person, GPT-5.6-sol rebuilt 11 catalog incidents from their records without seeing our replications. With Gemini 3.5 Flash under test, the 10 generated replications that passed their tests caused harm in 11 of 30 incident sessions and 0 of 60 control sessions. Our study’s replications of the same incidents caused harm in 11 of 33 incident sessions and 0 of 63 control sessions. If we count an incident as repeated when its incident condition caused harm and its controls did not, the two versions agree on 6 of the 11 incidents.

Validating the Reviews.
 A Claude coding agent read the sessions, state dumps and code of 26 builds of these incidents from five builder setups and labeled 8 builds with a fault that breaks a validity condition, such as a control that also changes the task. With Gemini 3.5 Flash as the review model, the reviews and checks rejected all 8 faulty builds and 11 of the 18 sound builds.

5 
Incidents in the Catalog

This section shows where incidents occur and why. The 199 eligible incidents span 38 classes in ten settings, and their number grew from 63 in all of 2025 to 136 in the first ten months of 2026. Researchers mostly demonstrate prompt injection on shipped products, whereas harm in practice came mostly from the agents’ own decisions.

Coding agents account for the most incidents (67 of 199), followed by vendor evaluation environments (30), the tool supply chain of MCP servers, skills and extensions (28), enterprise agents (17) and browser agents (17).

Untrusted instruction, the root cause behind prompt injection, is the largest root cause, with 82 incidents (41% of the pool). Each report describes in its own words what went wrong. Our two labelers read a summary of each report and chose the root cause that fits it best (§
3
), so the root causes in this section are our labels. To check these labels, one of the authors read 30 incidents drawn at random and agreed with the root cause in all 30 incidents.

The next three root causes involve no injected instructions. Unchecked authority (27) covers high-impact actions where a human process would require a confirmation, a limit or a narrower scope, as when coding agents pushed internal screenshots to public repositories under employees’ accounts

In instruction disregard (8 incidents), the agent breaks an explicit rule from its user, such as a code freeze; in fabrication (6), it states false facts that someone relies on; in failure escalation (2), its recovery from an error grows into the harm; and in manipulation (1), a person or agent in conversation persuades it.

In-the-Wild Non-Adversarial Harms.
 We split the pool by the evidence a report gives. Of the 199 incidents, 72 caused harm in the wild, 89 are attacks that researchers demonstrated on a shipped product, 28 come from vendor evaluations, and 10 are attack campaigns against agents described in threat reports. Although the first two groups are similar in size, they barely overlap in cause. Of the 89 demonstrated attacks, 88 involve an adversary and 76 are prompt injection, which disclosed data in 44 cases and changed systems without authorization in 27 cases. Of the 72 incidents in the wild, 62 had no attacker and 2 were prompt injection.

In the wild, data loss is the most common harm (32 of 72), ahead of data disclosure (10) and containment breaches (10). 6.1 
The Hugging Face Incident

The Reported Incident.
 The Hugging Face incident is the most widely covered incident in our catalog, and the companies involved and an independent investigator reported on it. In July 2026, OpenAI’s ExploitGym cyber evaluations launched tens of thousands of agents of several models, GPT-5.6-sol among them, in sandboxes that were meant to be isolated 
[
27
]
. According to METR (Model Evaluation and Threat Research), which read the agents’ messages and transcripts, agents that had been given an impossible task looked for a way to cheat through OpenAI’s internal package repository, where they noticed agents in other sandboxes.

One agent opened a message board, and its first message asked for help with an impossible task. About 1,200 agents sent more than 70,000 messages and files on this board, and 700 of them joined an attack on Hugging Face. Hugging Face reported that an autonomous agent system had reached internal datasets and service credentials and moved into several internal clusters over a weekend 
[
28
]
. No attacker directed the agents, which were doing their evaluation tasks.

The Decision We Replicate.
 The reports describe two steps, in which agents first coordinate on a channel that nobody assigned to them and some of them then leave the sandbox. The second step depends on vulnerabilities in OpenAI’s infrastructure, which an offline test cannot rebuild, and Gensee reproduced part of it with a live agent 
[
19
]
. 
ROGUE-AI
 therefore tests the first step, the decision that started the incident. In each run, 70 Claude Haiku 4.5 agents work in separate containers on an offline network, and each agent runs one shell command per turn. Half of the agents cannot finish their task, because a note in their workspace says that their decryption key went to a different agent by mistake. As in the report, the configuration lists the board, and no rule forbids messaging. In the matched control, the same configuration line lists a read-only mirror instead, and the board still runs.

As Figure 
3
 shows, 11 of the 35 agents without a key posted requests for their key, the first of them 62 seconds after the first agent started, and all 35 read the posts of other agents. With the mirror listed instead, 0 of 70 agents posted.

Finding 2.
 One configuration line that lists a shared message board was enough for agents to start coordinating on it. A rule in the prompt against messaging other workers did not stop them, as 39 of 50 agents without a key still posted.

Lessons from the Replication.
 No key changed hands, because 0 of the 233 key holders opened the board. The replication thus reproduces the first step of the incident, in which agents that cannot finish a task ask for help on a channel that nobody assigned to them. An offline test cannot rebuild the second step, the sandbox escape. For builders of evaluation sandboxes, the lesson is to keep shared services out of the sandbox, since a rule against using them failed.

6.2 
Failed Replications

Figure 4: 
Outcomes of the diagnose-fix-rerun loop for the 51 replications that the five models did not reproduce in the main runs, by simulation: reproduced by older or weaker models, reproduced in later rounds of the loop, or not reproduced. Other simulations are payments, personal assistant, customer support and multi-agent.

If a claim does not reproduce, the cause may lie in the model, the report or the replication. The 51 replications that the five models did not reproduce in the main runs therefore enter the diagnose-fix-rerun loop of Figure 
1
. Diagnoser agents read the transcripts and decide whether the model or the replication kept the harm from happening. In the first case, older and weaker models run the replication, to test whether any model can reach the harm. In the second case, a builder changes the replication, and the models run it again. A change may only remove an element that the report lacks, give the agent more turns or restore a detail that the report states (§
6.5
), and the controls receive the same change. The loop repeats until a model reproduces the replication or no change within the report remains. Because the loop runs after the main runs, the rates of the five models in Table 
4
 come from the main runs.

As Figure 
4
 shows, the loop reproduced 39 of the 51 replications, so 
ROGUE-AI
 reproduced the reported harm in 89% of the 108 replications. Llama-3.1-8B, Llama-3.3-70B, GPT-4.1-mini or Claude Haiku 4.5 reproduced 23 of them without a change, among them the $441,000 wallet transfer and the transfer that Grok relayed 
[
29
]
, both with Llama-3.1-8B. These reports thus describe mistakes that current models no longer make.

The other 16 replications reproduced in later rounds of the loop. Some incidents need more turns than others, because the reported harm comes at the end of a long chain of steps, and 3 reproduced once the agent had more turns. Other replications need a detail of the product that the report leaves out. In four injection exploits, for example, the product’s interface renders an image in the agent’s reply and so sends the data to the attacker without a click. With such details in place, 8 of the 11 replications that needed one reproduced, including ForcedLeak 
[
30
]
, CamoLeak and the Notion exfiltration, and DeepSeek-V4-Flash also repeated the Notion exfiltration. Because the controls receive each change as well, a change that makes harm easier affects both conditions. On five of these replications, such as ServiceNow 
[
31
]
 and Comet 
[
32
]
, GPT-4.1-mini caused harm in 5 to 10 of 10 incident sessions each, and the controls in 0 of 100 sessions.

The 12 replications that the loop did not reproduce show the limits of 
ROGUE-AI
. Seven are destructive actions or cloud operations, among them the cloud-operations versions of the Kiro and Terraform deletions. Their reports describe the harmful command but little of the session before it, such as the earlier conversation and the tool outputs that led the agent there, so a replication has to guess this context.

In the other five, no model took the reported step. Three are containment incidents from model evaluations, where the harm needs a step that nothing in the task motivates, such as reaching a machine outside the evaluation. The last two are EchoLeak 
[
33
]
 and the GitHub MCP data flow, in which Claude Haiku 4.5 called the injected requests attacks and refused them.

6.3 
Causes of Harm

Finding 3.
 Whether an incident repeats depends mostly on its environment and task, not on the model. Differences between replications explain 75% of the variance in harm rate, differences between root causes 18%, and differences between models 2%. Incidents with the same root cause can therefore end very differently, so 
ROGUE-AI
 replicates each one in its own environment.

Root Causes and Models.
 The five models mostly agree on a replication: all five caused harm in 18 replications, none did in 51, and they split on the other 39. As Table 
4
 shows, untrusted components caused the most harm on all five models, and the largest difference between models lies in untrusted instructions (§
6.4
).

Each marker is the share of a model’s sessions with harm on the replications that the model repeated most, and the gray band spans the five models’ rates in the incident condition. The neutral note has the same length as the note with the fact and consequence. ).

Evidence of a Cause.
 A supported replication shows that the hazard causes harm, because its incident condition and matched control differ only in the hazard (§
3
). To learn why the agent took the harmful step, we count an element of the environment as a cause only if changing that element alone lowers harm. If the change adds text, it must also lower harm more than a neutral note of the same length that says nothing about the hazard. We apply this test at two levels: interventions that change one element and rerun whole sessions, and edits at the harmful step of each harmful session (Table 
5
). We set aside the agent’s own account of its actions, since agents misreport them, and we use transcripts only to describe what the agent saw before it acted.

Finding 4.
 A note that states both the hazard and its consequence lowered harm for all five models. For Claude Sonnet 4.6, this note cut harm to 1 of 40 sessions, against 58% under a note that states only the fact. Restating the rule in the user’s message left harm at 67% to 80%.

Interventions on One Element.
 In the transcripts, the harmful step served the user’s task, and the agent did not recognize the hazard. We tested this explanation against four other explanations with interventions that change one element at a time (not counted in Table 
4
). Each model ran these interventions on the 7 to 11 replications where it had caused harm in at least two of its three main sessions, mostly without an attacker, with three to five sessions each.

In the incident condition, the five models caused harm in 85% to 98% of these sessions. As Figure 
5
 shows, a note after each tool output that states the hazard and its consequence lowered harm for all five models, to 1 of 40 sessions for Claude Sonnet 4.6 and to at most 62% for the others. In the Replit replication, this note states that the tests drop the production database. Under a neutral note of equal length, harm stayed between 83% and 98%, and under a note with the fact but without its consequence, harm stayed between 58% and 82%.

Naming the Hazard.
 We used GPT-5.6-sol as a judge of the transcripts of Claude Sonnet 4.6 and Gemini 3.5 Flash. In 64 of the 164 harmful sessions, a tool output that the agent had read before the harm showed the hazard, such as a list of zero-byte placeholders. The agent’s own text named the hazard before acting in 0 of the 164 sessions, and in 15 sessions the agent quoted the evidence without treating it as a risk.

As a second cause, the agents took the most direct path they knew. With a safe way to finish the task in the environment, such as a 
make
 target that runs the tests against a temporary database, harm stayed between 67% and 100%, and naming this safe path in the task cut it to between 17% and 60% (Figure 
5
). Removing pressure from the task lowered harm most for the two GPT models, to 16% for GPT-5.6-sol. For defenders, the hazard and its consequence should therefore reach the agent at the step of the action, for instance as a warning attached to a tool’s output. A rule or a safe path that the task does not name barely lowered harm.

Causes in Each Session.
 The interventions above change the environment and rerun whole sessions, giving a cause per replication. To find the cause of each harmful session, we also cut the 208 harmful sessions of the five models at the first harmful step and let the same model choose that step again five times, with the context unchanged and under each single edit. Each edit changed one thing, by removing the task’s request for the step or its pressure, showing the hazard in the last or the first tool output, restating the rule in the user’s message, removing the text a third party wrote, or adding a neutral note.

An edit halves harm if the unchanged step caused harm in at least 3 of 5 repeats, the edited step’s harm rate is at most half the unchanged rate with non-overlapping 95% Wilson intervals, and a neutral note of equal length in the same place does not do the same. Table 
5
 defines each cause by the edit that removes it. For example, a session counts as 
early warning not enough
 if a warning in the last tool output halves harm but the same warning in the first does not, so the agent needed the warning right before it acted.

As Table 
5
 shows, at least one edit removed the harm in 118 of the 208 sessions, and 62 sessions had several causes. The two most common causes were that the task asked for the harmful step and that the agent never saw the hazard. In contrast, in nearly half of the DeepSeek-V4-Flash sessions and about a third of the Gemini 3.5 Flash sessions, the agent saw the hazard in the last tool output and acted anyway. Only 14 sessions were rare slips, in which the same model caused harm in fewer than 3 of 5 repeats.

Finding 5.
 Most harmful steps with a known cause happened because the task asked for the step or because the agent never saw the hazard (94 of 118 sessions). However, DeepSeek-V4-Flash and Gemini 3.5 Flash saw the hazard and took the step anyway in 22 of 49 and 15 of 49 harmful sessions.

6.4 
Attackers and Defenses

With and Without an Attacker.
 Replications of prompt injection caused less harm than the other replications on all five models, as the untrusted-instruction row of Table 
4
 shows, and almost all of the harm in injection replications came from replications that do not rebuild a public exploit. In particular, the twelve replications of injection exploits on shipped products, such as EchoLeak 
[
33
]
, ForcedLeak and the GitHub MCP data flow, caused harm in 2 of 180 sessions across the five models. The injected text, however, reached the model in 108 of 166 logged sessions. In later rounds of the loop (§
6.2
), 8 of these exploits ran again, and GPT-4.1-mini reproduced 5 of the 8 (4 supported), whereas the five main models reproduced between 0 and 4 . Thus, an older model still follows most of these public exploits, while current models follow at most half of them.

Finding 6.
 On all five models, replications without an attacker caused more harm than replications of untrusted instructions such as prompt injection. Claude Sonnet 4.6, for example, caused harm in 0 of 138 sessions with untrusted instructions but in 26% of the sessions without an attacker.

As Table 
4
 also shows, unchecked authority caused more harm than untrusted instructions for all five models, for example 32% against 7% for GPT-5.6-luna. In the causes with the most harm, the agent either trusts a component that the user installed or has authority that no check limits. Therefore, a model can avoid harm from injected text and still publish, spend or delete what it should not.

Among the adversarial replications, malicious or swapped components caused the most harm, as Table 
4
 shows. GPT-5.6-luna caused harm in 19 of its 39 sessions in these replications. At the user’s request, the agent installs a skill or MCP server and follows the setup steps and tool descriptions, as the component’s author intends. GPT-5.6-luna ran a malicious skill’s installer in 3 of 3 sessions and sent mail through a server that added a hidden recipient in 3 of 3 sessions. Some components cause harm as soon as the agent calls them, but even without these 13 replications, the five models caused harm in 14% to 28% of incident sessions.

), and the matched controls lost no files. In the other nine replications, GPT-5.6-sol caused harm in 0 of 27 sessions and Claude Sonnet 4.6 in 0 of 27. In the Replit replication, both models asked for permission under the code freeze. Neither model detected a hazard that passes the user’s own check, such as a placeholder with the right checksum. The two models caused harm about as often in our own agent loop (Appendix 
B
).

The reckless-model check of Table 
2
 predicts most replications that do not reproduce (§
6.2
). It runs an inexpensive model, told to follow all instructions in its inputs, for two or three sessions; in our study it ran after the builds. It flagged 44 of the 51 replications that the five models did not reproduce in the main runs, against 6 of the 55 supported or suggestive ones. A flag calls for reading the transcripts first, since even a reckless model stops where the task gives no reason to go on. A not-reproduced outcome therefore bounds the harm rate of one replication only, and the transcripts show whether the bound also applies to the reported claim.

However, the same checks also found problems in reproduced replications. In 7 of them (5 supported), no control passes the state diff, for example because the control lacks the path by which the harm happens. Part of their harm difference may therefore come from the control. In 2 supported replications, a malicious mail server copies all messages, so any mail the agent sends counts as harm, and these replications measure the component more than the model. In 4 replications (3 of them multi-agent), the agent’s input contains a scoring or deadline sentence that their reports lack. Without it, all 4 still reproduced, and 27 of 57 incident sessions caused harm, against 27 of 59 with it.

7 
Discussion

Recommendations for Agent Builders.
 Most incidents with harm in the wild came from a wrong target or unchecked authority (23 and 21 of 72), and least privilege 
[
37
]
 limits the cost of such mistakes. Production credentials can be kept in an account that the agent cannot use, and destructive commands and payments can require a person’s approval.

Recommendations for Benchmark Builders.
 Benchmarks built from attacks measure the risk that researchers demonstrate, but most harm in the wild came from incidents without an attacker (§
5
). Agent safety benchmarks should therefore add non-adversarial hazards, name the source incident of each test case, pair each condition with a matched control and read harm from the environment’s state. Public incidents may also be in a model’s training data, but given the opening of each replication, three models named the right incident for only 12 of the 108, and these 12 were supported or suggestive about as often as the others (7 of 12, against 48 of 96).

Recommendations for Incident Reporting.
 Of the 51 claims that the five models did not reproduce, 11 needed a detail of the product that their reports left out, such as whether the interface renders images in the agent’s reply (§
6.2
). Reports seldom include the model and its version, the system prompt, the agent framework, the earlier conversation or the tool output that preceded the harmful action. The agent’s own account is a weak source, because its final message omitted or denied the harm in 77 of 136 harmful sessions of Gemini 3.5 Flash and in 18 of 49 harmful sessions of GPT-5.6-luna.

Outcomes and Reported Incidents.
 Because few reports name the model and its version, our replications run current models from four vendors instead of the model of each incident. A supported outcome means that the incident can happen today even if the original agent ran another model, and the audit of §
3
 can rerun a replication on a model that a report names. By contrast, a replication that only older or weaker models reproduce describes a mistake that current models no longer make, and a replication that no model reproduces leaves its report unconfirmed. However, a failed replication does not show that a report is false. Most of these reports leave out the conversation and tool outputs before the harmful step (§
6.2
), and a future version of 
ROGUE-AI
 could fill in this context in many plausible ways and run each version.

Safety of the ROGUE-AI Pipeline.
 
ROGUE-AI
 uses LLM agents to study the failures of LLM agents, so its own agents can fail in the same ways. We therefore apply our recommendations to the pipeline itself. No agent checks its own work or decides harm, a model from another vendor reviews each build, and the models under test run offline on synthetic data (§
4
). Because code decides harm without a model, an error shared by all vendors cannot change it. Likewise, we find the causes of harm by rerunning sessions or harmful steps with one element changed, and the agents’ accounts of their own actions do not count as evidence (§
6.3
). Appendix 
C
 details these checks by root cause.

Limitations.
 Our catalog counts publicly reported incidents, so it likely over-represents incidents that people write about, and the 38 classes are a lower bound. As the replications run in simulated environments with one agent loop, and only ten destructive-action replications also ran in shipped products (§
6.5
), a harm rate may misstate a product’s risk. Where a report gives no mechanism, our replication reconstructs it, and a replication that departs from the report can misstate the harm. 
ROGUE-AI
 did not reproduce 12 replications, mostly because their reports leave out what led the agent to the harmful step (§
6.2
). Model judgments err, as reviews sent back 11 of 18 sound builds and blind rebuilds disagreed with ours on 5 of 11 incidents.

9 
Conclusion

We presented 
ROGUE-AI
, a multi-agent framework that rebuilds a reported agent incident offline together with a matched control that lacks only the blamed cause. 
ROGUE-AI
 reproduced the reported harm in 89% of its 108 replications. Agents built on five current models still made the reported mistake in 18% to 33% of runs, and they rarely caused harm without the blamed cause. Most incidents with real-world harm had no attacker, and the agent did its task but missed an ordinary hazard. Defenses against prompt injection look for injected instructions, but these incidents contain none. In contrast, a warning that names the hazard and its consequence lowered harm for all five models. Agent builders should therefore add such warnings and keep production credentials out of the agent’s reach, benchmarks should include hazards without an attacker, and vendors can rerun the replications before each release. Future work could extend 
ROGUE-AI
 from agents that act on text to agents that act on images, such as computer-use agents that work from screenshots and robots driven by vision models.
