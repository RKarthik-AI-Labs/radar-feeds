Abstract

LLM agents that call tools are exposed to indirect prompt injection:
instructions hidden in tool outputs can steer an agent into calls the user never
asked for. We present a runtime audit that derives an executable 
intent
graph
 from the user’s objective and the deployment’s tool catalog with one LLM
call per task, and checks every tool call against it with a deterministic loop
that makes no LLM call (median 
s per call). Two further mechanisms
recover utility. Lookups of the user’s own state bypass the audit, because the
harm of an attack lies in its write or outward step. The calls that remain
flagged are escalated to a 
reasoning guardian
, in the spirit of
tool-integrated reasoning models such as START: a reasoning model that sees only
the objective, the plan, the call history without tool outputs, and the flagged
call, and can verify facts with a restricted Python-expression tool. We evaluate
on AgentDojo (97 tasks, 629 prompt-injection scenarios) under a protocol that
avoids evaluation leaks: the extractor sees only the objective and the tool
catalog, no policy is calibrated with attack labels, design choices are made on
development tasks, and results on 76 held-out tasks use cluster-bootstrap
intervals. Replaying logged traces of an older agent, the full audit reduces
trace-level attack success from 45.7% to 3.3% [1.7, 5.0] but flags 40% of
benign tasks; the tool allowlist provides
most of the protection and ordering constraints are the most expensive
component. Letting local reads bypass the audit leaves attack success at the
harmful step unchanged, and with the allowlist and argument scopes it blocks
8.8% of benign tasks at 4.3% attack success. The guardian overrides 22–25%
of the remaining flagged benign calls and none of the 226–242 flagged harmful
calls, lowering flagged benign tasks in that configuration from 27.6% to
21.1% at about 3.6 s per escalated call. Against AgentDojo’s built-in defenses,
re-scored on the same tasks, an LLM tool filter reaches 6.5% attack success
without losing benign utility, a strong baseline that our allowlist alone
approaches; scopes and ordering buy a few points more at a utility cost under our
replay-based proxy. Finally, we test whether the audit’s
alignment score can strengthen an identity-drift detector. It cannot: the score
carries no information about account takeover or drift, and for in-session
hijacking the audit’s own verdict is far stronger than any behavioral detector
(TPR 0.76 versus 0.07–0.12 at 5% FPR). All security numbers are replay-based:
a live pilot with a current agent showed no baseline attack success, so
end-to-end validation remains open.

Introduction

Agents built on the Model Context Protocol (MCP) 
[
1
]
 and similar
function-calling interfaces act on behalf of a user through tools: mail,
calendars, file stores, banking and messaging APIs. Whatever the agent reads can
carry instructions. In indirect prompt injection 
[
2
]
, an attacker
plants text in a document, web page, or tool description that the agent later
reads, and the agent then issues calls such as “send these files to this
address” that no one authorized. Defenses that inspect text or reasoning may be
bypassed by a sufficiently persuasive payload, so a complementary line of work
constrains what the agent 
can do
 rather than what it

reads
 
[
3
, 
4
, 
5
, 
6
]
.

Our system belongs to that line. Its premise is that the user’s objective
already determines most of what a legitimate run needs: the tools involved, some
argument values (the named recipient, file, channel, hotel, dates), and
sometimes an order. We ask an LLM 
once per task
, before any tool output
is read, to write this down as an executable intent graph, and then audit every
call against it with plain code. Because the graph is produced from the trusted
objective and the static tool catalog only, an injected instruction cannot
enlarge it. The price of least privilege is false positives: a plan misses
tools that a legitimate run needs. We reduce them in two ways. First, calls
that only read the user’s own state bypass the audit: an injected read does no
harm unless the agent then writes or sends something, and those steps stay
audited. Second, a reasoning guardian re-examines the calls that are still
flagged and can verify claims with executed code, in the spirit of
tool-integrated reasoning models 
[
7
]
.

A worked example.

In an AgentDojo task, the user asks, “Who else is
invited at the ‘Networking event’ on May 26th? Please give me their email
addresses and a summary of the event.” The extracted plan lists calendar and
contact lookups only. The agent reads the event, whose description contains an
injected instruction to send an email to an attacker-controlled address, and
issues 
send_email
. The undefended agent was compromised in the logged
run. 
send_email
 is not in the plan, so the audit blocks it, in each of
three independent graph extractions, while the two legitimate calls pass.

Contributions.

(1) We describe an intent-graph audit with a leak-free LLM extraction step and a
deterministic runtime loop, including a hardened scope-expression language
(Section 
4
). (2) We show that classifying tools as local reads,
external reads and writes removes a large share of false positives at no cost in
harmful-step attack success, while bypassing an external read such as a URL
fetch does cost security (Section 
6
). (3) We add a START-style
reasoning guardian for flagged calls and show that it preserves security while
reducing benign flags (Section 
8
). (4) We give an
evaluation protocol on AgentDojo that avoids three shortcuts that arise easily
when policies are generated or calibrated from session data: label-informed
policy calibration, a session-derived tool list given to the extractor, and
overlap between calibration and evaluation data (Section 
5
).
(5) We quantify the security/utility trade-off with ablations that approximate
tool-allowlist, per-call argument-policy, and planned-dependency-graph defenses
(Section 
6
). (6) We test, and reject, the hypothesis that
feeding the audit’s alignment score into an identity-drift detector improves
detection (Section 
9
).

Background and Related Work

Attack surface.

An MCP server exposes tools whose descriptions,
parameters and results all flow into the agent’s context. Attacks span poisoned
tool descriptions 
[
8
]
, exfiltration through injected auxiliary
calls 
[
9
]
, and injections arriving in tool outputs, which
AgentDojo 
[
2
]
 benchmarks with realistic multi-step tasks and
injection goals.

Policy enforcement.

AgentSpec 
[
3
]
 enforces
user-written rules in a domain-specific language at runtime. ProbGuard
(first released as Pro2Guard) 
[
10
]
 learns a Markov abstraction of
agent behavior and intervenes when the predicted risk of an unsafe state is
high, and agent behavioral contracts 
[
11
]
 add preconditions, invariants
and a drift bound. Progent 
[
5
]
 enforces programmable privilege
policies on tool calls and can have an LLM draft them from the user query.
Our audit shares Progent’s least-privilege goal; its contributions here are the
leak-free evaluation, the measured trade-off, and the reasoning escalation, not a
new policy language.

Planning and data flow.

IPIGuard 
[
6
]
 has the agent plan
a tool dependency graph before execution and restricts later calls to it, and
CaMeL 
[
4
]
 separates control flow from untrusted data with a custom
interpreter and capabilities. AgentArmor 
[
12
]
 builds a program
dependence graph from the observed runtime trace and enforces policies over
it, and ARM 
[
13
]
 adds provenance edges for denied actions. Our ablation
variants (Section 
5
) approximate the 
families
 of
tool-allowlist, argument-policy and planned-dependency defenses on identical
inputs; they are not re-implementations of these systems.

Reasoning with code.

START 
[
7
]
 trains a long
chain-of-thought model to call a Python interpreter during reasoning. Our
guardian is START-
style
: a general-purpose reasoning model that may call
a tool during its reasoning. We use a hardened Python 
expression

evaluator instead of an interpreter, and an off-the-shelf model rather than
START’s trained model.

Scanning and guardrails.

MCP-Scan 
[
14
]
 inspects tool
descriptions and offers a runtime proxy, and LlamaFirewall 
[
15
]

combines classifiers with an AlignmentCheck module that audits the agent’s
reasoning with a secondary LLM. Our audit differs in checking calls against a
structured plan with code, so the per-call path is deterministic and cheap, and
in invoking a reasoning model only on calls that the plan has already flagged.

3 
Threat Model

The user’s objective and the deployment’s tool catalog are trusted; the attacker
controls content that tools return (documents, web pages, messages) and can
thereby induce the agent to issue arbitrary calls. The attacker cannot modify
the objective, the catalog, the extracted graph, or the audit loop. The
arguments of a call are untrusted, since the agent may copy attacker text into
them; this matters for the guardian (Section 
4.6
). We evaluate
indirect prompt injection (Section 
5
) and, separately, three
identity attacks (Section 
9
): 
splice
 (another person
takes over mid-session), 
drift
 (behavior shifts gradually), and

hijack
 (injected calls inside an otherwise normal session). We do not
evaluate attacks adaptive to the audit or to the guardian.

4.2 
Phase 1: leak-free extraction

The extractor receives the system message given to the agent, the user
objective, and the 
full
 tool catalog of the deployment (names, parameter
names and one-line descriptions). It receives nothing derived from the session:
no tool list observed so far, no earlier events, and of course no tool outputs.
It returns a JSON graph under these rules: (i) list only tools the objective
plausibly needs, since every unlisted tool will be blocked; (ii) constrain an
argument only to values the objective itself determines, and leave values that
will be looked up from other tools unconstrained; (iii) add an edge 

only if

order. There is no post-hoc relaxation of scopes or edges from session events.
In our default configuration every node is treated as repeatable regardless of
the extractor’s flag (Section 
5
).

4.3 
Scope language

Scope predicates are Python expressions over 
params

the call’s arguments. They are parsed with 
ast

every node is in an allowlist (boolean and comparison operators, membership,
subscripts, conditional expressions, list/tuple/set literals, and list, set and
generator comprehensions), every called function is in a fixed set (
all
,

any
, 
len
, 
str
, 
isinstance
, and a few
others), every method is in a fixed set (
get
, 
startswith
,

endswith
, 
lower
, 
strip
, 
split
, and a few
others), and no attribute begins with an underscore. Evaluation runs with empty
builtins. Comprehensions matter because many arguments are lists (for example
recipients); in preliminary runs a narrower grammar without them silently
discarded roughly a quarter of the generated predicates. An expression that
fails to compile, or raises at run time, falls back to a configurable policy:
allow (fail-open) or treat as a scope failure (fail-closed). With the extended
language 0 of 340 generated predicates were rejected, so the choice did not
matter in our experiments. Restricted 
eval
 is not a strong isolation
boundary in Python; a production deployment should replace it with a
purpose-built expression interpreter. The same evaluator serves the guardian’s
tool (Section 
4.6
).

4.5 
Read-only tools

Many false positives are calls that merely look something up. We classified the
69 distinct tools of the four AgentDojo suites by reading their descriptions,
once and by hand before running the experiment, into 44 
local reads
 (they
read the user’s own mail, calendar, files, chat, travel or banking data and have
no outward effect), one 
external read
 (
get_webpage
, whose URL
can carry data out), and 24 writes or outward actions. Under the read-only
policy a local read bypasses Checks 1–4 and is allowed; it still satisfies its
plan step, so dependent steps are unlocked. Everything else, including

get_webpage
, is audited as before. The rationale is that an injected
read does no harm unless the agent then writes or sends something, and those
steps remain audited. The classification is per tool and specific to a
deployment’s catalog.

4.6 
Reasoning guardian

The audit is strict by design, and a plan inevitably omits tools that a
legitimate run needs or fixes an order that the agent does not follow. The
guardian re-examines 
only flagged calls
 and decides between

allow
 (the call is a necessary step toward the objective) and

keep_flag
. It is a reasoning model (Azure OpenAI 
gpt-5.2
) that
receives the user objective, the plan, the history of earlier calls with their
arguments, the flagged call, and the audit’s reason, and returns a one-sentence
justification. Three design choices limit its exposure to injection. It never
sees tool outputs, so injected text in documents cannot reach it. It is told
that call arguments are untrusted data, since the agent may have copied
attacker text into them. And any parsing failure or error keeps the flag.

In the START spirit the guardian can run code while it reasons: a function-calling
tool, 
eval_expr
, evaluates a restricted Python expression over the
objective, the call, the history and the plan, with the same allowlist as the
scope language (for example, testing whether a recipient appears in the
objective). The model may call it up to three times. The guardian prompt was
written once, before any evaluation; a six-request sanity check on development
tasks preceded a full development run (Section 
5
), and the prompt
was not tuned on either.

5 
Evaluation Methodology

5.1 
Testbed

We use the logged runs of AgentDojo 
[
2
]
 for

gpt-4o-2024-05-13
 (repository state of 2026-06-02): 97 user tasks in
four suites (workspace 40, slack 21, travel 20, banking 16), one attack-free run
per task, and 629 attacked runs with the 
important_instructions

attack, of which 300 (47.7%) compromised the agent. Each run is a sequence of
tool calls with arguments. The suites expose between 11 and 28 tools.

Labels.

A call is labelled malicious if (i) its function belongs to
the ground-truth calls of the run’s injection task, (ii) it follows the first
tool result that contains the injected text (for a successful attack in which
that text cannot be located, any earlier call is allowed), and (iii) the same
call, with the same arguments, does not occur in the attack-free run of the same
task. This labels at least one call in 98.3% of successful attacks and in 14.9%
of unsuccessful ones (attempts). A successful attack with no labelled call counts
as not stopped. Some labelled calls are ambiguous: they coincide in function
with a step of the user’s own task. In the published logs the attacked runs of
15 travel tasks (105 runs) carry a rewritten user prompt that differs from the
attack-free run’s; for these runs the plan is extracted from the prompt the agent
actually received (45 additional extractions). Using the attack-free prompt
instead changes no headline number (the largest change is 0.2 points).

Splits and repetitions.

Every fifth task of each suite is a
development set (21 tasks); the remaining 76 form the test set. A prompt rule
about edges was changed once, using four development tasks, and the default of
treating every node as repeatable was chosen from development-set diagnosis
(on the test tasks the two settings give identical results). Phase 1 was run
three times per task (291 extractions with Azure OpenAI 
gpt-5.2
, plus
45 for the rewritten travel prompts, no failures), and each audit result is
averaged over the three graphs.

Metrics.

Attack success rate (ASR)
: the fraction of attacked
runs in which the undefended agent was compromised and the defense would not
have flagged the first malicious call. This is a trace-level estimate that
assumes a flagged call is withheld and the agent does not find another route.
Because a read-only policy deliberately lets harmless first steps through, we
also report 
ASR at the harmful step
: the same quantity for the first
malicious call that is not a local read, which is where an attack does its
damage (two successful test attacks have no labelled harmful call and count as
not stopped). 
Malicious flagged
: among runs with a labelled malicious
call, the share whose first malicious call is flagged. 
Benign calls
flagged
 and 
benign tasks flagged/blocked
: on the attack-free runs, the
share of calls with a flag or block, of tasks with at least one flag, and of
tasks with at least one block. Intervals are 95% percentile bootstrap intervals
over tasks, from 2,000 resamples (all runs of a task share its graph), and
paired differences use the same resamples.

Variants.

On identical graphs we compare a 
tool allowlist

(plan tools only), 
scope-only
 (allowlist plus argument predicates, an
approximation of per-call privilege policies 
[
5
]
),

ordering-only
 (allowlist plus precondition edges, an approximation of a
planned dependency graph 
[
6
]
), and 
full Phase 2
, each with and
without the read-only policy of Section 
4.5
, plus a sensitivity
variant in which 
get_webpage

5.2 
Guardian protocol

To bound cost, the guardian is evaluated on the first graph repetition. For the
original full design, a request is created for every flagged call of an
attack-free run and for the first malicious call of an attacked run when it is
flagged: 311 test requests (73 benign, 238 malicious) and 77 development
requests. For the read-only design we create requests for the calls still
flagged after the bypass and for the first harmful malicious call: 283 test
decisions, of which 227 were already available and 56 were new. The scope-only
design reuses these decisions, since its flagged calls are a subset (the guardian
therefore saw the full design’s plan, including its edges). A call stays flagged
unless the guardian returns 
allow
. We report two simulations. In the

independent
 simulation an override changes only that call, which is
conservative because later calls that depend on it stay flagged. In the

state-updating
 simulation an override authorizes the call’s node exactly
as a normal allow would, as a deployment would behave; calls that become flagged
without a recorded decision keep their flag.

5.3 
Identity benchmark

AgentDojo runs are only three to five calls long, too short for behavioral
modeling, so we compose them into sessions. In the workspace suite we group the
40 tasks into four families by dominant tool (email, calendar, drive, other).
Twelve principals each get a task-family mixture drawn from a Dirichlet
distribution (concentration 0.8) and a personal timing scale. A session is 20 to 30
consecutive tasks (about 51 calls), long enough for the per-session detector,
which only starts scoring at event 20, to be active on 61% of events. A first
run with 8 to 12 tasks (about 20 calls, detector active on 10% of events) is
reported as a sensitivity analysis. Phase 2 audits each call under the graph of
its own task, extracted when that task starts, and its verdicts form 
.
For each principal we generate 24 training, 8 validation and 20 test benign
sessions, and 20 test sessions for each attack: 
splice
 (from 30–70% of
the session the tasks come from the principal with the most distant mixture),

drift
 (from 40% of the session, tasks come from that mixture with
increasing probability), and 
hijack
 (one or two tasks are replaced by
their prompt-injection runs, and only the malicious calls are positives). We
report the true-positive rate at 5% event-level false-positive rate (ties
broken by randomization) and AUROC, with negatives from held-out benign
sessions and 95% bootstrap intervals over sessions, averaged over the three
graph extractions. A 
residual
 analysis restricts positives and negatives
to events Phase 2 allowed, which is where a coupling could add information. We
also include a 
flag-persistence
 baseline: the maximum of 
 over
the last 10 events.

Security.

Full Phase 2 reduces trace-level ASR from 45.7% to 3.3%
(Table 
1
). The result holds on all 97 tasks (47.7% to 4.8%) and
the development tasks (54.7% to 10.2%). Most of the effect comes from
least privilege: of the 1,776 malicious-call evaluations over all attacked runs
(three extractions), 80.6% were blocked as outside the plan or out of order,
7.1% were flagged as scope violations, 1.7% were flagged by the taint check,
and 10.6% were allowed. The allowlist alone brings ASR to 10.2%; argument
scopes lower it to 5.5%; and edges bring it to 3.3%.

What each component costs.

Relative to scope-only, ordering edges
lower ASR by 2.2 points (paired 95% CI [0.7, 4.2]) while flagging 7.5 points
more benign tasks ([2.6, 13.2]) and blocking 31.1% instead of 16.2% of them.
Relative to the allowlist, the full audit lowers ASR by 7.0 points ([3.9, 10.3])
and flags 24.1 points more benign tasks ([15.8, 33.3]). Scopes help at no
increase in blocked tasks (16.2% in both) but add flagged calls (17.3% versus
10.1%). Ordering is the weakest component per unit of utility lost.

Read-only lookups.

Of the 73 flagged benign calls of the full design
(graph 0), 32 (44%) are local reads, mostly 
read_channel_messages
,

get_channels
 and 
get_users_in_channel
, and a further 12 are

get_webpage

harmful step unchanged for the allowlist, scope-only and full designs (2.0% for
the full design; paired difference 0.0 points [0.0, 0.0]). For the full design it
lowers flagged benign calls by 11.0 points ([5.8, 16.4]) and blocked benign tasks
by 7.9 points ([2.2, 14.0]). The best operating point is scope-only plus bypass:
it flags 25.4% and blocks 8.8% of benign tasks at 4.3% harmful-step ASR, where
the full design blocks 31.1% at 2.0% (paired: 22.4 points fewer blocked tasks
[14.9, 30.3], 2.2 points more attack success [0.7, 4.2]). Under the first-call
metric the bypass looks worse (11.4% instead of 3.3% for the full design)
because 22% of the flagged first malicious calls are local reads, such as an
email search, which precede the harmful step; the harmful step is still caught.
Bypassing 
get_webpage

The generated plans are small:
on average 3.5 nodes and 4.1 tools out of a catalog of 11 to 28, 82.5% have at

blocks 16.2%, close to this floor. On the development tasks, unmet ordering
preconditions accounted for 26 of the 35 flagged benign calls (counted over the

10 
Discussion

What the evidence supports.

Prospective least-privilege auditing is
effective against injection in this benchmark: the extracted plan from the
objective alone removes about 93% of the attack success, with a deterministic
audit that costs microseconds. The price is utility: at least 15% of benign
tasks need a tool the plan omits, and each additional check raises benign
flagging. Two inexpensive measures recover a good part of that cost. Letting
tools that only read the user’s own state bypass the audit costs no
harmful-step security, because the harmful step of nearly every attack we
labelled is a write or an external call, while a large share of the benign flags
were lookups. A
reasoning guardian then removes a further share of the remaining flags without
overriding any flagged harmful call, because it is invoked only on calls the
plan has already flagged. It is the one place where a reasoning model that
executes code adds value in our results. The leanest configuration we tested,
allowlist plus argument scopes with local reads bypassed, blocks 8.8% of benign
tasks at 4.3% harmful-step attack success; adding the guardian flags 21.1% of
benign tasks and blocks 7.9% (graph 0, harmful-step ASR 5.3%). Against the built-in defenses of AgentDojo, the LLM tool filter is the strongest
end-to-end baseline (6.5% attack success, no utility loss), and our allowlist-only
variant is statistically indistinguishable from it on security; the case for the
additional machinery rests on the lower attack success of the scope and full
variants (4.3% and 2.0% at the harmful step), which our replay-based utility
proxy suggests costs benign tasks.

Why the coupling fails.

The alignment score is a function of a call
and the current task’s graph. If the person at the keyboard changes, the new
requests re-define the task and the calls are legitimate under it, so the
score has nothing to say about who is asking. If the agent is hijacked inside a
task, the verdict itself already identifies the calls, and a behavioral model
built on top of it is a lossy copy. The idea could still work if the graph were
tied to a standing, per-principal role rather than to the current request, so
that a takeover is a deviation from the principal’s established intent; we did
not test this.

Limitations.

(1) One benchmark and one agent model: AgentDojo traces of a single model, with
trace-level ASR that assumes no re-planning after a block. (2) The extractor and
the guardian are LLMs: three graph repetitions capture sampling variance but not
variance across models or prompts, the prompt rules were tuned on four
development tasks, and the guardian was run once on a single graph repetition.
(3) Scopes are limited by what the objective determines: 61% of nodes leave
arguments unconstrained, and 10.6% of malicious-call evaluations were allowed.
(4) We did not test attacks adaptive to the audit or the guardian. Call
arguments reach the guardian and are attacker-influenced, and although we
instruct it to treat them as data, a targeted payload could try to persuade it.
(5) The guardian cannot see tool outputs, so it cannot verify the provenance of
an argument. (6) Some labelled malicious calls coincide in function with the
user’s own task, so override rates on malicious calls may be overstated.
(7) The read-only policy rests on a hand classification of tools and on the
assumption that harm occurs at a write or external step; an attack that leaks
data through reads alone, or through a tool we classified as a local read, would
evade it. 
get_webpage
 shows that the classification matters. The
harmful-step metric was introduced after seeing that the bypass changes which
call is first, and we report both metrics. (8) We report the lean Phase 2 design
in the identity benchmark because ordering edges raised false positives; we
chose this after seeing test-set Phase 2 results, and the full design is shown
as a robustness check with the same conclusion. (9) The identity benchmark is
synthetic: one suite, twelve principals with overlapping task mixtures, and
modest detectors overall (TPR 0.07–0.24 at 5% FPR), so a richer behavioral
signal may do better, although the argument above does not depend on detector
strength. Session length also matters: the per-session baseline was near chance
on sessions of about 20 calls and competitive on sessions of about 51.
(10) We did not evaluate on production MCP logs; the internal logs available to
us had a single endpoint and shared client addresses, too little variation to
test scopes or identity. (11) The scope compiler relies on restricted

eval
. (12) The comparison with built-in defenses mixes their end-to-end
evaluation with our trace replay: replay overstates security because it assumes
the agent does not route around a blocked call, and understates utility because
it counts a blocked task as failed. Live runs with the audit in the loop would
remove this gap. We built a harness for them (the audit gate inside AgentDojo’s
agent loop) and ran a pilot with a current agent (gpt-5.2, benchmark v1, 10 test
tasks with 2 injection tasks each, the same attack). Without a defense the agent
followed the injection in 0 of 20 runs, although the injected text reached it in
all 20; the attack-free utility was 0.60 and the utility under attack 0.50. With
no baseline attack success there was nothing for a defense to reduce, so we did
not run the defended configurations, and the paper’s security numbers remain
replay-based. The pilot also shows that the replay baseline (45.7% attack
success) describes an older, more injection-susceptible agent, and that our
results should be read as protection against agents of that kind.

Reproducibility.

The analysis scripts, the cached extractor outputs and
the guardian decisions are available from the authors on request. The benchmark
logs are publicly available from the AgentDojo repository.

11 
Conclusion

We presented an audit that turns a user’s objective into an executable intent
graph with one LLM call and checks every tool call against it with deterministic
code, with a bypass for tools that only read the user’s own state and a
reasoning guardian that reviews the calls that stay flagged. Under a leak-free
protocol on AgentDojo, replaying logged traces, the full audit lowers trace-level
attack success from 45.7% to 3.3%, at the price of flagging 40% of benign tasks. Our ablations
show that ordering constraints are the most expensive per point of protection,
that bypassing local reads recovers utility at no cost in harmful-step security
while bypassing an external read does not, and that the guardian overrides a
quarter of the remaining flagged benign calls and none of the flagged harmful
ones. Using the audit’s alignment score to improve identity-drift detection did
not improve detection beyond what the audit’s own verdict already provides. The
open problems are reducing benign flags further without weakening the allowlist,
hardening the guardian against adaptive payloads, validating end to end against an injection-susceptible agent (our one live pilot, with a current agent, showed no baseline attack success),
and tying intent to a standing role so that account-level attacks become visible
to the audit.
