Abstract

Effective computer-use agents (CUAs) should seamlessly combine visual GUI
interaction with code and terminal execution within a single policy. We present
Mage-VL-Cowork, a 4B hybrid CUA trained from a general multimodally aligned
checkpoint through an end-to-end, progressive five-stage curriculum across
midtraining, SFT, and RL. To power this curriculum at scale, Mage-CUA-Forge
replaces per-task agent construction with reusable, skill-conditioned
generation workflows and application-specific preparers, synthesizing 293,806
desktop and web tasks across 6,915 skills while reducing recurring per-task
expenditure by 82.6%. Rather than directly distilling a default teacher, we
evolve the teacher harness and instantiate specialized CUA harnesses to yield
high-quality trajectories alongside stage-specific supervision. Mage-VL-Cowork-4B
finally climbs to 66.0% on OSWorld-Verified through different training stages
with more efficient reasoning cost, achieving state-of-the-art performance at
its parameter size and pushing forward the frontier of on-device intelligence.

Introduction

Computer-use agents (CUAs) for productivity perceive graphical desktops through screenshots and
act through keyboard and mouse commands. This GUI channel is universal, but it is a
modeling choice rather than a property of the domain, and an expensive one:
a typical screenshot can require thousands of tokens, increasing the cost of
processing high-resolution visual input and grounding interface elements.
A person fluent with a computer does not confine
themselves to the mouse: they open a terminal when a terminal is faster and read
a file to confirm what a dialog claims to have saved.
Restricting the policy to
pixels forces it to re-derive through the GUI what a single command would
accomplish, and removes the most reliable channel it has for checking its own
work.
We therefore train a

hybrid
 CUA that acts through two action channels: the GUI channel, with
visual observation and coordinate control, and the terminal channel, a
persistent shell environment in which it may run code, invoke
command-line utilities, and call application libraries directly.

Hybrid access does not by itself produce hybrid competence, even for
frontier teachers. Prior work shows that access to application tools does not
ensure their effective use, and that the same tool set can affect different
models differently 
[
1
, 
2
]
. The policy must learn
which channel is appropriate for the current operation and at what level of
abstraction to act. Effective hybrid execution routes each operation to the
channel where it fits best: coding and terminal execution for structured files
(such as updating a spreadsheet with one library call rather than dozens of
clicks), and GUI interaction for visual or live application state (such as
browser settings that a running browser caches in memory and overwrites on
exit). Because even frontier models exhibit suboptimal channel routing under a
naive setup, distilling their default rollouts passes those same limits on to
the student. The harness is not a neutral container: its tool interfaces,
context handling, and guidance directly shape how a fixed teacher model acts.
Evolving the harness before large-scale rollout elicits stronger hybrid
execution than the teacher achieves by default and carries those improvements
across the entire training corpus.

Moreover, whereas existing pipelines such as ProCUA and ScaleCUA 
[
3
, 
4
]

post-train models that already have strong grounding, coding, and agent
capabilities, we present an end-to-end, progressive five-stage curriculum
starting from a general multimodally aligned checkpoint: GUI-oriented
midtraining, GUI agent SFT, coding and terminal SFT, hybrid CUA SFT, and
online hybrid RL. Sustaining such a
multi-stage curriculum requires massive, diverse training environments and
trajectories, for which we propose the Mage-CUA-Forge environment synthesis
pipeline. Unlike prior agent-first approaches that rely on open-ended agent
execution to construct each task from scratch, Mage-CUA-Forge uses an authoring
agent to construct application-specific preparers and reusable generation
workflows tailored to each application and its atomic functionalities, scaling
task and environment synthesis with high consistency and low recurring cost.

We introduce Mage-VL-Cowork, a hybrid CUA trained on 318,837 teacher trajectories
over 293,806 synthesized tasks and environments that cover 6,915 atomic skills
in an agent-constructed skill taxonomy. Three design decisions define the
pipeline:

1.

Learning from an evolved hybrid CUA harness.

To collect high-quality demonstrations even when a frontier teacher’s default
channel routing is imperfect, we evolve the harness including its scaffold, tool
interfaces, prompts, and terminal execution environment, before large-scale
rollout. Evolution here is as much pruning as growth: unlike skill libraries
that continuously accumulate tools 
[
5
, 
6
, 
7
]
, we
remove overlapping or ill-suited tools so the teacher produces clean hybrid
trajectories that yield much larger gains when distilled into the student
(§
3.1
, §
6.7
). Moreover,
harness evolution produces specialized configurations with different tool
sets—including a GUI harness, a terminal harness, and the hybrid CUA
harness—allowing us to roll out the same synthesized tasks under multiple
harnesses to collect trajectories emphasizing distinct capabilities across
our training stages (§
4
).

2.

A single policy that learns the hybrid execution policy.

Mage-VL-Cowork observes full-desktop screenshots and emits coordinate mouse and
keyboard actions, and in the same episode may execute code and terminal
commands on the machine it is operating. The two channels are complementary: pixels are the only
channel that reaches spatial, canvas, and rendering-dependent state, while code
edits at the abstraction the instruction is written in and lets the agent check
its work against ground truth rather than against a screenshot of a dialog.
Unlike systems that route between a GUI operator and a coding operator at the
orchestrator level 
[
8
, 
9
]
, the choice is internal to the policy
and is therefore something the training data must teach (§
3.1
).

3.

Workflow-first task and environment synthesis.

Agent effort is spent once per 
skill
 rather than once per task. For
each atomic skill, an authoring agent constructs and debugs a reusable
generation workflow that combines LLM nodes with application-specific

preparers
, which materialize input artifacts such as a Calc workbook
or a Thunderbird profile with a populated mail store. Combined workflows
produce a task package of instruction, environment setup script, and rubric,
and gate nodes check its consistency before the task is accepted. Shared
workflows and preparers propagate each improvement across all subsequently
generated task instances.
Task synthesis, including skill-based generation, has also been studied
in terminal settings, where the environment is a container
filesystem 
[
10
, 
11
]
; on a full desktop the environment
is application state, which is what the preparer exists to produce
(§
3.2
).

With 4B parameters, Mage-VL-Cowork achieves 66.0% on OSWorld-Verified under a
50-step budget, outperforming larger open-source agents including Muse
Glimmer-30B (65.9%), Qwen3.6-27B (63.9%), and EvoCUA-32B (56.7%).
Across our curriculum, performance climbs by 20.44 percentage points from GUI
SFT (45.56%) through Hybrid SFT (55.84%) to final RL (66.0%), pushing
forward practical on-device intelligence for autonomous desktop workflows.

Workflow-First Task and Environment Generation

A computer-use task package combines an instruction, an executable environment
setup, and an evaluation rubric. Workflow-first generation reuses the
construction procedure for these three coordinated components across task
instances.

Mage-CUA-Forge builds a reusable generation workflow for each atomic skill. Each
workflow combines LLM nodes, file preparers, and setup operations. For a
composite capability, the workflows share a unified specification of the
requested outcome, required files, and application preconditions, producing a
coordinated task package.

The source-file and setup-script branches share the task specification.
Branch-specific checks feed a final consistency gate over the complete task
package.

The workflow routes each required file to a preparer appropriate for its type,
reusing application-specific preparation logic across skill workflows. These
preparers materialize the input artifacts needed by the task. Other workflow
nodes produce the remaining setup code and combine it with shared setup
utilities, such as application launching and desktop-state adjustment. The
result is an 
environment setup script
 (
env setup script
), whose
purpose is to establish the required task preconditions and initial desktop
state inside the sandbox. Workflow-specific generation logic is thus separated
from reusable file and application preparation, as well as from generic setup
operations that are not tied to an individual skill.

Dedicated LLM nodes generate the user instruction and its evaluation rubric
from the shared specification. Task completion is judged by an LLM against this
rubric. Application setup details remain in the setup script, while the
instruction describes the user’s intended outcome.

Validation operates at two levels. File-level gates check artifacts against the
shared specification, and a package-level gate checks consistency among the
instruction, setup requirements, and rubric. Gate feedback improves the
reusable workflow and shared preparers. Subsequent trajectory evaluation
assesses the teacher’s execution of accepted tasks.

Workflow reuse separates one-time construction from recurring generation. LLM
nodes supply task-specific content within an established procedure, while
shared preparers provide reusable file and application setup logic across
skills and task instances.

For browser and cross-application workflows, such as retrieving structured
records from a website and compiling them into a spreadsheet or document, live
websites introduce anti-bot blocks, content drift, and non-resettable backend
state. We therefore pair desktop application preparers with self-hosted,
deterministic web environments combining synthesized
InfiniteWeb 
[
19
]
 sites and high-fidelity website
replicas built upon and extending WebHarbor 
[
20
]
, where each
replica resets from a local seed database per episode to support verifiable web
and cross-application task generation (Appendix 
A.1
).

Training Pipeline of Mage-VL-Cowork

Unlike pipelines that post-train checkpoints already specialized for GUI
grounding or coding, we present an end-to-end, progressive five-stage training
curriculum starting from an intermediate 4B Mage-VL checkpoint:
(1) GUI-Oriented Midtraining, (2) GUI Agent SFT, (3) Coding & Terminal SFT,
(4) Hybrid CUA SFT, and (5) Online Hybrid RL.
This specialize-then-unify curriculum first builds solid, standalone
capabilities in visual grounding, GUI interaction, and coding and terminal
execution before teaching the model to route and combine both channels within a
single episode.

Stage 2: GUI Agent SFT

The second stage turns the visual and tool-format foundation into a GUI
execution policy. We collect teacher trajectories with the GUI-only harness.
In this setting, task actions are
performed through the GUI channel, and the training examples pair the available
screenshot and interaction history with the teacher’s next action. We use these
trajectories to fine-tune the midtrained checkpoint on complete computer-use
workflows.

GUI trajectories connect single-step grounding to multi-step interaction,
teaching the model which control to operate next, when to scroll, how to enter
text, and how to continue after the interface changes. Building strong
standalone GUI execution first ensures that when the model later learns hybrid
channel routing, it chooses between two capable channels rather than routing
around a weak visual policy.

Stage 3: Coding & Terminal SFT

The third stage develops coding and terminal execution capabilities, including
terminal operation, code generation, repository navigation, and
debugging with Terminal-Bench-style 
[
28
]
 and SWE-bench-style training data 
[
29
]
.

We combine general software-engineering data with desktop terminal harness
trajectories from productivity tasks we synthesized in Section 
3
. While repository-level tasks cover source
files, tests, and build tools, desktop coding trajectories teach the model to
read and modify workbooks, documents, presentations, and application state
using specialized Python libraries and command-line utilities.

Specifically, we run a terminal-only teacher harness on the same batch of
desktop tasks used for GUI trajectory collection in Stage 2. Retaining the
successful coding and terminal trajectories alongside general terminal and
software-engineering data gives the student direct examples of how to solve
target desktop tasks through code before Stage 4 combines both channels.

Stage 4: Hybrid CUA SFT

Stage 4 brings the visual and coding foundations together by training on
the 318,837 trajectories collected under the evolved hybrid harness
(Section 
3.1
). Within a shared task context, a single policy
learns turn-level channel routing—deciding when to act through the GUI, when
to use coding and terminal execution, and when to switch between them, such as
using code to edit a structured file and then returning to the application
window to inspect the rendered result.

Because a 4B model is sensitive to noisy or ambiguous demonstrations,
optimizing the teacher harness for both task success and token efficiency and
filtering trajectories before training, which is critical. Rather than merely
exposing the student to a larger tool inventory, the resulting supervision
directly teaches effective channel routing and compact execution.

The final supervised stage draws on the 318,837 retained hybrid trajectories;
the final hybrid dataset contains 1,377,805 packed bins. The resulting model
combines the visual grounding and GUI execution learned in the first two stages,
the general and desktop-specific coding capabilities developed in the third,
and the hybrid execution policy demonstrated by the evolved hybrid agent.
We refer to the checkpoint obtained after this stage as Mage-VL-Cowork-SFT.

Stage 5: Online Hybrid RL

The final stage refines Mage-VL-Cowork-SFT with online reinforcement learning
in the hybrid harness. We train on the 1,988 tasks released by
ScaleCUA 
[
4
]
, each paired with a verifiable reward. Following
ScaleCUA, we use frontier sampling, with task weights based on pre-run success
rates to allocate rollouts toward the learning frontier. The policy is
optimized with GRPO 
[
30
]
. Rollouts are generated asynchronously with bounded
policy staleness, and we apply vanilla truncated importance sampling
(TIS) 
[
31
]
 to correct the mismatch between the rollout and
training policies. Each rollout uses the same step budget as our OSWorld-Verified
evaluation. The resulting model is Mage-VL-Cowork, which we evaluate in
Section 
6
.

Each optimizer update admits 96 task groups with eight episode slots per group.
A four-batch admission window bounds policy lag at three updates, and TIS caps
importance weights at 2.0. Mixed-policy episodes are enabled. CPU workers
execute desktop environments, while GPU services handle training and inference.
The relay carries control, inference, and compact trajectories; weight
synchronization uses an intra-GPU-cluster path.

Workload Characteristics and Design Requirements

Desktop rollouts combine inference with application loading, content entry, and
state updates. Individual observed episodes exceed 40 minutes, motivating
asynchronous scheduling so that completed tasks can advance training
independently of long-running episodes.

The resource requirements are also heterogeneous. Desktop environments need
CPU capacity, guest memory, and nested virtualization, whereas model inference
and optimization run on GPUs. For a compact model on B200 hardware,
environment execution and orchestration can remain important latency sources
even when individual model calls are relatively fast. We consequently manage
environment capacity separately from model-serving and training capacity,
and use asynchronous rollouts rather than requiring lockstep progress across
the desktop fleet.

Visual rollouts create repeated screenshot inputs across turn-level examples.
Compact episode transfer, prefetching, and node-local image expansion address
transport, preparation, and training-input materialization as separate stages
of the data path.

Conclusion

Mage-VL-Cowork brings effective hybrid computer use to a 4B policy, achieving
66.0% on OSWorld-Verified under a 50-step budget and outperforming
open-source agents several times its size. Rather than post-training a
checkpoint already specialized for computer use, our progressive five-stage
training curriculum, GUI-oriented midtraining, GUI agent SFT, coding and
terminal SFT, hybrid CUA SFT, and online hybrid RL, builds visual grounding,
GUI execution, desktop coding and terminal operation, hybrid channel routing,
and online RL from a general multimodally aligned starting point. Upstream of training, evolving the teacher harness, elicits stronger
demonstrations than the teacher model’s default setup, while reusable
skill-conditioned workflows cut recurring per-task generation expenditure by
82.6%. Together, these results provide a scalable route from reusable
environment construction and teacher-harness optimization to compact hybrid
computer-use policies, pushing forward the frontier of on-device intelligence.

High-Fidelity Web Replicas

Figure 9

To support the controllable browser workflows and offline evaluations introduced
in Sections

[

self-hosted website replicas built upon and expanding
WebHarbor 
[

replica runs as a local 
Flask

a fresh working database from a read-only seed snapshot, isolating stateful
operations across rollouts while exposing the underlying tables for deterministic
verification. Constructing and upgrading these replicas follows two core
principles:

Frontend and interactive fidelity.

Early mock environments often simplify pages into generic templates or static
placeholder blocks, which reduces visual complexity and omits the controls
needed for multi-step tasks. To match real-world interfaces, we capture
reference snapshots from target websites—spanning DOM hierarchies, computed
CSS rules, and static assets (logos, icons, and inline SVGs), supplemented by
web archives when live endpoints are restricted—and reconstruct the full
page structure. Beyond static layout, we implement the interactive controls
required for end-to-end task completion, including multi-attribute filter
panels, date pickers, sorting menus, pagination, stateful submission forms, and
domain-specific components such as 
Leaflet

Chart.js

views.

Database grounding and multimodal completion.

We populate each replica’s seed database primarily from authentic structured
sources, including public APIs and data dumps (e.g., ESPN, Stack Exchange,
Hacker News, and OpenStreetMap), web crawl archives, and bibliographic catalogs.
When raw records lack full-text bodies, detailed item descriptions, or image
assets, we condition LLM text generation and image-generation models on the
authentic structured attributes to synthesize coherent articles, descriptions,
and context-matched thumbnails. All synthesized presentation fields are tagged
separately from the canonical attributes queried by task verifiers, ensuring
realistic visual and textual density without introducing ambiguity into
ground-truth grading.

downstream action space and step-level rationales.

Both recipes reach comparable accuracy after downstream SFT; we adopt selective

<think>

decoupled from trajectory synthesis, uses fewer tokens, and iterates faster.

representative interaction steps sampled from real desktop trajectories across

tools (GIMP, VLC), development environments (VS Code), and system utilities.

instruction (naming the target control directly, e.g., 
“Click the

intent

(stating the local subgoal, e.g., 
“Open the VS Code settings page from

RL Infrastructure Details and Measurements

This appendix describes the RaaS implementation and deployment, followed by
workload, transport, update-timing, and policy-lag profiles. Each profile is
associated with its measurement run, update window, and aggregation rule.

Rollout-as-a-Service Architecture

The infrastructure integrates PoLar 
[
32
]
, Slime, Azure Relay, and
Azure Virtual Machine Scale Sets (VMSS). The training client uses Slime
adapters for desktop rollouts, turn-level samples, and data-parallel shards.
SGLang 
[
33
]
 serves model requests, while RaaS workers on Azure VMSS
run the resource manager and CUA runners. Routing and image preparation execute
on CPUs; inference and optimization execute on GPUs.

The relay exposes three logical communication channels:

•

Control.
 The training client submits work and queries
task status and ready manifests from the resource manager.

•

Inference.
 The harness sends prompts and screenshots to
the inference service and receives generated tokens and log probabilities.

•

Bulk trajectories.
 Stored compact episodes are delivered
to the training adapters using deduplication and gzip compression.

The relay carries control, inference, and compact-trajectory traffic.
Trainer-to-inference weight synchronization and training collectives use
intra-cluster paths. External judge calls and artifact storage use their
respective service interfaces.

Resource Management and Sandbox Execution

The resource manager contains three components. The 
Task Dispatcher

handles submission, queueing, dispatch, status, and ready manifests. The

Sandbox Scheduler
 manages fleet capacity and sandbox allocation and
release, with separate admission limits for initialization, running, and
post-run processing. The 
Compact Episode JSON Store
 gathers completed
trajectory records and supplies the bulk-transfer path. These components
separate task coordination and environment capacity from the model-serving
process.

Each host has separate concurrency caps for sandbox initialization, execution,
and post-run processing: 4 (
INIT
), 16 (
RUN
), and 8
(
POSTRUN
), respectively. Lifecycle-specific admission control manages
setup and post-processing alongside the 16 running-episode slots.

Each CUA runner contains four components. 
EnvRuntime
 provides the
desktop environment, captures screenshots, and executes actions.

CUAHarness
 maintains the stateful agent loop, issues model requests,
and dispatches GUI or terminal tools. 
Evaluator
 produces the task’s

an external judge where required. 
TrajectoryBuilder
 combines turn
traces and evaluator outcomes into compact episode JSON for transfer to the
training client.

Asynchronous Rollouts and Trajectory Preparation

The configured update batch contains 96 task groups with eight episode slots
per group, or 768 slots. The admission window spans four batches, with a
maximum configured policy lag of three optimizer updates. This organization
allows rollout collection and optimization to overlap while bounding the
policy-version gap of admitted data. Mixed-policy episodes are enabled.

TIS caps importance weights at 2.0. Admission is configured over a four-batch
window, with policy lag bounded at three optimizer updates
(Section 
4.5
).

The data path keeps compact trajectories separate from expanded training
tensors. The rollout bridge and adapters construct per-turn samples and
data-parallel shards. Ray distributes compressed images, tokens, and metadata;
node-local CPU processing decodes and resizes the images and applies the
model’s image processor before the tensors are consumed by the trainer GPUs.
Prefetching prepares trajectory data ahead of training consumption rather
than placing every preparation operation on the immediate update path.

Each turn retains up to three recent images. Compact episodes deduplicate
stored screenshots for transfer, and turn-level preparation materializes the
image inputs required by each training example.

Deployment Scale and Runtime Profile

The CPU fleet comprises 70 Standard_D64d_v5 hosts, each with 64 vCPUs and
256 GiB of memory. Sixteen GUI slots per host provide 1,120 configured slots.
Each guest receives eight vCPUs and 4 GiB of memory, giving a 2:1 guest-to-host
vCPU allocation ratio. The reference GPU deployment uses 32 B200 GPUs, split
into 24 training and eight inference GPUs.

A deployment with 28 training GPUs and four inference GPUs reached a peak
occupancy of 1,120 running environments. The 24/8 split is the reference
configuration used in the architecture diagram.
