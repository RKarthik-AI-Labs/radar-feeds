Abstract.

Web agents are increasingly deployed to complete tasks autonomously on real websites, where adversarially injected content can induce them to perform unauthorized actions.
Existing evaluations primarily use fixed attacks or focus on a single attack type, and evaluate attacks at the text level rather than through real state changes, thus underestimating how vulnerable agents are to diverse attacks.
To address the gap, we introduce 
REEF
, a benchmark of 
R
ed-teaming 
E
xecutable 
E

F

REEF covers 9 verifier-grounded websites spanning travel, commerce, productivity, media, and communication, and pairs every authentic benign task with a malicious objective delivered through 5 attack types at both the user and the environment level.
REEF’s state-based verifiers provide the execution feedback that drives 
ANGLER
, an

Rather than evaluating a fixed attack set, ANGLER uses outcomes from prior rollouts to guide LLM-based attack mutation and candidate selection, prioritizing near-miss seeds during refinement.
Across 8 VLM-based web agents, ANGLER achieves an end-to-end attack success rate (ASR) of 20.36%, compared with 15.24% for the non-adaptive setting.
Compared with attack-free execution on the same benign tasks, attacks generated by ANGLER reduce benign task success rate (BSR) from 61.9% to 44.4%.

Recent advances in large language models and vision-language models enable web agents to navigate websites and complete multi-step tasks on behalf of users 
(
Gur et al., 2024
; 
Zheng et al., 2024
; 
He et al., 2024
; 
Qi et al., 2025
)
.
However, these capabilities also introduce security risks, as malicious instructions may induce web agents to perform unauthorized actions, such as sending messages, modifying settings, or completing transactions 
(
Wang et al., 2025a
; 
Syros et al., 2026
; 
Evtimov et al., 2025
)
.
Adversarial content can reach web agents through user-level attacks that manipulate user instructions or environment-level attacks that inject malicious content into webpages encountered during execution.
If the agent follows such content, it may perform actions that are not authorized by the authentic user goal.
A faithful security evaluation must therefore test attacks during interactive website execution and verify whether they cause unauthorized changes to website state.

Existing security benchmarks provide executable environments for evaluating adversarial attacks against web agents and related tool-using agents.
WASP 
(
Evtimov et al., 2025
)
, RedAgentBench 
(
Chen et al., 2026b
)
, and SecureWebArena 
(
Ying et al., 2026
)
 execute adversarial tasks in interactive environments, but evaluate agents using fixed and static attack cases or trajectories.
However, these benchmarks do not adapt attack generation or selection during agent evaluation based on outcomes from previous rollouts, potentially missing vulnerabilities that could be uncovered through feedback-driven exploration.

Although recent works have begun to introduce adaptive attacks, they are typically limited to a single attack type.
Studies of pop-up and advertising-based injections each target a specific delivery channel 
(
Zhang et al., 2025
; 
Wang et al., 2025a
)
, while MUZZLE 
(
Syros et al., 2026
)
 uses execution feedback to adapt attacks but focuses specifically on indirect prompt injection.
Consequently, existing evaluations provide broad evaluation of fixed attacks or adaptive refinement within a narrow attack class.
What remains missing for web agents security evaluation is an adaptive but reproducible framework across multiple attack types.
However, simply adding an adaptive attacker to existing benchmarks is insufficient because newly generated attack plans must be validated against specific constraints and evaluated under consistent task contexts, objective definitions, and verifier rules.

Therefore, we address these requirements with REEF and ANGLER, which combine a fixed benchmark specification with adaptive search.
Built on 9 resettable AutoWebWorld environments 
(
Wu et al., 2026
)
, REEF pairs benign tasks with grounded malicious objectives across 5 attack types.
A site compiler enforces attack constraints and checks plan validity, while programmatic verifiers assess outcomes from website state and committed artifacts.
Within this feasible space, ANGLER combines systematic exploration, experience-guided LLM mutation, and feedback-driven candidate selection under a fixed rollout budget.
This separation enables controlled comparisons of discovery policies under shared attack constraints and success criteria.
Our contributions are summarized as follows:

•

We introduce REEF, an executable benchmark spanning 9 websites and 5 attack types.
Unlike fixed-case evaluations, REEF supports controlled online mutation of structured attack configurations and uses programmatic verifiers to measure benign task completion and malicious objective success.

•

We propose ANGLER, an adaptive experience-guided framework for red-teaming web agents.
It uses verifier-grounded rollout feedback to identify near-miss seeds for attack refinement and to select subsequent candidates within a predefined feasible attack-plan space.

•

We establish an evaluation protocol for comparing adaptive and non-adaptive attackers under identical task contexts and rollout counts.
Across 8 VLM-based web agents and 9 websites, ANGLER increases average ASR from 15.2% for the non-adaptive baseline to 20.4%, while its attacks reduce average BSR from 61.9% under attack-free execution to 44.4%.

2. 
Related Work

General Web Agent Benchmarks.
 
General web agent benchmarks establish the execution environments and evaluation protocols.
Mind2Web 
(
Deng et al., 2023
)
 and WebLINX 
(
Lù et al., 2024
)
 provide large-scale demonstrations collected from diverse real-world websites, supporting the learning and evaluation of agents across tasks and previously unseen domains.
WebArena 
(
Zhou et al., 2024
)
 introduced self-hosted websites and realistic multi-step tasks to evaluate language agents through the completion of functional tasks.
VisualWebArena 
(
Koh et al., 2024
)
 extended this setting with visually grounded tasks that require agents to jointly interpret webpage text, images, and interface elements.
BrowserGym 
(
Chezelles et al., 2024
)
 standardizes browser observations, actions, and experimental interfaces across multiple benchmarks, and AutoWebWorld 
(
Wu et al., 2026
)
 generates resettable and programmatically verifiable websites from finite-state specifications.
These benchmarks improve environmental realism, task diversity, and evaluation reproducibility, but primarily measure whether agents complete benign user tasks.

Web Agent Security Benchmarks.
 
Security benchmarks extend agent evaluation by introducing malicious objectives or untrusted external content.
ST-WebAgentBench 
(
Levy et al., 2026
)
 and SafeArena 
(
Tur et al., 2025
)
 respectively examine policy adherence and agents’ completion of harmful requests.
WASP 
(
Evtimov et al., 2025
)
 evaluates end-to-end prompt-injection attacks with realistic malicious objectives, while RedTeamCUA 
(
Liao et al., 2026
)
 extends adversarial testing to hybrid Web–OS environments.
TRAP 
(
Korgul et al., 2025
)
 studies how persuasive content embedded in realistic interfaces redirects web agents away from their original tasks.
SecureWebArena 
(
Ying et al., 2026
)
 covers multiple user- and environment-level attack vectors, and REDAgentBench 
(
Chen et al., 2026b
)
 emphasizes executable attacks and faithful measurement of their effects.
These benchmarks improve environmental realism and attack coverage, but evaluate adversarial cases instantiated before execution rather than refining subsequent attacks from observed outcomes.

Recent work has begun to make attack generation adaptive.
WebInject 
(
Wang et al., 2025b
)
 optimizes webpage-level pixel perturbations through the rendered interface to induce malicious actions.
Other approaches refine prompt injections through black-box tree search, reinforcement learning, or white-box and black-box prompt optimization 
(
Wang et al., 2025c
; 
Chen et al., 2026a
; 
Hofer et al., 2026
)
.
AdvWeb 
(
Xu et al., 2024
)
 trains a black-box adversarial prompter using successful and failed attack strings collected against a target VLM-based web agent.
Trajectory-driven methods instead use observed execution failures to guide subsequent attacks.
MUZZLE 
(
Syros et al., 2026
)
 revises indirect prompt injections from Web-agent execution feedback, while SIR 
(
Xiong et al., 2026
)
 extracts reusable attack principles from failed computer-use-agent trajectories.
These methods demonstrate the value of feedback-driven testing, but their adaptation remains within a narrow attack mechanism.

3.2. 
Threat Model

Adversarial Goal.
 
The adversary tries to induce the target agent to carry out a malicious objective 
 that is not authorized by the authentic user goal 
.
Representative objectives include sending an unauthorized message, modifying an account setting, or completing an unauthorized transaction.
Each malicious objective is paired with an executable verifier 
 that determines whether the unauthorized website-state change has occurred and remains effective at termination.

Capabilities.
 
The attacker can manipulate either the user instruction or the webpage content encountered by the target agent, corresponding to user-level and environment-level attacks, respectively.

•

In a user-level attack, the attacker appends an adversarial payload to the authentic user instruction while leaving the website environment unchanged.

•

In an environment-level attack, the authentic user instruction remains unchanged, while the attacker injects content through an eligible webpage surface, including ordinary page content, pop-up or modal overlays, distraction elements, and advertising or sponsored-content slots.
The four environment-level attack types and their delivery mechanisms are detailed in 
Section
 
A.1
.

Attacker Knowledge and Constraints.
 
The attacker selects a malicious objective supported by the current website and varies its payload, delivery configuration, injection surface, timing, and presentation parameters within a predefined feasible attack space.
After each rollout, the attacker receives execution-level feedback, including verifier outcomes and attack-progress signals, but has no access to the target model’s parameters, hidden states, or private reasoning.
The attacker cannot modify the agent implementation, underlying website logic, verifiers, or environment reset procedure.

4. 
REEF Construction

We construct REEF by combining diverse executable web environments, compositional task and attack generation, and programmatic verification of website-state changes.

4.1. 
Overview

REEF is an executable multi-site benchmark for systematically evaluating the security vulnerabilities of web agents.
Built on 9 stateful and realistic website environments from AutoWebWorld 
(
Wu et al., 2026
)
, REEF spans 5 application domains: travel, commerce, productivity, media, and communication.
These websites run in isolated environments with synthetic users and content, enabling reproducible state-changing interactions without affecting public services.
Across these websites, REEF instantiates 326 malicious objectives covering 5 functional categories: browsing and navigation, lightweight actions, content publishing, account configuration, and transactional commits.
Malicious objective completion is verified from the resulting website state, and browsing and navigation objectives additionally require the agent to terminate on the intended page.

Section
 
A.2
 provides the detailed statistics.

Each benchmark case combines an authentic benign task with a site-supported malicious objective and a compatible attack delivery configuration.
The malicious objective can be delivered through a user-level direct prompt injection or an environment-level webpage injection, while the payload, delivery configuration and injection surface are subject to site-specific constraints.
Each case is compiled and validated against site-compatible execution and evaluated using programmatic state-based verifiers that separately measure benign task completion, malicious
objective achievement, and recovery.
This executable design evaluates site-specific attack cases under a common protocol and measures their effects through website state changes, rather than treating payloads as isolated text prompts.

4.2. 
Task and Attack Construction

Benign Task Construction.
 
For each website, we model its user-facing workflows as a finite-state machine (FSM).
Starting from the reset state, breadth-first search (BFS) enumerates valid paths to reachable goal states.
We convert each path into a parameterized task template and instantiate its free variables using entities supported by the website.
Each resulting task is paired with a programmatic user verifier 
 that checks whether the specified goal state has been reached.
This construction increases task diversity while preserving the underlying workflow structure.

Attack Construction.
 
For each website, we define malicious-objective templates over unauthorized but executable state changes supported by that website.
Each objective is instantiated with site-valid entities and paired with an attacker verifier

Quality Control.
 
We combine automated consistency checks with manual audits during benchmark construction.
For each website, cases containing invalid configurations, implausible instructions, broken interactions, or mismatches between visible behavior and verifier outcomes are corrected and rerun.

4.3. 
Faithful Execution and Measurement

Compilation and Validation.
 
Given a candidate attack case 
, the compilation-and-validation pipeline either produces an executable case or rejects the candidate.
The compiler instantiates the selected benign-task, malicious-objective, and delivery templates with registered site-specific parameters and constructs the corresponding verifier specifications.
It produces a composed agent instruction for a user-level plan or a renderer-ready injection specification for an environment-level plan.
Static validation rejects undefined site-specific templates, entities, or injection surfaces, as well as incompatible task-objective pairs, invalid timing or payloads, and payload–objective inconsistencies.
Only validated cases are eligible for rollout.

Verifier-Grounded Measurement.
 
We determine rollout outcomes directly from recorded website states rather than relying on agent self-reports or LLM-as-a-judge scoring.
Each attack case is paired with three programmatic verifiers:

•

The user verifier 
 determines whether the benign objective is achieved during the rollout.

•

The attacker verifier 
 determines whether the malicious objective is achieved during the rollout and remains satisfied at termination.

•

The recovery verifier 
 confirms whether a malicious effect observed earlier is absent at termination.

Before each rollout, the attacker verifier 
 must be false in the reset state, preventing a pre-existing malicious effect from being counted as attack success.
Together, the three verifiers distinguish attacks that are never successful, recovered before termination, or successful at termination.

For environment-level attacks, we additionally record whether the agent engages with the initial injected call to action before evaluating the final malicious outcome.

5. 
Adaptive Attacker with Experience Guidance

We propose ANGLER, a two-stage adaptive framework for discovering vulnerabilities in web agents.
The first stage covers feasible combinations of benign tasks and attack types.
The second stage iteratively uses an experience pool to guide LLM mutation of candidate attacks, with near-miss records prioritized as mutation seeds.
A funnel-aware contextual bandit then selects the most promising candidate for execution.
Verifier feedback updates both the experience pool and the bandit.

. 
Overview of ANGLER.
A two-stage scheduler balances structured coverage and adaptive search, while verifier feedback guides candidate generation and contextual-bandit selection across subsequent rollouts.

5.1. 
Two-Stage Scheduler

Our two-stage scheduler separates systematic coverage from adaptive optimization by assigning the benign task and specifying the attack search space for each rollout.

Coverage Stage.
 
At the beginning of evaluation, the experience pool is empty, so the attacker has no prior outcomes to guide adaptive generation or selection.
To bootstrap this process, the coverage stage systematically evaluates feasible pairings of benign-task templates and supported attack types.
For each rollout, the scheduler prioritizes a pairing that has not reached its coverage quota, and then chooses one of the least-used instruction instances from that template.
Once every pairing reaches its predefined quota, which may differ across attack types, the scheduler transitions to the adaptive stage.
This forced exploration mitigates cold-start bias and prevents early random successes from prematurely dominating subsequent search.

Adaptive Stage.
 
Once the coverage requirements are satisfied, the scheduler enters the adaptive stage.
It selects a benign template uniformly, chooses one of its least-used instruction instances, and assigns the rollout to a compatible attack level, either user-level or environment-level.
These scheduling decisions are independent of previous attack outcomes.
Within the assigned attack level, the corresponding contextual bandit selects the specific attack type and delivery configuration.
This separation prevents the attacker from concentrating its rollout budget on easier task contexts while allowing adaptive optimization within each scheduled context.

5.2. 
Experience-guided Candidate Generation

Experience Pool and Seed Selection.
 
After each rollout, we add a record to the experience pool containing the executed attack plan, verifier outcomes, benign-task completion, and attack-funnel signals, and assign it to one of the four categories in 
Table
 
2
.
When only a few matching records are available or their observed ASR is low, seed selection favors verified successes because they provide executable starting points for further mutation.
As more records become available and ASR increases, the seed selection system will give higher priority to near-miss records.
Unlike blocked rollouts, near-misses show that an attack induced its malicious effect at least transiently, even though the effect was absent at termination.
They help locate the remaining bottleneck, allowing ANGLER to guide subsequent mutations toward the stage where the attack failed rather than treating all unsuccessful rollouts alike.
The exact sampling priorities and criteria are provided in

Candidate Generation.
 
During the adaptive stage, the attacker uses the selected seed as structured feedback for experience-guided LLM mutation.
For each candidate slot, the program assigns a malicious objective grounded in the current website, while the LLM determines how that objective is expressed and delivered.

We design a mutation router that uses the verified outcome and progress signals from the previous rollout to determine which components the LLM should revise.
For user-level failures, the router directs the LLM to revise the injected instruction.
For environment-level failures, it distinguishes failures of exposure, engagement, and continuation-phase navigation completion, directing the LLM toward placement and timing, CTA wording and visual salience, or continuation instructions, respectively.
Across all routes, the LLM may modify only permitted payload, delivery, timing, and presentation fields, while the assigned objective, verifier logic, site entities, and renderer behavior remain fixed.

Evaluation Protocol.
 
For each target agent and website, we compare ANGLER with a non-adaptive baseline attacker under matched task contexts and identical rollout budgets.
At each rollout, the baseline constructs candidate attacks supported by the current website, filters them through the compiler, and selects one of the remaining candidates uniformly at random.

Before each rollout, the environment is restored to its initial state, and all experimental conditions receive the same target-agent configuration and interaction horizon.
We report verifier-confirmed final attack success rate (ASR), benign-task success rate (BSR), and call-to-action engagement rate (CTA).

6.5. 
Discussion and Analysis

Engagement May Not Imply End-to-End Success.
 
CTA measures whether an agent engages with injected webpage content, whereas ASR requires the malicious objective to be satisfied at termination.
The attack-type breakdown in 
Table
 
11
 reveals substantial gaps between these stages: pop-up injection achieves 52.4% CTA but only 17.1% ASR, while distraction injection achieves 47.0% CTA and 17.8% ASR.
These gaps show that a high CTA does not necessarily translate into a high ASR, as the agent may abandon the malicious path before completing the objective.
Nevertheless, high engagement remains security-relevant because it may redirect the agent to attacker-controlled pages and expose it to further malicious content.
Therefore, CTA should be interpreted as a meaningful indicator of attack exposure and engagement.

Vulnerability Varies Across Models and Attack Types.
 
The effectiveness of an attack depends on both the target backbone and its delivery mechanism.
As shown in 
Table
 
11
, GPT-4o is highly susceptible to environment-level attacks: pop-up and distraction injection achieve CTA rates of 83.3% and 89.3%, together with ASRs of 42.3% and 39.3%, respectively.
In contrast, CTA never exceeds 5.4% for GPT-6.1 Sol or 2.3% for Claude Sonnet 5.5 across the four environment-level attack types.
However, direct prompt injection still achieves ASRs of 32.5% and 32.9% against these two models.
These results show that low engagement with injected webpage content does not imply general robustness, as a model that resists one delivery channel may remain vulnerable to another.

7. 
Conclusion

We presented REEF and ANGLER for measuring and discovering security
vulnerabilities of web agents through verified website-state changes.
REEF provides 8,316 executable cases over 9 stateful websites and 5 attack types spanning both user-level and environment-level delivery, using programmatic state verifiers to measure both benign and malicious task completion.
Across 8 VLM-based target agents, ANGLER increases average ASR from 15.24% to 20.36%, a relative improvement of 33.6%.

Ethics and Privacy Statement

All experiments are conducted in isolated and resettable benchmark environments using synthetic accounts, entities, and malicious objectives.
No attacks are directed at public services, real users, or real accounts, and the experiments do not collect personal data or access real secrets.

Appendix A 
REEF Details

A.1. 
Environment-level Attack Types

Figure
 
5
 illustrates the four environment-level attack types supported by REEF.
All four leave the authentic user instruction unchanged and inject adversarial content through the website environment.

Indirect Prompt Injection.
 
Indirect Prompt Injection embeds the adversarial instruction within ordinary webpage content, such as a community post, discussion note, or support message.
The injected content adopts the surrounding page’s native presentation and attempts to appear as task-relevant information that the agent should follow.
Unlike the other attack types, it does not rely on a modal interruption, warning-style distraction, or explicitly sponsored presentation.

Pop-up Injection.
 
Pop-up Injection presents the adversarial content in a modal overlay above the current webpage.
The pop-up interrupts the normal interaction flow and typically frames its call to action as a required verification, security check, or workflow prerequisite.
This attack tests whether visual prominence and apparent urgency cause the agent to prioritize the injected instruction over the authentic user goal.

Distraction Injection.
 
Distraction Injection places a non-modal notice or banner alongside the normal task interface.
The injected content commonly claims that the page state is outdated, inconsistent, or requires synchronization, thereby redirecting the agent toward an auxiliary action while leaving the original interface accessible.
It differs from Indirect Prompt Injection by presenting the payload as a separate warning or status notice rather than ordinary page content.

Ad Injection.
 
Ad Injection delivers the adversarial instruction through a designated advertising or sponsored-content surface, such as a promoted card or corner advertisement.
The payload uses promotional framing, such as offering a shortcut or task assistant, to make its call to action appear beneficial to the current workflow.
This attack evaluates whether the agent treats sponsored content as actionable guidance for completing the user’s task.

A.2. 
Statistics of Malicious Objectives

Malicious Task Categories.
 
The catalog defines 72 malicious objective templates, which produce 326 executable malicious instances after parameter instantiation.
Each instance fixes a concrete malicious target and the parameters evaluated by its attack verifier.
These instances are not complete benchmark cases: one objective instance can be paired with multiple compatible benign tasks and attack configurations to produce different executable cases.
We group the objective instances by their terminal website effects into five broad categories: browsing or navigation, lightweight action, content publishing, account configuration, and transactional commit.
This effect-based taxonomy groups semantically comparable objectives across websites despite differences in interface structure and terminology.

Observation Space.
 
Our implementation supports three observation presets derived from VisualWebArena 
(

)
: a text-only accessibility tree, a multimodal accessibility tree paired with the current viewport screenshot, and a set-of-marks representation that overlays numbered element identifiers on the screenshot.

B.3. 
Mutation Prompts

For each adaptive proposal round, we construct a JSON-serialized prompt that combines fixed mutation instructions with rollout-specific context.
The fixed instructions define the permitted modifications, output format, and validity constraints.
The rollout-specific context contains the parent attack plan, benign user goal, outcome category, verifier results, attack-funnel signals, delivery configuration, and site-specific catalog constraints.
The program additionally assigns 
 objective slots, each specifying a catalog-provided malicious objective, its parameters, action URL, attacker instruction, and a unique slot identifier.
The proposal model must yield one mutation per slot, preserving its assigned objective or parameters.

The mutation router determines which aspects of the parent plan may be revised according to its attack type and observed failure stage.
For user-level attacks, only the injected instruction may be revised.
For environment-level attacks, the prompt emphasizes placement and timing when the injection was not observed, CTA wording and visual salience when it was observed but not engaged, and continuation instructions when the malicious path was reached without completing the objective.
For successful seeds, the program may assign new catalog-backed objectives, while the proposal model varies only their expression and delivery.

The proposal model must return a single JSON object containing exactly 
 mutations with distinct slot identifiers.
Each mutation must preserve the catalog-provided attacker instruction and, when applicable, its action URL and CTA label.
The model may not introduce new objective parameters, entity identifiers, routes, verifier rules, rendering logic, HTML, or arbitrary CSS.

B.4. 
Mutation Output Schema

The proposal model does not directly generate executable attack plans.
Instead, it returns candidate revisions through a constrained JSON interface, allowing each revision to be bound to a program-assigned objective and validated before execution.
The output is a single JSON object containing a 
mutations
 array.
Each entry must bind to a unique assigned objective slot through 
slot_id

Table

No other fields are accepted.

The system normalizes the returned mutations and compiles them into executable attack plans before candidate selection.
It removes entries with missing or duplicate slot identifiers, unsupported fields, invalid values, or payloads that omit required catalog-provided instructions, URLs, or CTA labels.
It also rejects duplicate plans and candidates that cannot be instantiated by the site-specific compiler.
If fewer than the required number of valid mutations remain, the unfilled slots receive catalog candidates that pass the same compiler validation.

We report the wall-clock execution time of ANGLER across all 8 victim backbones and 9 websites.
For each valid formal rollout, we measure the elapsed time from the creation of its execution artifact to the completion of the final trajectory.
The measurement therefore includes victim-model inference, browser interaction, environment execution, and verifier evaluation.
It excludes candidate generation before rollout dispatch, queueing between rollouts, interrupted executions, and infrastructure failures that were not committed as formal experience records.

Table
 
12
 reports the mean execution time per valid rollout.

The results show that the runtime of ANGLER depends primarily on the latency of the victim backbone and the number of interaction steps required by each website.
Qwen3.7-Flash has the lowest average execution time at 63.9 seconds per rollout, followed by GPT-4o at 94.3 seconds and GLM-5V-Turbo at 109.2 seconds.
Qwen3-VL requires the longest average runtime at 299.7 seconds per rollout, with particularly long executions on Coursera and Slack.
GPT-6.1 Sol also exhibits substantial site-dependent variation, primarily due to long executions on Coursera and Walmart.
Because the victim models are served through a mix of local GPUs and remote APIs, these measurements represent practical rollout latency under our evaluation setup rather than controlled model-serving throughput.
