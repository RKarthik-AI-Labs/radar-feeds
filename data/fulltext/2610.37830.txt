Abstract.

LLM agents can turn a plain-English description into code that compiles, but whether the code behaves as required is rarely measured with validated instruments. We study this for smart contracts, the programs behind Web3 applications that move funds and cannot be changed once deployed. Starting from 600 existing contracts, we have an LLM describe each and measure implementation fidelity, the share of replayed transactions on which a generated contract behaves like the original. Three findings concern measurement. LLM judges, static analysis and LLM-based testers fail on planted mistakes, an answer key written from function names alone catches most conventional ones, and scoring only the functions all systems share, or adapting calls to each contract, hides omissions. Under exact replay, information supplied before generation matters most. Answers from a simulated client that reads the original contract raise fidelity by 19 to 23 points for three generator families, an optimistic estimate of what real authors would provide, and three to five well-chosen questions recover 60 to 75% of that gain. Stages after generation add at most about one point, and an automated security-repair loop costs 12.8 points. An elicitation-first pipeline reaches 72.9% on 500 held-out contracts, against 53.9% for one-shot generation and 39.3% for the original pipeline. We release the harness, tasks and scores.

Keywords: 
evaluation methodology, LLM agents, code generation, user simulation, LLM as judge, differential testing, smart contracts, Web3

1. 
Introduction

Agentic pipelines that turn natural-language requirements into code are now routine, and for many tasks the code compiles and runs. Whether it does what its author meant is a different question, and it is the one that matters when the code moves money. Smart contracts make this concrete. They are the back end of Web3 applications that people use through browsers and wallets, they hold and transfer value autonomously, cannot be patched after deployment, and fail expensively 
(
Atzei et al., 2017
; 
Chen et al., 2020
; 
Luu et al., 2016
)
. Several systems now synthesize Solidity from requirements with multi-agent pipelines 
(
Luo et al., 2025
; 
Chen et al., 2026
; 
Zhang et al., 2026
; 
Goel et al., 2026b
)
. Agents that act on Web services for a user face a related problem, since a natural-language request also underdetermines the intended behavior; contracts are a convenient place to study it because every action can be replayed exactly in a sandbox.

Evaluating such systems is hard for three reasons. The only statement of what is wanted is usually a description written in English, with no implementation to compare against. The instruments commonly used as proxies, such as LLM judges, static analyzers and compilation, measure something other than intent. And much of what a contract must do follows universal conventions that a model knows without reading the description, so an evaluation can reward conventions and look like it rewards understanding.

This paper is an evaluation study. We start from our earlier seven-phase pipeline 
(
Goel et al., 2026b
)
, whose evaluation used an LLM rubric judge and an LLM security gate 
(
Goel et al., 2026b
; 
Goel et al., 2026a
)
, ask how its output should be measured, and use the resulting instruments to locate where information is lost and which stages recover it. We distinguish author intent, compliance with a written specification and implementation fidelity, agreement with a given implementation on the same transactions. Because our tasks start from existing contracts, implementation fidelity is the construct we measure; it reflects intent only where the original contract embodies what its author wanted. Our central lesson is methodological. An evaluation of agents that turn specifications into programs must test its instruments on planted errors, control for what models know without the specification, and replay exactly what it claims to check. Each of these changed a conclusion here, the last one through an external audit of our own scorer.

3. 
Study Design

Corpus.
 Contracts come from FSM-SCG 
(
Luo et al., 2025
)
. Its implementations are not all reliable ground truth, since 35.1% of the 21,976 contain placeholder markers and 27.8% a comment-only function body. We keep non-stub contracts of at least 40 lines that compile at their declared Solidity version, deploy, and contain at least one contract-specific rule, meaning logic outside token and ownership plumbing. The development experiments use 100 such contracts and the scale replication 500 further contracts, none an exact duplicate after removing comments and whitespace; 12 share at least 90% of their token 5-grams with a development contract, and excluding them moves no gap on the 500 contracts by more than 0.4 points. For each contract an LLM (Gemini 2.5 Flash) writes a short description of about 140 words, as a client might, and a complete requirements document of about 1,700 words that states every rule with exact values.

Simulated client.
 We use GPT-5.4 reading the real contract and answering each question in at most two sentences of plain English without mentioning code. Because the descriptions and the answers both derive from the original contract that fidelity is scored against, an elicitation gain measures how much of a hidden implementation a question recovers. It is an optimistic estimate of what a human author would provide under this simulator, not a measurement of it (§
6
).

Executable reference models.
 A writer model, called separately from the generator, receives the description, the contract’s public interface and the deployment parameters, and returns a Python class with one method per public function. Methods take the caller first, raise 
Revert
 when the description says a call must fail and read the block time and attached ether from the harness. Models run in a separate process without imports and with restricted builtins; a reverted call restores the model’s state and class-level state is reset between sequences, both covered by known-answer tests.

 Reference models are fallible pipeline components. They are the object of the oracle-validity experiments, and inside the elicitation-first pipeline they flag candidate disagreements for the client to adjudicate; they never score generated contracts, which are always compared with the original Solidity contract.

Transactions.
 For each contract we generate 60 random sequences of 8 steps over its state-changing functions. Callers are drawn from three roles. Arguments mix small values, boundary values and values seeded from contract literals and getters with their neighbors; 15% of steps advance the clock by an hour to a year; payable functions receive ether. Contracts run in an in-process EVM compiled at their declared version.

Measure 1, oracle validity.
 To test whether a reference model knows the required behavior, we plant one-rule mistakes into real contracts and keep an untouched twin 
(
Jia and Harman, 2011
)
. A mistake is exposed if some transaction makes the twin and the mutant behave differently. Because outcomes are binary, disagreeing with the mutant somewhere is passed by a coin flip, so we use strict side-picking. Over exposing transactions we count how often the oracle sides with the twin and how often with the mutant, and the mistake is caught only if the former is larger. Two uninformed oracles, always succeed and always revert, expose class-specific shortcuts, and a description-free control writes the reference model from function names alone.

Measure 2, implementation fidelity.
 The original contract is the oracle for every fidelity number. We replay held-out sequences on it and on each generated contract, each continuing from its own state, so a step after a first divergence is still scored on its own. The required interface is every state-changing function of the original, the same for all systems. Replay is exact. Each step calls the original’s signature with its argument types and attached ether, so a missing or changed signature fails the step and ether sent to a non-payable function reverts, and the chain clock is fixed so that every original scores 100% against itself. A step is correct only if its outcome matches and, when it succeeds, every observed value changes as in the original; a change the generated contract does not expose is not credited. Observations cover up to 39 numeric, boolean and address-valued getters and the ether balance. Transaction-level fidelity is a contract’s share of correct contract-specific steps, averaged over contracts; we also report the share of contracts that match the initial state and pass every sampled step, and the shares of required functions and value changes that can be observed. A system that never builds scores zero.

Statistics and criteria.
 Intervals are 95% percentile bootstrap intervals over contracts with 2,000 resamples, paired for differences and conditional on one generation per condition, so they omit sampling variability. Each experiment states pass or fail criteria in its script; ten were committed together with their results and are marked as such (Appendix 
E
). We test 36 criteria without correction for multiplicity, and we call an effect detectable when its interval excludes zero and meaningful when it also meets its criterion.

Generated contracts.
 Elicitation also helps the contracts a generator writes (GPT-5.4-mini, 92 contracts). Transaction-level fidelity is 55.6% from the short description, 79.4% with the interviewer’s answers, 76.0% with the checklist answers and 91.0% from the complete document. Unlike for reference models, neither elicitor closes the gap, and the checklist does not beat the interviewer (

Checklist answers describe behavior only and leave argument types and stored values to the generator, so its contracts implement fewer required signatures (88.7% against 94.8% with the interviewer and 95.3% from the complete document) and expose fewer of the original’s values (78.6% against 92.0% and 98.6%). The complete document also yields far more contracts that pass all sampled tests (59% against 21%). The gain does not depend on the generator. With Claude Sonnet 5 the checklist answers raise fidelity from 56.1% to 75.1% (

Is the gain an artifact of synthetic descriptions?
 Our descriptions are written by an LLM from the real contract, so some contain false statements that elicitation then corrects. An auditor model (GPT-5.4) compared each short description with its contract. It found at least one contradiction in 76 of 100 descriptions, most often an access rule that does not exist (“an administrator can open trading” when anyone can), and on average 14.9 omitted contract-specific rules. Elicitation therefore often corrects misinformation as well as filling omissions. On the 24 descriptions without any contradiction the checklist gain is still

) and the audit is itself an LLM judgment. A simulated client generated from the answer can silently correct the inputs of the systems it evaluates 
(
Balog and Zhai, 2025
)
, and splitting results by audited input quality is a cheap check.

An omission-only example.
 The description of a liquidity-management contract, which the audit found free of contradictions, lists its states and operations but never says who may call them. Generated from it, the contract restricts pausing and resuming to an owner and makes withdrawals depend on an ether balance, matching 25% of transactions. The single answer to “anything unusual” (all operations are open to any account, and no token accounting exists) raises fidelity to 100%.

4.4. 
RQ4. What do the pipeline’s stages do?

Security-driven rewriting.
 With complete requirements as input, generation alone reaches 95.3% fidelity on 94 contracts. The original pipeline’s audit then rates most contracts high or critical, its refiner rewrites 86, and fidelity falls to 82.5%, a loss of 12.8 points 
 with 60 contracts worse and the share passing all sampled tests falling from 62% to 23%. Fidelity and safety are separate outcomes, and a change that violates an unsafe specification can still be justified, because the original contracts can be permissive. We therefore had GPT-5.4 classify a capped selection of behavior changes against the complete requirements, 341 deduplicated success-or-revert changes in the 72 rewritten contracts, at most six per contract, drawn from 4,886 changed steps. Of the selected changes, 80% break a stated requirement, 14% block a genuine vulnerability that the requirements do not ask for and 6% are not decided by the requirements. These labels are not human-verified. On the 51 contracts with no justified fix among the selected changes, fidelity falls by 17.4 points. The loop mostly removes behavior the client asked for rather than trading it for safety (Figure 
4
); 44 of the 49 justified fixes add a restriction that could have been put to the client as a question.

Reference-model verification.
 Repairing contracts where they disagree with a reference model has no detectable effect (
 
) when requirements are complete. The instrument’s validity does not transfer from planted to real mistakes. The complete-description model catches 94.3% of planted conventional and 87.5% of exposed contract-specific mistakes, but on real generation defects, the 3.2% of steps where a generated contract differs from the original, it sides with the original only 31.6% of the time on a common set of 1,217 outcome disagreements, against 80.4% for always succeed. Most residual defects are conservative checks the description never mentions, which a model written from it repeats. Only 34.8% of its flags mark real defects, an elevenfold enrichment over the 3.2% base rate but wrong more often than right. Description-derived checkers verify what a description states and cannot adjudicate its silences, so their flags go to the client as questions.

Distributions.
 The original pipeline scores zero on 25.5% of contracts, mostly because nothing it delivers builds (Figure

Its gain is largest on contracts that are not tokens, sales or NFTs, where the original mostly fails by omission (55% against 87% of required functions).

What still goes wrong.
 Of the steps the elicitation-first pipeline gets wrong, 45% call a function the contract lacks or declares with different argument types, 29% have the wrong outcome, 6% the wrong change in a balance, counter or state, and 20% change a value the contract does not expose; 202 of 499 contracts lack at least one required signature. Descriptions name operations but not argument types, so much of this is interface guessing that a typed interface in the request would remove.

Metric sensitivity.
 The earlier evaluation of this pipeline 
(
Goel et al., 2026a
)
, like many comparisons, scored only functions all systems implement on contracts where all build. Figure 
7
 scores the same outputs four ways. The shared-interface metric reports 95% for the elicitation-first pipeline and 76% for the original, a gap of 19 points on 364 contracts. With a fixed required interface the gap is 35 points on 499 contracts, and 34 under exact replay. Restricting to a shared interface removes 28% of the original’s contract-specific functions in a typical comparison and with them the failures of the system that omitted them, and excluding contracts where any system fails to build removes 27% of the sample, mostly failures of the original pipeline.

Auditing our own scorer.
 An external audit of the previous version of our scorer found four ways a wrong contract could score 100%. Calls were adapted to the generated contract’s own signatures, ether was dropped for non-payable functions, a value change the generated contract did not expose was skipped, and only changes, not initial values, were compared. Under that version 43.9% of the elicitation-first pipeline’s contracts passed every test, but 162 of those 219 had an unobserved value or a missing or mismatched function. The scorer used throughout this paper replays exactly and passes known-answer tests built from all four counterexamples. It lowers fidelity by 12 to 14 points for every system and the pipeline’s pass rate to 19.6%, yet moves no gap between systems by more than 1.2 points. Every rule we tried preserves the ranking, but absolute fidelity, gap sizes and pass rates depend on the rule, so all should be reported with interface and observation coverage.

5. 
Discussion

Lessons for evaluating generative pipelines.
 Several evaluation choices changed our conclusions, and reporting failures mattered as much. Eighteen of our criteria failed, and consistently so. No agent applied after the requirements were fixed produced a meaningful gain, targeted questioning never beat the generic checklist by its margin, and adaptive stopping missed its margin. We would ask the following of any evaluation of systems that turn natural-language requirements into executable artifacts.

(1)

Validate every instrument on planted errors with untouched twins, and report its false alarms next to its detections.

(2)

Include a control that withholds the specification, and report how much of a score survives without it.

(3)

Score a fixed required interface by exact replay, count outputs that do not build as failures, report coverage and pass rates, and test the scorer on known wrong answers.

(4)

When users or inputs are simulated from the answer, audit the inputs, report results separately for inputs the simulator could have repaired, and treat the gains as optimistic.

(5)

Fix pass and fail criteria before running, and report the failures with the same prominence as the successes.

What the results say about pipeline design.
 In the configurations we tested, information gathered before generation mattered far more than anything after it. A few broad questions recover much of it, and verification is best used as an alarm that enriches real defects but is usually wrong, so its disagreements go back to the client. Automated security repair should turn its findings into questions rather than rewrite. Architecture matters mostly by not destroying information.

Implications for decentralized and Web applications.
 Smart contracts are the logic layer of decentralized Web applications, so these findings bear directly on how contract-writing agents for them should be evaluated. We hypothesize, without having tested it, that Web agents that act on a user’s request share the same problems, a request that underdetermines behavior, judges that stand in for users and simulated users that can leak the answer, and that replayable sandboxes, description-free controls and scored clarification would transfer to them.

6. 
Limitations

Construction and simulated client.
 Descriptions and answers are generated from the contract that fidelity is scored against, so we measure implementation fidelity under incomplete information, not author intent. No human answered our questions; real authors may be unsure or inconsistent, or may volunteer more, so elicitation gains are optimistic estimates under this simulator. We had no independently authored specification or expert-written tasks, and no controlled omission-only condition. 
Originals as intent.
 We treat the original contract as the intended behavior even where it lacks access control. The security classification addresses this, but its labels come from an LLM, cover a capped selection of outcome changes and were not verified by people. 
Coverage.
 Observations exclude events and ether received by external accounts, and random sequences do not expose every rule. 
Baselines and scope.
 The pipeline baseline is our earlier system and one-shot generation, not ClarifyGPT or TiCoder. All contracts come from one corpus and one language, generator families share a compile-repair step, and criteria are not corrected for multiplicity. The pipeline’s verification stage ran before the reference-model runner was fixed and was not rerun, so its sub-point benefit is provisional; intervals omit generation-to-generation variability.

7. 
Future Work

Human authors.
 The most important next step is a study with people who commission contracts and write their requirements before any implementation exists, which would measure intent rather than implementation fidelity and the effort that answering questions costs a person. 
Autonomous agents that transact.
 LLM agents increasingly hold wallets and call contracts for their users, paying, trading or settling escrow, and agents may negotiate and transact with one another. The same replayable sandbox could evaluate such agents end to end, scoring whether each transaction an agent sends matches its user’s request, whether the agent that writes a contract and the agents that use it read it the same way, and when an agent should ask its user before moving funds. 
Security as questions.
 A security agent that phrases each finding as a question to the client would keep the justified fixes without the regressions. 
Broader settings.
 A second corpus, comparisons with published clarification systems, repeated generations and other languages would test how far the findings generalize.

8. 
Conclusion

Evaluating agentic code synthesis requires instruments that are themselves tested, controls for what models know without the requirements, a scorer that replays exactly and does not hide omissions, and checks on the simulated users that stand in for authors. Each of these changed a conclusion in the earlier evaluation of this pipeline or in our own. On measurement, LLM judges, static analysis and LLM testers failed on planted mistakes, a description-free control showed that conventional benchmarks largely reward conventions, and shared-interface scoring and adapted replay hid omissions until exact replay and known-answer tests exposed them. On pipeline design, information supplied before generation mattered far more than anything after it. Elicited answers raised fidelity by 19 to 23 points across three generator families, while review, repair and triage added at most about one point and security rewriting removed required behavior. On elicitation, three to five well-chosen questions recovered 60 to 75% of what a simulated client could supply, and question value could be ranked without the original contract, although which questions matter depended on errors in the synthetic descriptions. A pipeline rebuilt on these findings reaches 72.9% implementation fidelity on held-out contracts against 53.9% for one-shot generation and 39.3% for the original, yet only 20% of its contracts pass all sampled tests, a gap that studies with human authors should address next. All code, tasks, client transcripts and scores are released (Appendix

Appendix F 
Prompts

Description writer.
 Writes the 120 to 200 word description a product owner would write, naming operations but without code; the complete document states every rule with exact numbers and boundaries.

Generator.
 Implements every described operation as one self-contained Solidity 0.8.20 contract with the given name, without imports.

Reference-model writer.
 Given the requirements, public interface and deployment arguments, writes 
class Model
 with one method per function, sender first, raising 
Revert
 when a call must fail and choosing the most conventional behavior where the requirements are silent.

Checklist questions.
 (1) limits or caps on amounts, with exact values and inclusiveness; (2) prices, rates or required payments; (3) fees and how they are calculated; (4) time windows, deadlines or waiting periods; (5) phases or states and the operations each allows; (6) operations restricted to accounts or roles, and who holds them; (7) freezing, pausing, blacklisting or whitelisting; (8) how balances or supply change per operation; (9) which operations should fail and when; (10) anything unusual a developer might get wrong.

Simulated client.
 Reads the original contract and answers each question in at most two plain-English sentences with exact numbers, describing behavior only and nothing beyond the question. For triage it sees two options in random order and answers 1, 2 or 0 for neither.

Appendix G 
Case Study and Transcript

The short description of an NFT key contract says an administrator changes the sale status and adds addresses to the gold list, but the real contract has no privileged role. One-shot generation and the original pipeline implement the conventional reading; the answer to the roles question corrects it.

•

Which operations are restricted to specific accounts or roles?
 “No operation is restricted to a privileged owner, admin, or special role. Any account may add any address to the gold list, change the sale status […] and mint only if its own address is on the silver or gold list and the sale is live.”

Appendix H 
Resource Documentation

Contents.
 For each of 600 contracts (100 development, 500 replication) the release contains the original source, the short description, every generated or repaired contract and per-contract scores; the development contracts also have complete requirements, client answers, interviewer transcripts and reference models. Original-pipeline records keep the final contract and a log tail, and its code is not redistributed.

Models.
 Descriptions were written by Gemini 2.5 Flash. Reference models were written by GPT-5.4, Gemini 3.1 Pro (preview), Gemini 3.5 Flash, Claude Sonnet 5 and, in the pilot, Claude Sonnet 4.5. Contracts were generated by GPT-5.4-mini, and in the replication by Claude Sonnet 5 and Gemini 3.5 Flash (9 of 372 requests returned nothing usable and count as never built), with the same GPT-5.4-mini compile repair for every family. The client, auditor, security classifier and question agents use GPT-5.4.

Cost and samples.
 On the 500-contract run, everything but the uninstrumented original pipeline used about 4.2 million GPT-5.4, 4.5 million GPT-5.4-mini and 0.8 million Gemini 2.5 Flash tokens; grading needs no model calls. Development experiments include the contracts whose earlier stages produced output (93 to 97 of 100), minus one with no scorable contract-specific step, as does the scale run (499 of 500).

Licensing, ethics and reproducibility.
 Sources keep the FSM-SCG license; no personal data is involved and no contract was deployed publicly. Every number can be recomputed from cached outputs, and the repository linked in the introduction maps each table and figure to its script.
