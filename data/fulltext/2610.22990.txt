Abstract

Computer-use agents (CUAs) are commonly evaluated against fixed task specifications, but users may omit requirements, add constraints, or require approval before consequential actions. Completing the benchmark instruction does not guarantee serving the person who asked. We introduce PersonaCUABench, which holds 74 tasks across 11 domains fixed and varies only who asks. A persona agent, playing one of 44 personas in four groups, rewrites each instruction in that user’s own words and answers the CUA’s questions, while the CUA sees only the dialogue, never the profile or the original instruction. Across nine backbones (3,330 runs), mean task completion falls by 36% relative to the original requests. The losses have two sources: in 59.9% of cells that lose points, the agent engages with what the user asked for and still gets it wrong, and 11.2% are stops the user requested that the checker scores as failures. Even when a persona request is fully completed, the user gives the top satisfaction rating in only 62.7% of cells, against 84.1% for the original requests. CUAs should therefore be evaluated not only on task completion but also on whether they meet the requirements and constraints users express.

Computer-use agents (CUAs) increasingly perform multi-step tasks in web browsers and desktop applications, from gathering information to making reservations and sending messages 
(
Garg et al., 2025
)
. Existing benchmarks primarily evaluate whether agents complete predefined tasks 
(
Zhou et al., 2024
; 
Xie et al., 2024
)
, including increasingly challenging long-horizon settings 
(
Jang et al., 2026b
; 
Yuan et al., 2026
)
.
In real-world use, however, users may express goals incompletely, introduce personal constraints, or request confirmation before consequential actions. Satisfying a predefined task specification can therefore differ from serving the person who made the request. A fixed specification cannot reveal this gap, which raises our question: 
when different people ask a CUA for the same task in their own words, does it serve each of them, or only the task?

Serving the person is harder than completing a fixed specification. The agent must infer what the user leaves unsaid and judge when to ask or confirm before acting, and for a CUA these judgments are consequential: a misread request can mean money spent, an email sent, or more disclosed than the user intended 
(
Goel and Gurevych, 2026
; 
Hu et al., 2026
)
. Success is also user-dependent. An agent that drafts an offer and stops may fail a checker written for sending it, yet do exactly what a cautious user asked. Completing the specified task and serving the person can thus come apart, so an evaluation of CUAs needs to measure both.

Prior work makes agents personal by giving the agent stored information about the user: a logged profile, a long-term history, or a logged-in environment 
(
Cai et al., 2025
; 
Kim et al., 2026
; 
Jang et al., 2026a
)
. We give the agent no profile. It learns who the user is only from the request and from the user’s answers to its questions. Each user is built from attributes of the MatrAIx persona schema 
(
Li et al., 2026
)
. Holding the task fixed and changing only who asks isolates the effect of who is asking.

We introduce 
PersonaCUABench
 (Figure 
1
), built around a persona-conditioned request protocol: a persona agent is given a profile and the original instruction, writes the opening request in that person’s own words, and answers the CUA’s clarifying questions in character, so the CUA works only from the dialogue. The tasks come from existing benchmarks so that outcomes stay independently checkable: information tasks on live websites and action tasks on sandboxed replicas of real sites, across everyday and work scenarios in 11 domains. Each task is asked by the four personas of its domain, one per group (
expert
, 
senior
, 
young
, 
practical
), and by an original request that passes the instruction unchanged, without a persona. Because a request can leave requirements unsaid, we score whether the user raised each requirement, whether the agent engaged with it, and whether it was met, and we report this diagnosis alongside task completion and the user’s own satisfaction.

Evaluating nine backbones in one shared browser harness, we find that a persona-phrased request lowers average task completion from 0.689 to 0.441 with every backbone losing between 28% and 45%. The diagnosis locates two sources of this loss: in 59.9% of the cells that lose points the agent engages with what the user raised yet still gets a requirement wrong, while another 11.2% are stops the user asked for that the original checker counts as failures. We further find that task completion and user satisfaction diverge in both directions
and that, on GPT-6 Astra, neither revealing the user’s profile nor requiring a clarification question is sufficient to recover the loss in task completion. PersonaCUABench thus provides a controlled testbed for personal CUAs: it compares different personas on the same tasks, diagnoses how user requirements are handled, and measures task completion and user satisfaction.

We draw tasks from two recent benchmarks that together cover what users ask computer-use agents to do: find information and take actions. Odysseys 
(

Experiments

4.1 
Setup

Our experiments are a controlled comparison in which only two things vary, the execution backbone and the persona condition, while the tasks, the user model, the environment, and the scoring are held fixed. Table 
3
 lists the nine backbones that serve as the agent under test, in order of release: MiniMax M3, Kimi K3, Muse Glimmer 30B, Grok 4.6, Qwen 3.8 27B, Gemini 3.8 Flash, GPT-6 Astra, DeepSeek V4.1 Flash, and Claude Opus 5.5. Each is run on the same 
 cells of Eq. 
4
: every task under its four domain personas and under the original request.

Everything else is held constant. At the judge stage, GPT-5.6-terra fills two separate roles. One instance plays every persona agent and rates its own satisfaction in the same conversation after the episode. A fresh instance, which shares no context with the persona agent, serves as the objective judges, scoring each requirement against the rubric, and labels the loss cells.
All nine run in one harness with the same text tools and the same budget, at most 
 agent turns and 
 calls to 
ask_user
 per episode, with the agent and the persona agent both sampled at temperature 1.0, and we log the tokens and API cost of every call. Appendices 
B
 further describes the harness, the cost, and the human annotation that checks the judges.

5.1 
Task Completion vs. User Satisfaction

Figure 4: 
A 
practical
 user’s case, run by DeepSeek V4.1 Flash. Appendix 
D
 gives one case for each of the other three groups.

Task completion is judged against the original instruction, while simulated users rate how well the outcome meets their requests. At delivery, mean satisfaction is 4.04 for the original request and 3.10–3.59 across persona groups (Figure 
3
). Yet completing the task does not guarantee satisfaction. Among 646 fully successful persona cells, only 62.7% receive the top rating of 5 and 25.9% receive 3 or lower, compared with 84.1% and 9.5% for fully successful original requests.

Conversely, users often perceive failed tasks as complete. Among 800 failed action cells under personas, 56% are judged done at delivery, falling to 27% after site-state verification. Two factors contribute to this mismatch. First, 138 of the 343 action loss cells involve correct stops requested by users, 62% of which are judged done at delivery. Second, agents sometimes misreport outcomes: final replies are inconsistent with the outcome in 45% of information loss cells and 26% of action loss cells. Among the remaining 205 action loss cells, misreporting is associated with higher satisfaction (3.47 vs. 3.13) and the share judged done (55% vs. 41%; Table 
18
).

Together, these findings show that task completion and user satisfaction diverge in both directions: fully successful tasks can leave users dissatisfied, while failed tasks can seem done because agents correctly stop or misrepresent their outcomes.

Case Study: Good Score, Unhappy User

Figure 
4
 follows one 
practical
 user who asks for a simple dinner from a store’s buy-one-get-one offers. The agent engages with the request but suggests pork chops or steak with bacon or sausage, so it meets three of four rubric items, and the user’s rating of 2/5 names this list of options. A partial score can thus hide how far an answer falls from what the user asked.

5.2 
Where the Drop Comes From

The previous subsection shows how users perceive the results. To trace how the drop arises, we take the 1,230 loss cells, the persona cells that score below the original request on the same task and backbone, and give each one a primary cause. A cell that ends without the final submission is a stop, either one the user asked for by requesting a draft, a review, or to finish the action themselves, or one the agent made on its own. For every other cell we look at the requirements it lost and take the earliest break between the user and the outcome. The user may never have raised the requirement, the agent may not have engaged with a requirement the user raised, or the agent may have engaged with it and still not met it. Figure 
5
 shows the shares.

Figure 5: 
Primary cause of each loss cell, nine models pooled. Each cell has one cause. (a) All 1,230 loss cells. (b) Each persona group, with its number of loss cells.

Most loss cells arise from how agents act on what users say. In 59.9% of loss cells the agent engaged with the requirements the user raised and still missed at least one of them. Only 17.1% lose points solely on requirements the user never raised, and 2.1% on a raised requirement that the agent never engaged with. The remaining 20.9% end before the final step. In more than half of these, 11.2% of all loss cells, the user had asked for a draft or a review first, so stopping is what the user wanted even though the checker scores it as a failure.

The mix of causes differs by group. Requirements the user never raised account for 22.9% of the losses of 
senior
s against 6.2% for 
expert
s, so non-experts leave more unsaid. Stops that the user asked for account for 20.2% of 
expert
 losses and 16.7% of 
practical
 losses, against 3.5% for 
young
 users. This is consistent with 
expert
 requests reaching the lowest task completion in professional and tying for the lowest in productivity, the two action-only domains of Figure 
3
.

This analysis reveals that most loss cells arise after the agent has heard the requirement. Users leave some requirements unsaid, most of all 
senior
 users, but the larger share of loss cells comes from raised requirements that the agent engages with and still gets wrong. The rest is largely stops that the user asked for, where following the user conflicts with the original checker.

5.3 
Interventions

The analyses so far are observational. To test whether more information about the user, or more interaction with it, recovers the loss, we rerun GPT-6 Astra with one change at a time. Both runs reuse the opening requests of the main experiment and keep the tasks, tools, budgets, persona agents, and judges fixed. The profile-visible run reruns the 296 persona cells with the user’s profile added to the agent’s input. The forced-question run reruns all 370 cells, including the original requests, and requires the agent to ask the user at least one question before it acts. Appendix 
C.6
 gives the full results.

Intervention 1: Showing the agent the profile.

With the profile, answers are longer for 
expert
 users and shorter for 
senior
 users. Information-task completion decreases by

), with the largest estimated decline among

Intervention 2: Forcing the agent to ask.

When the agent must ask before it acts, every cell contains a question, yet task completion on persona requests does not recover, moving from 0.434 to 0.421. On action tasks with the original request the extra question even lowers task completion from 0.583 to 0.472, because the persona agent answers with constraints absent from the instruction. Questions also rarely reach what the user left unsaid: only 24% of the 609 questions in the main experiment target an omitted requirement.

7 
Conclusion

PersonaCUABench poses the same computer-use tasks for different users, and persona requests lower task completion from 0.689 to 0.441 across nine backbones. Most loss cells arise after the agent has engaged with what the user raised, and another 11.2% are stops the user asked for that the checker scores as failures. A fixed specification thus conflates how well the agent executes with how far the user’s request departs from it. On GPT-6 Astra, neither showing the profile nor requiring a question closes the gap: the bottleneck is carrying what the user said through a long sequence of actions. As completion and satisfaction also diverge, personal CUAs should be judged against the user’s request and from the user’s side, with simulated users validated against real ones.

Limitations

PersonaCUABench spans 11 domains drawn from everyday and work settings and evaluates nine general-purpose backbones in a shared browser harness. Its tasks focus on finding information and taking actions on websites, leaving desktop applications, standalone chat, and coding workflows outside its scope. Each episode begins with a single request and focuses on one task, whereas personal agents in real-world use can accumulate knowledge about their users across interactions. Future extensions could evaluate repeated interactions with persistent user memory and extend the intervention study to additional backbones.

Ethical Statement

PersonaCUABench uses constructed personas and LLM-simulated users. Information tasks access live websites, while action tasks run on sandboxed replicas to avoid real-world transactions or communications. We acknowledge that persona construction may encode stereotypes and cannot capture the full diversity within demographic groups. Accordingly, performance differences should not be generalized to real populations, and simulated satisfaction ratings cannot replace feedback from real users. Our benchmark aims to improve user-aligned evaluation and highlights the importance of respecting user intent and obtaining authorization before consequential actions.

A.1 
Task Curation

Selection.

Odysseys contains 200 live-web tasks and REAL 112 tasks on replicas of 11 websites. From the candidates we considered in the two sources, we dropped 20 tasks: 12 live-web tasks whose site blocked automated access or did not load, three REAL tasks on the eleventh replica (Omnizon), whose host was unreachable from our network, two pure navigation tasks that leave no room for preferences, two duplicates of kept tasks, and one task that requires watching a video. Our action tasks therefore use ten of the eleven REAL websites. By the source benchmarks’ own labels, the information tasks are 18 easy and 20 medium, and the action tasks 35 medium and one hard.

Requirements of REAL tasks.

A REAL task comes with one instruction and one pass/fail checker. To analyze intent on these tasks, we derive the requirements that each checker tests from the task manifest and the checker’s code (e.g., “the order includes a pizza” and “the order total is under $30”), phrase them as what the user wants, and review them by hand. These 107 requirements serve the intent measures of §
2.3
.

Domains.

Each task belongs to one of 11 domains, assigned through its website. A domain can group several websites. Travel, for instance, combines five Odysseys tasks with REAL airline, lodging, and ride-hailing replicas, whereas professional and productivity contain only REAL tasks. The tasks span two scenarios, 40 life and 34 work tasks. Figure

 (top) shows how the 74 tasks spread over the 11 domains.

  01  Role and Profile

Preamble.
 You are role-playing a person with the following profile. Stay fully in character: let these traits shape your choices and language naturally, the way a real person with this profile would behave. Do not announce that you are role-playing.

# Your profile
  

  02  Situation and Request

# Right now

You need help with something, and you are about to ask an AI assistant that can browse the web to do it for you.

Below is a complete checklist of what would fully satisfy you. An expert wrote it, not you: its website names, step order and instructions about tabs are the expert’s, and most people would never phrase a request like that. Use it only to know what you are after.

Now ask for help the way YOU actually would, given who you are:

– Talk about your situation and what you want to find out or decide—not a step-by-step procedure, unless you are the kind of person who writes those.

– Mention a specific website, tool or technical step only if someone with your background would know it and care about it. Otherwise describe what you want in your own terms, or leave it out.

– Say as much or as little as you really would. Leaving things unsaid that you would not think to mention is fine—the assistant can ask.

– Use your own vocabulary and tone. Write it from scratch: do not copy or closely paraphrase the checklist’s sentences, order or structure.

  03  Persona Expression

Let your profile show. Someone reading only your message should be able to tell what kind of person wrote it:

– 
Language:
 match your education, language background and tech-savviness in word choice, grammar and jargon (or the lack of it). If English is not your first language, write the way you actually write English.

– 
Length and shape:
 match your patience, attention span and taste for detail—a quick line, or a long message full of context.

– 
Your circumstances:
 bring in the parts of your life that bear on this request—budget, schedule, family, health or accessibility needs, the device you are on, how much risk you accept—the way you naturally would, often in passing rather than as a list of requirements.

– 
What you want back:
 say how you want the answer (just the gist, every detail, sources, step by step) only if you are the kind of person who would say so.

Show these traits the way a real person does. Never list your profile or label yourself (“I am risk-averse”, “I have low tech-savviness”).

  04  Clarification Replies

When the assistant asks you something, answer as yourself, truthfully according to the checklist—including details you left out at first, if you are asked about them. If it asks about something the checklist does not settle, answer the way you plausibly would, consistent with your profile (your budget, needs, habits and tastes). Keep replies short and natural. Never say you are an AI, a simulation, or that you were given a task or a checklist.

Task completion.

The evaluation procedure 
 takes one of two forms. An LLM rubric judge decides each 
 from the agent’s final answer 
, its action log, and the tabs 
 left open, applying each requirement’s verification condition: a requirement that a page be left open is met only if that page is among the open tabs, a reported figure counts only if the agent visited a page that shows it, and a requirement naming a specific site is met only by that site. The judge does not see the dialogue, so 
 depends only on the outcome. A programmatic checker instead reads the site’s final state 
 and returns one verdict 
, which sets

User satisfaction.

Satisfaction is rated by the persona agent 
 that made the request, so each rollout is assessed by the person it was meant to serve. After the episode, 
 is rebuilt with its profile 
, its goal 
, and the exact conversation it had with the agent, and is shown what a user would see: the agent’s final answer 
 and the tabs 
 left open. Staying in character, it returns a satisfaction score from 1 (very dissatisfied) to 5 (very satisfied), whether it believes the agent did what it asked (yes, no, or unsure), and a one-sentence reason. For action tasks it is asked a second time after verification, when it is also shown what changed on the site. For the original request, 
 rates without a profile. Only the latest scored run of each cell is rated. Because 
 is rebuilt with 
, its rating can draw on the original instruction as well as on what it asked for. Appendix 
C.3
 discusses what this means for stops the user asked for. 
Appendix 
B.5
 compares both rating stages with human satisfaction annotations on the 22 selected tasks.

We also ran an external judge, used only to check the user’s rating in Appendix 
C.3
. The external judge, GPT-5.6-terra, sees the persona’s profile, the original instruction 
 (marked as unseen by the agent), the full dialogue, the agent’s actions, its final answer, and the open tabs. It judges the agent against what this person said and who they are, and scores five dimensions on a 1–5 scale (or n/a when the rollout gives no evidence):

•

P1 Asked-for
: whether the agent delivered what this person stated, clearly implied, or confirmed when asked.

•

P2 Readable
: whether this person can read and understand the answer, given their vocabulary, technology familiarity, attention span, and constraints such as low vision or a phone.

•

P3 Actionable
: whether this person can act on the answer without help they lack, with concrete next steps, prices, times, and links, and with the pages they asked for left open.

•

P4 Gap handling
: whether the agent noticed what this person left unsaid, through a question, a stated assumption, or a flagged risk.

•

P5 Overall
: whether this person would say they were well served, judged as a whole.

The judge also lists explicit requests that went unmet and unstated needs that the agent missed.

B.3 
API Cost

For each cell we log tokens (including cached and reasoning tokens), monetary cost, wall-clock time, and step count, with judging cost kept separate from agent cost. Table 
10
 reports the API cost over the cells in the paper, using the latest scored run of each cell. We cost every agent backbone at its list price per million input and output tokens, without cache discounts, so that the backbones are comparable. Providers bill cached input at a discount, and 68% of all agent input tokens are cached, so the billed cost is lower than the list cost. Over the eight backbones with a list price, the agent costs 4,737 USD, or 1.60 USD per cell. The cost per cell ranges from 0.26 USD for DeepSeek V4.1 Flash to 3.26 USD for Kimi K3 and follows the price per token more than the number of steps. Muse Glimmer 30B has no list price, so we report its tokens only.

The persona agents and all automated judges run on GPT-5.6-terra, for which the run records contain tokens but no price. We estimate their cost at its list price of 2.00 USD per million input tokens and 12.00 USD per million output tokens, again without cache discounts. This gives about 202 USD over all nine backbones, or 17 to 26 USD per backbone, an order of magnitude below the agents. The estimate covers the persona agents’ replies to questions, the rubric, intent, external, and fidelity judges, and the satisfaction ratings. It leaves out the generation of the opening requests.

We check the GPT-5.6-terra judgments against annotations from two human annotators, P1 and P2. The annotation set contains 22 tasks, with two representative tasks selected from each of the 11 domains.
