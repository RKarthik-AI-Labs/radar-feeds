Abstract

Retrieval-augmented generation (RAG) over visually rich documents must
find both relevant content and the evidence that supports an answer.
Screenshot retrieval preserves images and page structure, but written
facts within screenshots also need to be searchable.
Moreover, topical relevance alone does not identify which retrieved
tile contains evidence for the answer.
We introduce Pix2Evidence, a multimodal RAG system that encodes each
screenshot tile together with its available transcription into a
single fused image–text representation, so that layout and readable
text are considered jointly during retrieval.
To guide evidence selection, a vision-language teacher describes the
visible content that supports each training question.
We use these descriptions to adapt the retriever, then rerank the
retrieved candidates before answer generation. Extensive experiments demonstrate that Pix2Evidence outperforms state-of-the-art methods.
Across five widely-used Wikipedia QA benchmarks, the non-reranked Pix2Evidence leads the main
comparison in answer accuracy on four.
On MMSearch, it reaches 26.0%, 4.4 percentage points above PixelRAG.
We will release the code and share derived data where licensing
and privacy reviews permit.

1 
Introduction

Retrieval-augmented generation (RAG) grounds answers in an external
document collection 
(
Guu et al., 2020
; 
Lewis et al., 2020
)
.
A retriever selects candidate sources, and a reader generates an answer
from the material it receives 
(
Karpukhin et al., 2020
; 
Izacard and Grave, 2021
)
.
Open-domain QA often uses web content: Natural Questions pairs queries
with Wikipedia pages 
(
Kwiatkowski et al., 2019
)
, while WebQA draws on both visual and
textual web sources 
(
Chang et al., 2022
)
.

Vision-based retrieval can preserve information that is difficult to
capture as plain text, including images, tables, and page layout.
Document image retrievers represent rendered pages rather than relying
only on extracted text 
(
Ma et al., 2024
; 
Faysse et al., 2024
; 
Yu et al., 2024
)
.
PixelRAG applies this approach to Wikipedia QA by indexing screenshot
tiles at scale 
(
Wang et al., 2026
)
.
However, many questions still depend on written facts such as names,
dates, and numbers.
When these facts are embedded in an image, a retriever must recognise
the text visually before it can match it to the question.
This motivates encoding the text together with the visual tile in a
single fused representation, so that written facts become directly
available for retrieval without discarding visual and layout cues.

Retrieving relevant content is only the first step.
A tile may match a question’s topic without containing the fact needed
for the answer, especially when the reader sees only a few tiles 
(
Yang et al., 2026
)
.
Standard question and document supervision 
(
Xiong et al., 2021
)
 identifies a relevant tile
but does not directly describe the content within it that supports the
answer.
We therefore generate question-conditioned descriptions of visible
answer evidence during training.
A vision-language teacher uses the question, a positive tile, and the
reference answer to describe the supporting content.
These descriptions provide evidence-focused supervision for adapting
the retriever.

Figure 1: 
An overview of our data construction pipeline, which consists
of two parts. (1) Screenshot Text Transcription: Text is extracted and
transcribed from image patches using Qwen3-VL-4B-Instruct.
(2) Question-Conditioned Evidence Descriptions: A high-capacity model
serves as a teacher to generate evidence description text, facilitating
alignment during training.

Pix2Evidence addresses these two needs with fused multimodal retrieval
and evidence-guided training.
Our retrieval component integrates textual and visual information: it
jointly encodes each screenshot and its available transcription into a
shared multimodal representation, retrieves candidates from this fused
view, and reranks them before passing them to the reader.
During training, the teacher descriptions make the supporting evidence
explicit.
We use them to align the candidate rankings induced by a question and
its evidence description, alongside contrastive learning.
In this way, retriever adaptation attends not only to which tile is
relevant, but also to the evidence that makes it useful for answering.
Figure 
2
 illustrates the inference setting;
Sections 
3
 and 
4
 detail the data and
training procedure.

We evaluate the complete system on five Wikipedia QA benchmarks over
approximately 7.1 million pages and 28.2 million screenshot tiles.
Our non-reranked configuration numerically exceeds PixelRAG in answer
accuracy on four benchmarks.
On MMSearch it reaches 26.0%, an improvement of 4.4 percentage points
over PixelRAG.
Additional configurations examine how the input representation,
candidate fusion, and reader depth affect these outcomes.
Our contributions are:

•

Starting from PixelRAG’s rendered screenshot tiles, we create
transcriptions for indexing and teacher descriptions of
answer evidence for retriever training.

•

We develop a multimodal RAG system that fuses image and text
into a single retrievable representation and adapts its encoder with
evidence-guided training.

•

We evaluate the system across five QA benchmarks and multiple
configurations. Its non-reranked configuration scores above PixelRAG on four and exceeds both text-extraction baselines on all five.

Related Work

Retrieval-augmented generation.

REALM and RAG incorporate external retrieval into language modelling
and knowledge-intensive prediction 
(
Guu et al., 2020
; 
Lewis et al., 2020
)
.
DPR learns dense question–passage representations 
(
Karpukhin et al., 2020
)
, and
Fusion-in-Decoder combines multiple passages during generation

(
Izacard and Grave, 2021
)
.
Beyond initial retrieval, instruction-following language models can
rerank candidate passages, as demonstrated by RankGPT 
(
Sun et al., 2023
)
.
Readers do not always handle distracting retrieved contexts reliably

(
Shen et al., 2024
)
.
We study this selection problem in multimodal RAG, where text and
visual content may offer different routes to the same answer.

Visual documents and screenshot retrieval.

Document understanding models combine text, layout, and image features,
as in LayoutLMv3 
(
Huang et al., 2022
)
, or generate directly from document
images without a separate OCR module, as in Donut 
(
Kim et al., 2022
)
.
WebSRC pairs page screenshots with HTML and questions that require
structural understanding 
(
Chen et al., 2021
)
.
VisualMRC studies answer generation from document images collected
across web domains 
(
Tanaka et al., 2021
)
.
These tasks show why reading web content involves both text and visual
organisation, although neither evaluates our web-scale retrieval setup.
For retrieval, DSE encodes screenshots into dense representations

(
Ma et al., 2024
)
; ColPali extends late interaction from ColBERT to visual
pages 
(
Khattab and Zaharia, 2020
; 
Faysse et al., 2024
)
.
VisRAG retrieves document images for vision-language generation

(
Yu et al., 2024
)
, and PixelRAG scales screenshot retrieval to web
QA 
(
Wang et al., 2026
)
.
SERVAL indexes model-generated page descriptions 
(
Nguyen et al., 2025
)
.
We instead index transcribed text from screenshot tiles and reserve
question-conditioned descriptions for training.
ViDoRe V3 evaluates retrieval, grounding, and generation in visually
rich documents 
(
Loison et al., 2026
)
.
Our setting keeps web tiles as retrieval units and studies how both
textual and visual views affect evidence selection.

Hybrid retrieval and multimodal evidence fusion.

WebQA asks systems to select and combine visual and textual web sources

(
Chang et al., 2022
)
.
MultiModalQA studies questions that require reasoning across text,
tables, and images 
(
Talmor et al., 2021
)
.
Both illustrate the need for evidence beyond a single text passage,
but they use different task settings from our Wikipedia tile index.
MuRAG retrieves from a multimodal memory 
(
Chen et al., 2022
)
, while VisRAG
passes retrieved document images to a vision language generator

(
Yu et al., 2024
)
.
In our system, the retriever encodes each tile together with its
available transcription in one fused representation, so that readable
text and layout are considered jointly rather than in separate indexes.

Evidence-guided retrieval supervision.

Contrastive learning distinguishes positive documents from negatives

(
van den Oord et al., 2018
; 
Karpukhin et al., 2020
)
.
RocketQA improves dense retrieval with additional negatives and data
augmentation 
(
Qu et al., 2021
)
.
Other work uses generated supervision: GPL combines synthetic queries
with relevance labels from a cross encoder to adapt dense retrieval

(
Wang et al., 2022
)
.
ReAlign generates question-focused descriptions for selected regions
of a document page, then aligns document rankings induced by the
question and those descriptions 
(
Yang et al., 2026
)
.
We keep a distributional alignment objective but change what the
supervision is attached to.
Our teacher describes evidence inside a fixed screenshot tile, using the
training question and reference answer as guidance, and these
descriptions supervise the same encoder that produces our fused tile
representation.
Unlike ReAlign’s region selection, our pipeline does not predict
bounding boxes.

3 
Data Construction

We use the Wikipedia screenshots already rendered and tiled by
PixelRAG 
(
Wang et al., 2026
)
 as our visual corpus.
The corpus used here comprises approximately 7.1 million pages and
28.2 million tiles, each linked to its source page.
On top of these images, we construct two distinct kinds of text.
As shown in Fig 
1
, query-independent transcriptions serve as index content, whereas
query-focused evidence descriptions provide training supervision.
The latter depend on a training question and reference answer and are
not available as test-time document fields.
Appendix 
A
 reports corpus counts.

3.1 
Screenshot Text Transcription

We process every indexed tile 
 with Qwen3-VL-4B-Instruct

(
Bai et al., 2025
)
 to transcribe visible text as 
 in reading order.
The prompt discourages completion of words cut off at tile boundaries.
Transcriptions are cached independently of retrieval questions and
reference answers. We then perform quality, length, and format checks on the resulting transcriptions.
About 85% of indexed tiles have nonempty transcriptions; tiles with
no visible text retain an empty text field and use image-only inputs.

3.2 
Question-Conditioned Evidence Descriptions

Inspired by ReAlign 
(
Yang et al., 2026
)
, we use
Qwen3-VL-32B-Instruct 
(
Bai et al., 2025
)
 as a teacher to generate 

descriptions of the evidence that supports the question for each training triple 
.
The question defines what information is needed; the reference answer

 helps the teacher locate that information in the positive tile 
.
The generation instruction asks for supporting content visible in
the tile, rather than an unsupported restatement of the answer.
The resulting descriptions supply answer-conditioned training signals
intended to focus the multimodal retriever on useful evidence.
It differs from ReAlign’s region descriptions 
(
Yang et al., 2026
)
 because
we describe fixed screenshot tiles and do not select bounding boxes.

Every training question has a supervision text 
.
When generated descriptions are available, we sample one uniformly at
each training use; otherwise, we concatenate the question and its
reference answer to form 
.
The reference answer helps the teacher locate supporting content
during data construction.
This supervision is used only for training and is not introduced at
inference.

5.2 
Main Results

Table 
1
 presents the main comparison.
Without reranking, Pix2Evidence already achieves better results than
both text-extraction and screenshot-retrieval baselines on most
benchmarks, especially on MMSearch and EVQA, reaching 26.0 and 40.6,
respectively.
This shows that fusing visual and textual information in a single
retrieval view provides stronger evidence than using either modality
alone.

Adding the vision-language reranker further improves answer accuracy
on NQ, NQ-Tables, and SimpleQA, reaching 33.2, 27.1, and 77.6,
respectively.
Compared with PixelRAG, these gains are 2.1, 1.3, and 4.8 percentage
points.
The reranked configuration also raises SimpleQA evidence recall from
83.1 to 86.9 and NQ-Tables recall from 50.7 to 55.8.
The non-reranked configuration remains strongest on MMSearch at 26.0
and EVQA at 40.6, which allows the reranking stage to be enabled or
disabled according to the target scenario.

5.5 
Dual-Branch Fusion Ablation

Our main pipeline uses a single fused image–text retrieval view.
As an extension, we analyze how a dual-branch design would behave if a
text-only branch were added, and compare four fusion rules without
reranking at 
 (Table 
4
).
All variants use the same image–text and text branches, with
candidates deduplicated by tile.
Max keeps the larger raw score for each tile; RRF sums reciprocal ranks
with offset 60 
(
Cormack et al., 2009
)
; z-score and min–max normalise each branch’s
scores within a query before summation.

Fusion changes how the two retrieval views prioritise shared
candidates.
Relative to Max, z-score raises SimpleQA from 64.6 to 67.3 and EVQA
from 30.4 to 33.5.
RRF achieves the highest NQ EM at 31.6 and the highest MMSearch score
at 22.0, and ties z-score on NQ-Tables EM at 24.4.
No single rule dominates across all benchmarks, but every fusion rule
outperforms Max on at least one benchmark, showing that combining
normalised scores or branch rankings is more effective than taking the
maximum raw score.

The system remains effective across all evaluated reader sizes, and
its performance generally improves as the reader becomes stronger.

6 
Conclusion

We presented Pix2Evidence, a multimodal RAG system for question
answering over Wikipedia pages.
It treats each page as a collection of screenshot tiles and encodes
each tile together with its available transcription into a fused
image–text representation, so that layout and readable text are
considered jointly rather than as separate retrieval views.
At inference time, the fused retriever returns candidate tiles, a
vision-language reranker selects the most relevant ones, and a reader
generates the answer from the question and the selected evidence.
For training, a teacher model produces descriptions of
answer-supporting evidence, which guide the retriever through a
contrastive objective and an evidence-alignment term.
Across five Wikipedia QA benchmarks, the non-reranked system scores above
PixelRAG in answer accuracy and leads the main comparison on four.
Its 26.0% MMSearch accuracy exceeds PixelRAG by 4.4 percentage
points.
The results underline a practical distinction: retaining rich document
content is useful, but a RAG system must also deliver the right
evidence to the reader.
Extensive experiments demonstrate the effectiveness of Pix2Evidence.

Limitations

Our evaluation focuses on English Wikipedia QA and a limited set of
model configurations.
Although we test readers from two model families, the sweep does not
cover other architectures, larger scales, or non-English domains.
A broader reader-model evaluation, including multilingual and
domain-specific settings, remains future work. The fused image–text index and the vision-language reranker introduce
additional storage and computation compared with a text-only pipeline.
Our input-budget study varies pixel area and text length, but it does
not measure peak memory and end-to-end latency.
These factors are important for practical deployment, especially when
the reader context is large. A complete cost evaluation and more efficient indexing and reranking
designs therefore remain future work.
For example, one could explore compressed index representations,
lightweight rerankers, or adaptive reranking that is applied only when
the initial retrieval is uncertain.

Ethical Considerations

We adhere to the ethical guidelines of the research community.
All experiments use publicly available datasets and open-source models,
ensuring transparency and reproducibility.
We have not collected new data involving human subjects or personally
identifiable information.

The datastore contains rendered web pages and may include copyrighted
material or personal information.
Retrieved evidence improves traceability, but it does not establish
that a source is correct or appropriate to disclose.
Reference answers condition training descriptions only and are not
provided during test-time retrieval or generation.
Our method focuses on retrieval and evidence selection and does not
modify the underlying safety alignment of the reader models.

3. Preserve the wording and numbers exactly; keep line breaks between
distinct lines/paragraphs.

4. If the image contains no readable text, output exactly: [NO TEXT]

Output only the transcribed text, with no preamble or commentary.

Evidence-description prompt

Positive tile

{screenshot tile}

You are given a screenshot tile cropped from a rendered web/document
page, and a question. This tile was retrieved as the evidence that
answers the question. Think step by step about which visible content in
the tile supports the answer, then write {k} SELF-CONTAINED evidence
descriptions that each explain — grounded in what is actually visible
in this tile — WHY this tile is relevant to and answers the question.
Each description must stand on its own as a faithful summary of the
tile’s query-relevant evidence.

Guidelines:

1. Ground every description in content actually visible in the tile; do
not invent facts, and do not complete text that is cut off at the crop
boundary.

2. Name the key evidence (entities, numbers, dates, titles) explicitly
and include the immediate context needed to interpret it; do not clip
numbers or symbols.

3. For tables/charts, mention the relevant header/row/column or
legend/axis/unit so the evidence is interpretable.

4. Make the {k} descriptions genuinely different in wording and
emphasis (different salient evidence or phrasing), not trivial
paraphrases — this diversity is used for sampling during training.

5. Each description should read like a short factual passage that, on
its own, would let a retriever match it to the question.

Output format
 — a single JSON object, no markdown fence, no
extra text:

{"think": "your brief step-by-step reasoning", "descriptions":
["desc 1", "desc 2", …]}

Question: {query}{answer_hint}

A.4 
Retriever Training

Optimisation.

The recorded launch uses batch size 32, gradient-cache chunks of two

(
Gao et al., 2021
)
, learning rate 
, 20 warm-up steps, and a
cosine schedule capped at 350 steps.
A text warm-up stage uses about 15K question and answer pairs for
50 steps. The selected retriever checkpoint is at step 100. The visual-token limit is 4096.
Three H800 80GB GPUs train the retriever; a fourth serves the reader
through vLLM 
(
Kwon et al., 2023
)
.

Alignment objective.

Question and evidence-description distributions share a temperature
of approximately 0.07.
The forward objective in Section 
4.3.3
 weights the KL
term by 0.05 and stops gradients through the question-induced target.
For the reverse-KL variant, the description-induced distribution is
detached and the query branch can still receive gradients.

Development subset.

The development subset, adopted from PixelRAG, is a compact
mini-datastore for embedding ablations, containing 400 questions and
7,426 tiles.
For each question, it includes all tiles from the gold article plus the
top-100 tiles retrieved by the base embedding model, mixing relevant and
irrelevant candidates.
We use this subset for our training alignment ablation.

A.5 
Candidate Processing and Reader Inputs

Candidate lists.

Our main fused retrieval path returns a single ranked list and passes

In the ablation study, we use a dual-view recall of text and fused

C.3 
Agentic Search on MoNaCo

Setting and metric.

We evaluate our retrieval backends as the search tool of a GPT-5 ReAct
agent on the full MoNaCo benchmark, 1,315 multi-hop Wikipedia questions.
Only the search backend varies across conditions; the agent loop, the
prompt, and the GPT-5 reader are identical, and every run completed all
1,315 questions.
The agent issues up to 15 search queries per question with three results
per query, a shorter budget than the 20 queries with five hits each of
PixelRAG’s reference protocol 
(
Wang et al., 2026
)
.
MoNaCo answers are frequently multi-value lists, so we report judge-F1,
computed from an LLM judge that scores each predicted answer against the
reference answers.
Table 
15
 reports judge-F1 on a 0–1 scale together
with agent API cost and retrieval GPU time.

Backends.

Text-only search uses the transcription index, and image-only search the
base screenshot index.
Dual-view search unions a screenshot path with a second path that
searches the transcriptions as text; the screenshot path uses either the
base index or ours, which encodes each tile together with its
transcription so that a single retrieved item carries both the rendered
evidence and its text.

Results.

Judge-F1 ranges from 0.4673 to 0.4816 across the six runs.
The best score comes from dual-view search on our index without
reranking (0.4816).
At the same retrieval design, our index adds 0.0108 over the base index
(0.4708 to 0.4816), the largest effect in the table.
Text-only search is competitive at 0.4755 and exceeds image-only search
on the base index (0.4673), which matches our expectation that the
transcription view contributes evidence a screenshot-only index can miss;
combining the two views on our index then gives the best result.
Reranking behaves differently on the two indexes: it raises the
base-index dual-view setting from 0.4708 to 0.4792, but it does not help
on our index (0.4816 to 0.4688), so its benefit is largest where
first-stage retrieval is weaker.

Cost.

Agent-side cost varies little across the backends with complete usage:
text-only search and the dual-view runs each accumulate 9.3–9.8M prompt
tokens and cost $57.26–$57.82 per run.
Adding the text view therefore leaves the agent’s conversation length
essentially unchanged, because every retrieved item remains a screenshot
tile rather than an extracted passage.
Each reranker invocation adds about 1.2–1.4 seconds.
On the retrieval side, our index is cheaper than the base index for the
same design: 16.3 versus 25.2 hours for dual-view, and 18.1 versus 24.7
hours with reranking.
