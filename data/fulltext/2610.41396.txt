Abstract

In AI for Science scenarios, experimental design and method reproduction require retrieving protocols that satisfy multiple interdependent constraints, yet existing benchmarks lack systematic evaluation of this capability. To address this gap, we introduce ProSearch, a benchmark for multi-constraint protocol retrieval in experimental science. ProSearch has three key features: (1) realism, with queries grounded in real experimental records and expert-defined templates; (2) complexity, with 60 experimental fields and their dependencies; and (3) diagnosticity, with 3–5 explicit constraints per query, including numerical and negation constraints. We construct ProSearch through LLM-based extraction, data-driven constraint selection, controlled query generation, and evidence-based relevance validation. The resulting benchmark contains 1,515 queries across six experimental science domains.
We conduct extensive experiments on ProSearch with 19 representative retrievers and complementary analyses. The best-performing retriever achieves an average nDCG@10 of only 0.290, which improves to 0.474 with reranking. Structured diagnostic analysis shows that explicit constraint matching provides a strong ranking signal, while manual error analysis identifies joint constraint binding as a key bottleneck. ProSearch provides a testbed for systematically evaluating scientific retrieval systems.

Introduction

As AI for Science advances, artificial intelligence systems are increasingly being used for scientific tasks 
(
Xie et al., 2025
; 
Weng et al., 2026
)
 such as experimental design 
(
Ma et al., 2025
; 
Wang et al., 2026
)
 and protocol reproduction 
(
Gridach et al., 2025
; 
Chen et al., 2025b
)
. In these settings, systems must not only understand the research question but also retrieve actionable methodological evidence from the scientific literature to identify protocols that meet specific experimental requirements 
(
Kasmaee et al., 2025
)
. In this context, protocol retrieval has become an important foundational capability for AI for Science 
(
Kon et al., 2025
; 
Eger et al., 2025
; 
Gupta et al., 2022
; 
Gu et al., 2021
)
.

Beyond topical relevance, protocol retrieval aims to identify method paragraphs describing experimental protocols that satisfy multiple specific conditions 
(
Liu et al., 2026
)
. For example, a researcher may require a specific cell line to be cultured at 
C while excluding the use of DMEM as the culture medium. Retrieval systems must not only identify these conditions but also verify that they hold within the same coherent experimental configuration. However, method paragraphs often describe multiple experimental configurations or variants within the same context 
(
Sun et al., 2025
)
. Therefore, even when all query conditions appear in the same paragraph, they may correspond to different experimental procedures, leading keyword-based retrieval methods to produce false matches.

Existing benchmarks provide limited evaluation of this capability 
(
Zhong et al., 2025
; 
Ajith et al., 2024
; 
Chen et al., 2026
)
. Traditional scientific datasets focus on abstract-level fact verification or passage-level question answering 
(
Wadden et al., 2020
; 
Jin et al., 2019
)
. More recent reasoning-intensive benchmarks, such as BRIGHT 
(
Su et al., 2025
)
, introduce queries that require inference beyond surface-level matching, but do not impose explicit multi-constraint requirements. MultiConIR 
(
Lu et al., 2025
)
 addresses multi-constraint retrieval, yet focuses on structured items rather than unstructured scientific text. Existing evaluations do not adequately measure whether retrievers can jointly bind multiple constraints to a single experimental variant.

However, constructing such a benchmark presents several challenges 
Song et al. (2026)
. First, realistic protocol queries are not readily available in existing retrieval datasets and cannot be generated by simply combining keywords. They must reflect meaningful experimental needs and follow valid experimental logic. Moreover, a plausible query does not necessarily have supporting evidence in the retrieval corpus. Query construction must therefore be grounded in real experimental protocols. Finally, relevance labeling requires verifying that the retrieved text supports all query constraints within a consistent experimental configuration, making reliable annotation difficult to automate.

To address these challenges, we develop an expert-guided construction pipeline. Domain experts define experimental fields, dependencies, and query templates. We instantiate these templates using values from extracted protocol records and select constraint combinations in the corpus. LLM-assisted filtering and query generation then produce meaningful natural-language queries. For relevance labeling, we use structured records to identify candidate paragraphs but determine final relevance from the original text, labeling a paragraph as relevant only when a single experimental configuration supports all query constraints. Through this pipeline, we introduce 
ProSearch
, a multi-constraint protocol retrieval benchmark comprising 1,515 queries across six experimental science domains. ProSearch has three key characteristics: (1) 
realism
, with queries grounded in real experimental records and expert-defined templates; (2) 
complexity
, with 60 experimental fields and their dependencies; and (3) 
diagnosticity
, with 3–5 explicit constraints per query, including numerical and negation constraints.

To assess current retrieval capabilities on ProSearch, we conduct a series of comprehensive experiments. Our evaluation of 19 retrievers shows that ProSearch is a major challenge; even the best models achieve an average nDCG@10 of only 0.290, leaving large room for improvement. We find that reranking improves this score to 0.474, while query reformulation yields only modest gains. Structured diagnostic analysis based on extracted protocol records achieves an average nDCG@10 of 0.774, increasing to 0.814 when dense similarity is used to break ties. Manual error analysis further reveals that 90% of sampled top-ranked non-relevant paragraphs violate at least one query constraint, highlighting constraint binding as a key bottleneck. Overall, we hope ProSearch serves as a testbed for building both better retrievers and next generation scientific agents that can truly handle complex experimental logic.

3.2 
Dataset Construction

In this section, we present the construction of ProSearch. Our pipeline (Figure 
1
) is designed to ensure: (1) 
Retrieval Usefulness
, where queries represent meaningful requests that reflect the actual information needs of domain researchers; and (2) 
Verifiability
, where paragraph relevance is determined by explicit, evidence-grounded validation.

Expert-Guided Modeling.

To construct meaningful multi-constraint protocol queries, we first collaborate with domain experts to define experimental fields and their usage rules, then organize these fields through shared roles and query templates.

Domain Coverage and Field Selection.

We cover six domains: Cell Culture, Immunotechnology, Electrochemistry, Organic Synthesis, Inorganic Materials, and Polymer Materials.
For each domain, an expert identifies a representative experiment type and selects fields according to three criteria:
(1) 
Experimental relevance
 requires a field to describe a key aspect of the target protocol, such as cell type or medium in cell culture.
(2) 
Textual extractability and standardizability
 requires that field values can be identified in method paragraphs and normalized under controlled rules.
(3) 
Discriminative power
 refers to the ability to distinguish protocols with similar goals but different configurations. For example, temperature alone provides little discrimination when most protocols use 37 
∘
C.
Experts also specify each field’s value type, permitted operators, dependencies, and usage rules.

Role-based Template Design.

To organize fields consistently across domains, we classify them into four functional roles.

Goal
 denotes the primary experimental target anchoring each query template, such as the target cell type in cell culture.

Input
 covers materials, samples, or reagents; 
Condition
 covers experimental parameters such as temperature, concentration, time, or atmosphere; and 
Method
 covers procedural operations, treatments, or measurements.
We define 20 shared role-level templates (Appendix Table 
21
), each containing 3–5 role slots.
These role-level templates are instantiated with domain-specific fields to generate candidate field-level templates.

Field-level Template Filtering.

Not every field combination generated from a role-level template forms a meaningful retrieval request.
We therefore filter field-level templates using the expert-defined dependencies and usage rules.
For example, the role-level template 
Goal + Input + Condition
 can produce 
Cell Type + Basal Medium + Confluence
. This combination is filtered out because Confluence depends on Culture Mode. In contrast, 
Cell Type + Basal Medium + Confluence + Culture Mode
, generated from 
Goal + Input + Condition + Method
, satisfies the dependency and is retained.
Complete field definitions, rules, and templates are provided in Appendix 
B.1
.

Corpus Collection and Paragraph Filtering.

For each domain, we collect English open-access research articles published between 2020 and 2025 via OpenAlex 
(
Priem et al., 2022
)
.
We use GROBID 
(
Lopez, 2009
)
 to reconstruct section structures and paragraph boundaries.
We identify method-related sections by matching top-level section headings against expert-defined patterns and retain paragraphs from these sections.
We exclude non-paragraph content, such as tables and figure captions, and discard paragraphs exceeding 2,048 GPT-2 tokens.
The retained method paragraphs form the retrieval corpus 
.
Further details are provided in Appendix 
B.2
.

Figure 1: 

ProSearch data construction pipeline.

Protocol Record Construction.

A method paragraph may describe multiple experimental configurations, such as different material combinations or reaction conditions.
To avoid mixing conditions from different configurations, we use GPT-5.2 to extract a separate structured record for each configuration based on expert-defined experimental fields.
Each record preserves the field values and their supporting text spans from the original paragraph, grounding the extraction in textual evidence. Since the same experimental value may be expressed differently across papers, we then use GPT-5.2 to normalize the extracted field values 
(
Ai et al., 2025
)
.
For closed-set fields, we select the most specific predefined category supported by the text.
For open-set fields, we normalize synonymous expressions while preserving the specific identities supported by the original text.
Further details are provided in Appendix 
E
.

Query Construction.

We instantiate the filtered field-level templates with values from a single normalized protocol record to generate candidate constraint sets. For each set, we compute its support count using the extracted records, counting a paragraph once if at least one of its records satisfies all constraints. We retain sets with support counts between 3 and 8 to balance task specificity and evaluation stability, excluding overly broad constraint sets and those with insufficient structured support. We then sample constraint sets stratified by constraint count and use GPT-5.4 to filter out scientifically uninformative sets and convert the retained ones into natural-language queries 
(
Cai et al., 2023
)
. We use Claude Sonnet 4.6 to evaluate the queries along three dimensions:
(1) 
Faithfulness
, ensuring no constraints are added or omitted;
(2) 
Clarity
, ensuring natural and unambiguous expression; and (3) 
Retrieval Usefulness
, confirming that the query represents a meaningful scientific request.
Only queries passing all three checks are retained. This process yields 1,551 constructed queries across the six domains.
Figure 
3
 summarizes the resulting query patterns.
Detailed sampling statistics and filtering examples are provided in
Appendix 
B.3
.

Relevance Labeling.

Since exhaustive labeling is impractical, we use structured records to construct an annotation pool of potentially relevant paragraphs for each query. We first identify paragraphs containing at least one extracted record matching all query constraints as 
exact-support candidates
.
Extraction omissions or normalization inconsistencies may cause exact matching to miss relevant paragraphs.
We therefore also include 
near-miss candidates
: paragraphs containing at least one extracted record matching all but one constraint.
We sample up to 100 near-miss candidates per query.
Both candidate types are defined by structured matching over extracted records and do not determine relevance labels.
We then use GPT-5.4 to judge candidate relevance based on the original paragraph text.
The model examines experimental configurations separately and labels a paragraph as relevant only when the text supports all query constraints within the same configuration.
Of the 1,551 constructed queries, 36 had no associated relevance judgments (qrels) and were excluded from retrieval evaluation, leaving 1,515 queries in the final evaluation set.
More details are provided in Appendix 
E
.

4.2 
Main Results

ProSearch remains challenging for existing retrieval systems.

Results in Table 
6
 show that ProSearch is highly challenging, with the best model achieving an average nDCG@10 of 0.290, indicating that existing retrieval models cannot reliably perform multi-constraint protocol retrieval. We observe that general-purpose dense retrievers achieve the best overall performance, which may be attributed to their broader training data coverage. In addition, scientific retrievers generally perform poorly, implying that adaptation on scientific text does not improve protocol retrieval performance. Interestingly, reasoning-oriented retrievers still lag behind the strongest general-purpose dense retrievers, suggesting that existing reasoning signals are not sufficient for ProSearch. The task requires not only domain-specific understanding, but also multi-constraint reasoning, including constraint dependencies within a coherent protocol. We also observe large performance differences across domains, with much lower scores on Immunotechnology and Electrochemistry, indicating that the difficulty of ProSearch is closely related to how experimental protocols are described and how constraints interact in different domains.

Reranking substantially improves retrieval performance.

We further examine whether reranking can improve ProSearch by reranking the top-100 paragraphs retrieved by Qwen3-Embedding-8B with several representative rerankers. Results in Table

5 
Conclusion

In this work, we introduce ProSearch, the first benchmark dedicated to multi-constraint protocol retrieval in experimental science. Our evaluation shows that current retrievers, including those specialized for reasoning, struggle to retrieve paragraphs that satisfy multiple experimental constraints within a single coherent protocol variant. Structured diagnostic analysis shows that explicit constraint matching provides a strong ranking signal, while manual error analysis highlights joint constraint binding as a key bottleneck. We hope ProSearch provides a new perspective for evaluating scientific retrieval and inspires further research into building more logically robust IR systems.

6 
Limitations

While ProSearch provides a systematic evaluation of multi-constraint protocol retrieval, several limitations remain. First, the field schemas and constraint rules are designed by domain experts for selected experimental protocol types across six domains, limiting coverage of other experimental procedures and requiring additional expert effort for extension. Second, ProSearch focuses on individual method paragraphs and does not evaluate evidence integration across multiple paragraphs, tables, or supplementary materials. Third, LLM-based protocol extraction and relevance labeling, together with annotation pools constructed from extracted records, may introduce errors or omit relevant evidence. Although expert audits and robustness analyses support the stability of the main retrieval findings, systematic biases cannot be fully ruled out. Finally, while the queries are grounded in real experimental records, they are generated using templates and may not fully reflect researchers’ actual information needs. Whether benchmark scores translate into retrieval usefulness in real scientific workflows also remains to be established. Future work will extend ProSearch to cross-paragraph protocol retrieval and incorporate researcher-authored queries and human evaluations to assess its practical applicability.

Appendix A 
Broader Impacts

ProSearch is intended to support research on more reliable scientific evidence retrieval.
By focusing on method paragraphs and protocol-level constraints, it may help develop retrieval systems and scientific agents that better locate experimental evidence for protocol design, literature analysis, and reproducibility-oriented research.

However, ProSearch should not be treated as providing authoritative experimental recommendations.
Retrieval systems may still return incomplete or incorrect evidence, which could lead to flawed experimental decisions if used without expert verification.
The benchmark may also reflect biases in English open-access scientific literature.
Therefore, systems developed using ProSearch should be used as decision-support tools, and retrieved protocol evidence should be checked against the original papers before practical use.

B.3 
Query Construction Details

This section provides additional details on query construction in ProSearch.
We describe how candidate constraint sets are instantiated from protocol records, how they are selected and sampled, how weak constraint sets are filtered, and how the retained constraint sets are converted into natural-language queries.

Instantiating constraint sets from protocol records.

Given the field-level templates described in Section 
B.1
, we instantiate candidate constraint sets using the normalized protocol records.
For each field-level template, all fields are filled using values from a single protocol record.
If any required field is missing in that record, the candidate is discarded.
This prevents the resulting constraint set from combining conditions that come from different experimental configurations.
Categorical values are instantiated as equality constraints, numeric point values as equality constraints, and numeric intervals as range constraints.
The allowed operators for each field follow the field schema.

Selecting and sampling constraint sets.

For each candidate constraint set, we compute its support count, defined as the number of unique paragraphs containing at least one protocol record that satisfies all constraints.
We retain candidates with support counts between 3 and 8.
The lower bound ensures that each retained candidate has multiple structurally supported paragraphs before validation, while the upper bound removes constraint sets that are too frequent to represent a specific protocol search need.
For candidate constraint sets with an exploration field, we additionally require the explored field to have multiple distinct observed values among the supporting records.
This avoids generating questions whose answer is either unavailable or nearly constant in the corpus.
For constraint sets with negation, we only use negated values that occur sufficiently often in the corpus, so that the negated condition reflects a meaningful alternative rather than a rare value.
From the remaining candidates, we sample constraint sets for each domain.
Sampling is stratified by constraint count, so that the final benchmark includes queries with different levels of constraint complexity.

Filtering constraint sets with an LLM.

We further use GPT-5.4 to assess whether each sampled constraint set forms a meaningful protocol retrieval request.
This filtering step targets cases that satisfy the automatic construction rules but remain scientifically underspecified or too broad for retrieval evaluation.
Common rejected cases include constraint sets with missing experimental context, overly broad negated constraints, or explored fields whose values depend on omitted setup information.

Constraint diversity.

Figure 
3
 characterizes the constraint patterns of the final query set after construction and filtering.
Across domains, ProSearch is dominated by 3- and 4-constraint queries, while 5-constraint queries are retained when sufficient structured support is available.
This distribution reflects the realism constraint in our query design: the queries are more specific than broad topical searches, but avoid overly narrow combinations that domain experts would be unlikely to ask in practice.
Numeric constraints are frequent in strongly parameterized domains such as electrochemistry, inorganic materials, and polymer materials.
Negation constraints appear in a substantial fraction of queries, allowing ProSearch to test whether retrievers can exclude protocols with disallowed conditions rather than only match positive evidence.
Overall, these statistics show that ProSearch queries are grounded in real structured records while covering diverse constraint patterns beyond topical matching.

C.2 
Query variant experiments

To evaluate whether transforming the original natural-language query improves protocol retrieval, we generate several query variants for each query.
These variants are used as retrieval inputs while keeping the document corpus, retriever, and evaluation protocol unchanged.
This setting allows us to isolate the effect of query formulation from changes in the retrieval model.

Table 31: 

Prompts used for query variant experiments.

Query Decomposition

Given a retrieval query, decompose it into a small set of simpler retrieval sub-queries.

First, identify internally the query intent and the constraints in the query.
Then generate the smallest non-redundant set of sub-queries that together cover the original constraints.

Requirements:
(1) Each sub-query must remain a natural question.
(2) Each sub-query must preserve the original query intent.
For an exploration query, it must still ask about the same field as the original query.
For a reproduction query, it must still ask for a setup/protocol/paragraph satisfying constraints.
(3) Each sub-query should keep only part of the original constraints, so that it is simpler than the original query.
(4) Different sub-queries should reflect different retained constraints, not paraphrases of the same reduced query.
(5) Together, the sub-queries should cover all original constraints.
(6) Use as few sub-queries as possible.
(7) Do not introduce new constraints or change the meaning of the original query.
