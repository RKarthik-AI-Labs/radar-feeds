Abstract

Web agents powered by large language and vision-language models are increasingly applied to realistic browser work that spans heterogeneous applications, multimodal content, and stateful workflows. However, existing reproducible web-agent benchmarks cover only a small number of web applications drawn from a few software categories, and restrict modality to text and vision. Live benchmarks broaden site coverage but sacrifice reproducibility, since pages and data drift between runs. Moreover, existing benchmarks do not meaningfully evaluate whether agents can understand and use audio and video content embedded within web tasks. To address these gaps, we introduce WebArena-Pro, a benchmark comprising 300 tasks across 20 self-hosted web applications in six domain categories, spanning distinct interface conventions, workflows, and data models. Across the evaluated agents, the best performance is achieved by both Codex with GPT 6.1 Sol and Claude Code with Claude Opus 5.5 at 62.3%, followed by OpenCode with Kimi 3.1 Pro at 60.7%. The strongest GenericAgent configurations, Gemini 3.1 Pro omni and Gemma4 31B, both achieve 30.3%. Among reproducible, human-curated web agent benchmarks, WebArena-Pro provides the broadest application coverage and the most comprehensive multimodal support to date. The benchmark treats audio and video as core observations alongside text and vision, with dedicated actions for extracting information from each. WebArena-Pro runs each task in isolation and supports reproducible, parallel evaluation. Tasks are authored through a dedicated annotator interface, filtered by LLM-assisted triage, and finally validated by humans before release. Project page: 
https://webarena-pro.github.io
.

First, prior self-hosted benchmarks cover only a small number of web applications drawn from a few software categories, which limits the heterogeneity of interfaces, workflows, and data models that an agent encounters during evaluation. WebArena-Pro

First, addressing the application coverage gap, WebArena-Pro spans 20 self-hosted web applications across six domain categories (productivity, communication, analytics, business operations, design and media, and travel), with applications modeled on widely used services such as Notion, Slack, Spotify, Figma, and Airbnb (Table

transcribe()
 and 
extract_frames()
 actions so that agents can incorporate temporal media directly into browser workflows. Third, addressing the reproducibility limitation of live benchmarks, WebArena-Pro runs each task in isolation against per-task seeded container state, supporting reproducible parallel evaluation that avoids drift between runs.

WebArena-Pro contains 300 tasks categorized by site coverage (204 single-site, 96 cross-site) and modality (221 text/vision, 79 audio/video), as detailed in Table

Tasks are authored through a dedicated annotator interface and pass through a two-stage filter, in which LLM-assisted triage flags candidates that appear infeasible or trivial and human reviewers make the final acceptance decision. This pipeline keeps task quality grounded in human judgment while using LLM assistance to scale the authoring process.

•

Heterogeneous web coverage.
 We construct a benchmark of 20 self-hosted web applications across six domain categories with distinct interface conventions, workflows, and data models.

•

•

 We run each task in isolation against per-task seeded container state, supporting reproducible parallel rollouts and avoiding drift between runs.

 We release a task creation pipeline that combines an annotator interface, LLM-assisted infeasibility and triviality triage, and final human validation.

Self-Hosted Web Benchmarks.

WebArena is the closest predecessor to WebArena-Pro. It introduced a self-hosted benchmark for realistic web navigation over six web applications, with agents completing natural-language tasks by operating a browser 
(
Zhou et al., 2023
)
. VisualWebArena 
(
Koh et al., 2024
)
 extended the setting to visually grounded tasks where success depends on understanding screenshots rather than only DOM text, and WebChoreArena 
(
Miyai et al., 2025
)
 stressed long-horizon, tedious browsing patterns with self-hosted websites as well. While these benchmarks provide valuable foundations for realistic and reproducible web-agent evaluation, WebArena-Pro differs along three axes visible in Table 
1
. First, it covers 20 applications across six domain categories, the broadest application coverage among self-hosted web benchmarks. Second, it enforces per-task isolation by explicitly resetting application state between tasks. In contrast, these benchmarks retain state across tasks, so backend changes an agent makes while solving one task persist into the next and can contaminate later evaluations. Third, it authors each task as its own dedicated template. In contrast, these benchmarks instantiate many task instances from a smaller template set (e.g., 241 templates for 812 instances in WebArena), which may lead to a less diverse evaluation.

Enterprise Benchmarks.

A parallel line of work pushes toward workplace realism. WorkArena evaluates agents on common knowledge-work tasks in ServiceNow 
(
Drouin et al., 2024
)
, and WorkArena++ extends this direction with compositional planning tasks and automatically generated ground-truth trajectories 
(
Boisvert et al., 2024
)
. TheAgentCompany simulates a small company across a handful of internal services and introduces non-binary partial scoring 
(
Xu et al., 2025
)
. These benchmarks emphasize enterprise workflows, long-horizon planning, and task composition. WebArena-Pro is complementary; rather than centering on one enterprise platform, it spans productivity, communication, analytics, business operations, design and media, and travel applications, while still retaining stateful authenticated workflows.

Live and Computer-Use Benchmarks.

Other benchmarks broaden the evaluation setting in a different direction. Mind2Web studies generalization to real websites using collected human demonstrations 
(
Deng et al., 2023
)
, and OnlineMind2Web 
(
Xue et al., 2025
)
 considers a live variant where the target websites may change over time. Live benchmarks improve ecological validity but make repeatability difficult, since pages, data, policies, and layouts can drift between evaluations. WebArena-Pro instead uses self-hosted applications and seeded data, which makes failures easier to reproduce and enables backend-state evaluation. Beyond the browser, computer-use benchmarks such as OSWorld 
(
Xie et al., 2024
)
 broaden the target from browsers to full desktop environments, and Gym-Anything 
(
Aggarwal et al., 2026
)
 pursues a different scaling axis by using LLMs to configure environments and auto-generate evaluators. WebArena-Pro instead focuses specifically on web software, where browser instrumentation and application-level reset can be made reliable enough for controlled experiments, and keeps task authoring human-validated.

Multimodal Web Benchmarks.

VisualWebArena showed that many web tasks require visual grounding and that text-only agents miss information that is obvious to humans 
(
Koh et al., 2024
)
.
WebArena-Pro follows this motivation and extends multimodal support beyond static visual content to include audio and video. To enable this, we add new actions to the action space of the agent, such as 
transcribe()
 and 
extract_frames()
. The agent invokes 
transcribe()
 to convert an audio source to text and 
extract_frames()
 to sample representative frames from a video source. The resulting transcripts are merged into the accessibility-tree observation as synthetic nodes, while extracted frames are returned as image content alongside the AXTree, so the agent perceives temporal media within the same observation structure it already uses for the rest of the page (Figure 
1
).
Finally, VideoWebArena 
(
Jang et al., 2025
)
 keeps the original WebArena websites and adds external tutorial videos that agents must draw facts or skills from. Unlike VideoWebArena, WebArena-Pro builds its audio and video content into the 20 new self-hosted applications, so multimodal understanding is part of the environment itself.

3.1 
Web Environments

WebArena-Pro consists of 20 self-hosted web applications grouped into six domain categories, listed in Table 
2
. Each application runs as a Docker container with seeded data and fixed login credentials, and is reachable at a fixed local URL during evaluation. Before each task, the container state is reset to its seeded baseline, so changes made by an agent during one task do not persist into the next. Local hosting also fixes the application version and the database contents across runs, which removes the drift in pages, data, or policies.

The six domains are productivity, communication, analytics, business operations, design and media, and travel. Within each domain the applications share a broad task family, such as file management in productivity or dashboard analysis in analytics, but differ in interface conventions, authentication flows, and backend state schemas. NextCloud and MyDrive both store files, for example, but they expose distinct REST APIs, distinct folder and permission models, and distinct Document Object Model (DOM) structures, so an agent that has learned to operate one is not guaranteed to transfer to the other. This grouping is what allows WebArena-Pro to test transfer at the level of interface and backend conventions, rather than memorization of a single product.

Each application is modeled on a familiar reference application, listed in the third column of Table 
2
, which names the workflow pattern reproduced rather than implying data or feature parity.

A task in WebArena-Pro is specified by a natural-language intent, one or more starting sites, an authenticated browser state, and an evaluation specification that determines success and partial credit (Section

The default action space follows the BrowserGym convention 
(

)
, with element-targeted actions (

,

,

) and navigation actions (

To support audio/video tasks, we extend this default action space by surfacing audio and video sources as nodes in the accessibility tree and introducing four actions that operate on them (Figure

).

•

: Returns a transcript of the audio segment from 
start
 to 
end
 (in seconds) using a local Whisper model.

•

extract_frames(url, n, start, end)
 (vision-language agents only): Returns 
 evenly spaced frames from the video segment between 
start
 and 
end
 (in seconds).

•

 (omni models only): Provides the audio segment from start to end (in seconds) as direct audio input to the model.

•

watch(url, start, end, include_audio)
 (omni models only): Provides the video segment from start to end (in seconds) as direct video input to the model, optionally including synchronized audio.

The agent invokes these actions when it judges that the audio or video content is needed for the task.
The resulting transcripts and extracted frames from 
transcribe()
 and 
extract_frames()
 are returned as observations in the next step, with transcripts merged into the accessibility tree as synthetic nodes and frames returned as image content alongside the accessibility tree.
For omni models, 
listen()
 and 
watch()
 allow the videos and audio to be sent with the accessibility tree and processed by the model as a different modality.

3.3 
Evaluation

We evaluate each trajectory with a rubric-based verifier. Every task is paired with a small set of human-written criteria, tagged as 
[action]
 or 
[outcome]
. Action rubrics measure whether the agent performed required steps, such as searching, filtering, or submitting a form. Outcome rubrics measure whether the final state of the website or the final answer satisfies the request, and for question-answering tasks they include a reference answer. We organize the rubrics of a task into a directed acyclic graph (DAG) with one rubric node per criterion. A rubric node that depends on a failed rubric node is counted as failed. A task counts as a success only when all of its rubric nodes pass, and we report the success rate as the fraction of tasks that succeed.

Each grader decides whether a rubric is satisfied, and each rubric node uses one or more graders. There are three kinds of graders. (1) Deterministic graders query the backend state of the website, for example whether a booking exists, or look for required strings in the final answer of the agent. (2) Heuristic graders match patterns in the URLs the agent visited and the actions it took. (3) An LLM judge reads the trajectory and the rubric. When a rubric has an unambiguous expected result, such as an exact name in the answer, a deterministic grader decides whether the rubric node passes or fails on its own. Otherwise, the graders are applied in the order deterministic, heuristic, then LLM judge. If a grader finds the rubric satisfied, the rubric node passes. If not, the next grader is tried, so that a correct but unexpected solution can still be recognized. The LLM judge always comes last and makes the final decision, and it is the only grader for rubrics that cannot be verified from the backend state or the actions of the agent.

Mock Data and Personas.

Each application is shipped with seeded data so that tasks operate on a realistic, non-empty state. Seed contents are application-appropriate and include documents, files, messages, calendar events, dashboards, listings, support tickets, and similar records, as well as the relations between them, such as channel memberships, file shares, and assignments. Each application is also seeded with one or more user personas, represented by credentials and pre-populated account state, so that tasks begin from an authenticated browser session.

Task Creation Pipeline.

Tasks are authored by an annotator team composed of the authors of this paper. Through a dedicated annotator interface, an annotator writes the natural-language intent, selects the relevant sites, and drafts the evaluation rubric. Each candidate then undergoes an automated triage step that flags trivial tasks by running against an LLM-based agent and discarding those solved correctly on the first attempt. Tasks that pass triage are reviewed by a second annotator on the live application, who confirms feasibility, finalizes the rubric items used for scoring, and confirms the difficulty label. Human validation is the gating step before a task enters the released benchmark, and we do not release tasks that fail any of these checks.

4 
Experiments

4.1 
Experimental Setup

Environment Setup.

We evaluate agents by running each task in a BrowserGym-compatible browser environment 
Chezelles et al. (2025)
. At the beginning of an episode, the benchmark starts a fresh website container, waits for readiness, performs the required UI login, and navigates the browser to the task start URL.
The agent receives the natural-language intent, with the list of accessible websites for the task, and then acts in the browser until it calls 
done()
 or 
send_msg_to_user()
, or reaches the maximum number of steps.
Each task is limited to 50 browser actions. We report success rates using the benchmark’s evaluator output.

Modeling.

We evaluate representative agent architectures paired with different language, vision-language, and omni models.
Each agent has its own configuration and action space.
For instance, GenericAgent 
Chezelles et al. (2025)
; 
Drouin et al. (2024)
 is a ReAct 
Yao et al. (2023)
 agent that asks for chain-of-thought 
(
Wei et al., 2022
)
 and an action at each step. It uses the BrowserGym 
Chezelles et al. (2025)
 harness to obtain observations and act on the web page.
In our setup, GenericAgent instances receive the same task intent, browser observation, and high-level action space. GenericAgent instances operate on the accessibility tree, with screenshots augmented with Set-of-Mark 
Yang et al. (2023)
.
They also use our WebArena-Pro custom action set, which is derived from the bid action set from BrowserGym, and augmented with 
done()
, 
transcribe()
, and 
extract_frames()
 actions, which respectively allow finishing the current task, transcribing audio segments, and extracting frames from video segments (Section 
3.2
).
The action space for omni agents includes 
listen()
 and 
watch()
 instead, for direct modality interaction with both audio and video, respectively.

OpenCode, Codex, and Claude Code are evaluated via the Harbor 
Harbor Framework Team (2026)
 harness. These coding agents are provided with a Playwright MCP and an augmented media MCP to allow 
transcribe()
 and 
extract_frames()
 functions. Playwright MCP handles the observation extraction and action execution on the browser. Detailed setup of these agents is given in Appendix 
A
.

We select twelve models as agent backbones: seven open-source models, including Qwen 3.5 9B, Qwen 3.6 27B, Qwen 3.8 27B, Qwen 3.8 Max Prime, Gemma4 26B A4B, Gemma4 31B 
(
Farabet and Lacombe, 2026
)
, and Kimi 3.1 Pro. And five closed-source models, including Gemini 3.1 Flash Lite, Gemini 3.1 Pro 
(
Pichai et al., 2025
)
, Claude Opus 4.7 
(
Anthropic, 
)
, Claude Opus 5.5, and GPT 6.1 Sol.
We evaluate Gemini3.1 Pro as both a text and an omni model. In the latter, it leverages raw audio and video files returned by the omni action space.

For all models, we enable extended thinking—reasoning effort set to high—and set the temperature to 1.0, following the recommendations of the respective model developers. We also cap the maximum number of tokens per step at 40k 
Chezelles et al. (2025)
; 
Drouin et al. (2024)
 for GenericAgent runs.

Rubric-based LLM Judge.

We use Qwen 3.6 27B as the LLM judge, the last grader of the rubric-based verifier described in Section 
3.3
. We chose it over more expensive alternatives, Gemini 3.1 Pro and Kimi 2.6, because it agrees with human annotations nearly as well while being open-weight and cost-efficient (Appendix 
D
).

Metrics.

We report task Success Rate (SR) as our primary metric, defined as the fraction of tasks for which every rubric passes under the rubric-based grader of Section 
3.3
. To capture partial progress on unsuccessful tasks, we also report a partial-completion score that measures the fraction of rubric items passed per task, in Appendix 
B.2
.

5 
Discussion

Costs.

The cost of each agent run depends on its architecture, harness, and underlying model. We report recorded API costs for a 300-task evaluation, including retries and recovery runs but excluding hosting infrastructure. GenericAgent costs approximately USD 800 with Claude Opus 4.7. For the coding agents, recorded costs including agent inference are USD 386 for Claude Code with Opus 5.5, USD 166 for Codex with GPT 6.1 Sol, USD 689 for OpenCode with Qwen 3.8 Max Prime, and USD 340 for OpenCode with Kimi 3.1 Pro. Judging with Qwen 3.6 27B through OpenRouter accounts for less than USD 4 per 300-task evaluation in these coding-agent runs.

Future work.

The same self-hosted infrastructure that supports parallel evaluation can also serve as a training environment, where the rubric-based verifier provides a per-task reward signal for reinforcement learning or rejection sampling. The controlled environment also supports robustness studies that perturb the underlying web pages to test resilience to UI drift and prompt injection. Finally, expanding the action space to richer temporal modalities such as live voice and streaming video would let the benchmark track agents that move beyond static page interaction.

6 
Conclusion

We presented WebArena-Pro, a reproducible benchmark of 300 human-validated tasks across 20 self-hosted web applications spanning six domain categories. It treats audio and video as core observations alongside text and vision, and runs each task in container isolation for reproducible parallel evaluation.
Across twelve model backbones and four agent harnesses, the strongest agent, Claude Code with Opus 5.5 and Codex with GPT 6.1 Sol, reach only 62.3% success at a 50-step budget, with cross-site tasks remaining harder than single-site ones, and media-access ablations demonstrate the importance of accessing audio and video content. These results indicate considerable headroom for progress on heterogeneous, multimodal web agents.

Limitations

We note the following limitations to our work.

Limited Temporal Interaction.

Our action-space extension covers only prerecorded audio segments and discrete video frames, leaving richer temporal interaction modalities such as voice dialogue and live video streams to future work.

Evaluation Comparability and Reliability.

Our comparisons evaluate particular combinations of models, harnesses, and tool configurations. Performance differences cannot generally be attributed to model capability or harness design alone. A shared 50-step budget also does not equalize computational resources: agents differ in token consumption, native tool use, observation frequency, and latency. Reported costs depend on provider pricing and cache utilization. Controlled comparisons across harnesses and repeated runs would strengthen conclusions about efficiency and reliability.

C.1 
GenericAgent Failure Modes

Across the eight models, failures involve incomplete workflows, unsuccessful navigation, incorrect selections, and premature termination. These patterns can overlap: an agent may repeatedly search for the wrong entity, exhaust its action budget, and leave a required action unfinished.

Model-level differences extend beyond trajectory length.
Table 
12
 provides qualitative examples of models’ failures.
Gemini 3.1 Pro has the lowest recorded failure rate.
Its qualitative failure examples include omitted artifacts and incorrect target entities.
Both Gemma models exhibit premature or empty finalizations in the reviewed examples.
Qwen 3.6 27B solves more tasks than Qwen 3.5 9B, but still exhibits missed end-state actions and incorrect entity or value selections.

Gadget

C.2 
Coding Agents Failure Modes

We analyze the five coding-agent configurations on the 300-task WebArena-Pro Test split: Claude Code, Codex, and OpenCode with Gemini 3.1 Pro, Kimi 3.1 Pro, and Qwen 3.8 Max Prime.
Table 
14
 illustrates representative failure modes.
Across the 1,500 runs, 375 of the 633 graded failures (59.2%) received partial reward.
Representative failures involve incomplete workflows or missing final state changes: agents prepared records without saving them, created files locally without placing them in the target application, or returned answers instead of updating the requested page.
Stale references, obstructed clicks, and ineffective recovery further disrupted execution.
Other observed failures involve cross-site coordination, visual event counting, and temporal localization despite successful media access.
Short trajectories sometimes reflect clarification requests or explicit refusals rather than premature abandonment.

Figure 
6
 shows trajectory lengths for solved and unsolved tasks across all five configurations.
Of the 633 unsuccessful runs, 92 (14.5%) reached the 50-step limit.
The proportion was highest for OpenCode with Gemini 3.1 Pro (32.1%) and Kimi 3.1 Pro (20.3%), compared with 8.0% for Codex, 3.8% for OpenCode with Qwen 3.8 Max Prime, and 3.5% for Claude Code.
Most unsuccessful trajectories therefore end before exhausting the step budget.

Appendix E 
Websites

WebArena-Pro includes 20 containerized
website environments. Of these, 9 are built by adapting existing open-source
applications with benchmark-specific seeded data and reset logic, while 11 are
custom websites developed with AI assistance and human review. We provide details about the sources and Docker image sizes in Table 
16
. Additionally, in WebArena-Pro, there is no data is seeded after the container creation. For most websites, the data is seeded when building the image; the container can then be built fast. Exceptions are made for ERP-Next, which initializes the containers with data when it starts.

Media datasets.

Some WebArena-Pro environments required media-heavy seed datasets that are stored outside Git and baked into Docker images at build time. For Acidwave, we created a music catalog with CC-licensed MP3 assets and accompanying metadata, including title, artist, album, genre, duration, play counts, license, attribution, and source URL; the current seed references 50 unique audio files. For 
yt-lite
, we used samples from 
FineVideo
: videos were decoded locally, paired with generated thumbnails, and transcoded to 720p HEVC/H.265 for compression before being packaged in the yt-lite image. For Immich, we sampled photos from 
Open Images V7
, assigned them across the admin and agent accounts, manually curated them to remove low-quality, inappropriate, duplicate, or privacy-sensitive images, and then baked the uploaded photos, thumbnails, database state, and ML cache into the final image.
